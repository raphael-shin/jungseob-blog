## TL;DR

- 확인 질문 없이 에이전트를 돌리는 YOLO 모드는 편하지만, 에이전트가 사용자가 닿는 모든 것에 닿는다. 글은 에이전트를 샌드박스 안에서 YOLO로 돌리되, 허락한 것에만 닿고 키는 절대 보지 못하게 하자고 제안한다.
- Strands Box는 에이전트를 운영체제 샌드박스에 넣고, 셸 명령과 파일, 네트워크 요청, MCP 호출을 모두 정책으로 검사하는 오픈소스 도구다. 검사는 모델 밖에서 일어나서, 에이전트가 읽은 내용이나 스스로 내린 판단으로 결과를 바꿀 수 없다.
- 이번에 Claude Code, Codex, Kiro CLI를 `box run claude` 같은 한 줄로 상자 안에서 돌릴 수 있게 됐다. 팩은 프로그램 하나에 필요한 것을, 프로필은 팩을 묶은 에이전트의 역할을 담는다.
- 키는 상자 밖에 둔다. 에이전트는 자리표시자만 보고, 요청이 상자를 나갈 때 게이트웨이가 진짜 키로 바꿔 끼우니 에이전트가 키를 흘릴 수 없다. 다만 프로젝트 파일 등에 이미 적힌 키는 여전히 보인다.
- Dogwood 규칙은 세션의 지난 기록도 본다. 당직용 프로필은 지난 1시간에 끝난 AWS MCP 호출이 60번이면 61번째를 막고, 지금까지 찾은 것을 보고하라는 이유를 에이전트에게 돌려준다.

## 무슨 글인가

Strands Agents 블로그에 2026년 11월 23일 Mackenzie Zastrow와 Abhishek Srinivasa Raju Padmavathi가 올린 글이다. Strands Agents는 에이전트를 만드는 오픈소스 SDK이고 Strands Box는 그 프로젝트의 오픈소스 샌드박스다. 이 노트는 r.jina.ai로 받은 본문 약 1만 2천 자를 끝까지 읽었다. 그림 넷과 터미널 녹화 하나는 대체 문구로만 내용을 짐작했다. 글이 링크한 10월 Strands Box 소개 글, Marc Brooker의 'Strands Box: The Big Picture', Dogwood 저장소, 설치 문서는 열지 않았다. 자기 도구를 알리는 글이라, 동작 설명은 모두 만든 쪽의 설명이다.

## YOLO 모드의 딜레마

글은 개발자들이 점점 더 코딩 에이전트를 YOLO 모드로 돌린다는 데서 시작한다. 권한이나 보안 확인 창도 없고 명령 하나하나를 검토하지도 않는다. 사람이 다른 일을 하는 동안 에이전트는 계속 일한다. 많은 팀에게 이것이 에이전트가 일을 해내는 방식이다. 그런데 이는 에이전트가 사용자가 닿는 모든 것에 닿는다는 뜻이기도 하다. 글은 에이전트가 자격 증명을 흘리거나 지우지 말아야 할 것을 지운 이야기를 다들 봤다고 말한다. 모델은 계속 좋아지지만 모델의 선한 의도는 운영 데이터베이스를 걸 만큼 믿을 만하지 않다. 에이전트는 속을 수도 있다. 에이전트가 읽은 README나 웹 페이지가 사용자가 시킨 적 없는 일을 하라고 지시할 수 있다.

그래서 대부분 개발자는 두 가지 가운데 하나를 고른다. YOLO 모드로 돌리고 사고가 안 나길 바라거나 세션이 운영 서버나 자격 증명에 가까워질 때마다 한 단계씩 손으로 승인하는 방식으로 돌아간다. 새벽 3시에 호출을 받았는데 도구 호출마다 승인해야 한다면 에이전트가 아껴 주는 시간은 별로 없다. 글이 원하는 것은 샌드박스 안에서 YOLO로 돌리는 것이다. 에이전트는 자유롭게 일하지만 허락한 것에만 닿고 자격 증명은 보지 못한다. 알맞은 한계는 일마다 다르다. 한 프로젝트에서 코드를 쓰는 에이전트와 AWS 계정의 장애를 조사하는 에이전트는 필요한 접근이 다르다. 그래서 일의 종류마다 한계를 한 번 정하고 샌드박스가 모든 요청에 그것을 적용한다.

## 한 줄로 상자에 넣기

Strands Box는 10월에 나온 오픈소스 샌드박스로, 사용자 컴퓨터에서 에이전트를 가두고 에이전트가 하는 일을 정책에 비춰 검사한다. 이번 글은 여기에 Claude Code, Codex, Kiro CLI 기본 지원을 더했다고 알린다. 컴퓨터에 이미 설치된 에이전트와 도구로, 프로젝트 폴더에서 `box run claude` 한 줄을 치면 상자 안 세션이 시작된다. 처음 실행하면 `box`가 몇 가지를 묻고 에이전트를 돌릴 프로필을 쓴다. 그 뒤로는 같은 명령이 에이전트를 상자 안에서 시작한다. 여전히 Claude Code이고 평소처럼 쓰면 된다. Box는 아래에 깔려 있다가 에이전트가 닿으면 안 되는 것에 손을 뻗을 때만 나선다. Codex와 Kiro CLI도 같다.

## Box는 어떻게 동작하나

Box는 에이전트를 운영체제 샌드박스 안에서 돌려, 프로필이 허락한 파일에만 닿게 한다. 에이전트가 하는 나머지 모든 일은 Box를 거친다. 모든 셸 명령과 그 명령이 건드리는 파일, 모든 네트워크 요청, 모든 MCP 호출이다. MCP는 에이전트가 외부 도구에 연결하는 규약이다. Box는 이 요청을 하나하나 정책에 비춰 검사한다. 요청이 무슨 뜻인지 이해하기 때문에 규칙에 파일, 명령, 호스트, 도구를 이름으로 적을 수 있다. 검사는 모델 밖에서 일어난다. 그래서 에이전트가 무엇을 읽고 무엇을 결정하든 답이 바뀌지 않고 에이전트가 자기 정책을 고칠 수도 없다.

Box의 규칙은 Dogwood라는 정책 언어로 쓴다. 각 규칙은 파일 읽기, 명령 실행, 호스트로 요청 보내기, MCP 도구 호출처럼 에이전트가 실제로 하는 일에 관한 것이다. 그래서 구체적으로 적을 수 있다. 뒤에 나올 코딩 프로필에서는 에이전트가 `~/.shared`는 읽지만 그 안의 비밀 폴더는 읽지 못한다. 규칙은 세션에서 에이전트가 이미 한 일을 돌아볼 수도 있다. 당직 프로필은 이를 써서 에이전트가 한 시간에 하는 AWS 호출 수에 상한을 둔다. 단순한 허용이나 거부로는 할 수 없는 일이다.

## 팩과 프로필

에이전트를 Strands Box에서 돌리려면 여러 가지가 맞아야 한다. Claude Code를 샌드박스 안에서 돌리려면 Box가 프로세스와 설정을 잡고 사용자 키를 붙여 모델로 가는 경로를 만들어야 한다. Box CLI에는 이 일을 대신 해 주는 두 층이 있다. 팩은 프로그램 하나가 상자 안에서 필요로 하는 것을 담는다. 에이전트 자체, 모델 제공자, 도구가 모두 팩이다. 팩은 프로그램을 어떻게 시작하고 무엇이 필요한지를 적는다. 예를 들어 `@box/bedrock` 팩은 에이전트의 모델 요청을 Amazon Bedrock으로 보내고 나가는 길에 API 키를 붙인다. CLI는 에이전트(Claude Code, Codex, Kiro CLI), 모델 제공자(Amazon Bedrock, Anthropic), 일상 도구(git, gh, npm, uv, cargo)용 팩을 함께 준다. 프로필은 팩을 묶어 하나의 에이전트 역할로 만든다. 프로필에는 쓸 팩, 정책 파일, 사용자 설정이 들어간다.

## 키는 상자 밖에

에이전트가 일하려면 키가 필요하다. 모델 API 키, GitHub에 올릴 토큰, 계정을 들여다볼 AWS 자격 증명 같은 것이다. Box에 경로로 키를 주면 Box는 그 키를 상자 밖에 둔다. 에이전트는 자리표시자만 보고 요청이 상자를 나갈 때 Box의 출구 게이트웨이가 진짜 키로 바꿔 끼운다. 에이전트가 키를 쥐지 않으니 흘릴 수도 없다. 글은 이 보호가 경로로 준 키에만 해당한다고 분명히 한다. 프로젝트 파일에 있거나 MCP 서버 설정에 적힌 키처럼 에이전트가 이미 읽을 수 있는 키는 여전히 보인다. 그러니 그런 키는 경로로 옮기라고 권한다.

`@box/bedrock` 팩은 이미 모델 키를 이렇게 다룬다. 다른 키는 프로필에 경로를 더하면 된다. 글의 코딩 에이전트는 github.com으로 가는 경로를 두고 환경 변수의 토큰을 기본 인증 방식으로 끼워 넣는다. 상자 안에서 그 변수는 자리표시자이고 github.com으로 가는 요청이 상자를 나갈 때 게이트웨이가 진짜 토큰을 넣는다. 경로는 AWS 프로필에서 키를 가져올 수도 있다. `aws://<profile>`을 쓰면 Box가 그 프로필의 자격 증명으로 요청마다 서명한다. 뒤에 나올 당직 에이전트가 이 방식을 쓴다.

## 코딩 에이전트 프로필

프로필은 원하는 만큼 두고 `box run <profile>`로 그때그때 고른다. 프로필마다 만들 때 고른 기본 정책에서 출발하고 그 위에 자기 규칙을 더한다. 글은 `coding`과 `oncall` 두 예시를 든다. 둘 다 `profile.toml`에서 Claude Code의 권한 확인 창을 끈다. 상자가 대신 결정하기 때문이다. 글쓴이들은 이 글의 정책을 손으로 쓰지 않았고 독자에게도 그러길 기대하지 않는다고 밝힌다. Box는 에이전트가 정책을 써 주도록 만들어졌고 모든 프로필에는 코딩 에이전트용 안내서가 딸려 있다. 원하는 규칙을 상자 밖의 일반 에이전트에게 설명하고 쓴 것을 읽고 `box profile show`로 확인한다.

코딩 에이전트는 한 프로젝트에서 코드를 쓴다. 그 프로젝트를 읽고 바꾸고 git과 npm을 돌리고 모델과 npm 레지스트리에 닿고 앞의 경로로 GitHub에 올린다. 일하다가 정책을 고쳐야 할 때도 있다. 예를 들어 코딩 에이전트가 프로젝트 밖의 공유 메모 폴더 `~/.shared`가 필요하다고 하자. 처음에는 허락하는 규칙이 없어 상자가 읽기를 거부하고 에이전트 아래에 뜨는 상태 줄에 거부가 표시된다. 그러면 다른 터미널에서 상자 밖의 Claude Code에게 그 폴더는 읽기로 열되 `~/.shared/.secrets`의 자격 증명은 닫아 두라고 부탁한다. 그 에이전트는 허용 규칙 하나와, 그 폴더에 자격 증명이 있으니 필요한 걸 사용자에게 물으라는 설명이 붙은 금지 규칙 하나를 더한다. 세션을 다시 시작할 필요는 없다. Box CLI가 수정을 확인하고 상태 줄에 업데이트가 준비됐다고 띄우면, 키 하나로 적용되고 에이전트는 계속 돈다. 같은 세션에서 에이전트는 이제 메모를 읽지만 그 안의 비밀 폴더는 못 읽는다. 규칙이 요청을 거부하면 Box는 규칙의 설명을 이유로 에이전트에게 돌려준다. 그래서 에이전트는 무작정 다시 시도하지 않고 대응할 수 있다.

## 당직 에이전트 프로필

두 번째 프로필은 새벽 3시의 당직 엔지니어를 돕는다. 이 에이전트는 코드를 쓸 필요가 없다. AWS 계정에서 무슨 일이 일어나는지 살펴보고 찾은 것을 보고한다. 가장 엄격한 `locked` 정책에서 출발해, 모델과 AWS MCP 서버에만 요청을 보내고 네트워크의 다른 곳에는 닿지 않는다. AWS MCP 서버로 가는 경로는 `aws://`를 써서, 읽기 전용 AWS 프로필로 Box가 요청마다 서명한다. 그래서 에이전트는 AWS 키에 직접 닿지 않는다.

호출 수 제한은 기록에 기대는 규칙이다. 장애의 근본 원인을 못 찾은 에이전트는 계속 조사하면서 같은 도구를 거듭 부르고 사람이 반쯤 잠든 사이 토큰과 API 호출을 태울 수 있다. 이 규칙은 지난 1시간 동안 끝난 AWS MCP 도구 호출을 세어 60번이 되면 61번째를 거부하고 지금까지 찾은 것을 사용자에게 보고하라는 메시지를 돌려준다. 두 프로필 모두 Claude Code를 돌리지만 에이전트에게 허락하는 일은 아주 다르다. 각자 저장소도 따로 둬서, 당직 에이전트의 세션과 기억이 코딩 에이전트의 상자에 나타나지 않고 그 반대도 마찬가지다. 글쓴이들은 당직용까지 두 프로필 모두 YOLO 모드로 돌린다고 밝힌다. 경계를 미리 정했고 에이전트가 그것을 바꿀 수 없기 때문이다. 다만 데이터만 읽고 상태를 바꾸는 API는 부르지 않는 프로필은 운영 에이전트에 잘 맞지만 일상 작업에는 더 느슨한 프로필과 정책이 필요할 때가 많다고 덧붙인다.

## 써 보기

Box CLI는 macOS 15 이상의 Apple silicon Mac과, ARM64와 x86-64 Linux에서 돈다. 설치 스크립트 한 줄로 설치하고 프로젝트에서 `box run claude`를 치면 된다. 글은 코딩 프로필로 시작해 에이전트에게 `~/.shared/.secrets`의 파일을 읽게 하고 상자가 거부하는 걸 지켜본 뒤, 자기 방식에 맞게 규칙을 바꿔 보라고 권한다. 기대대로 동작하지 않거나 아직 없는 도구의 팩이 필요하면 GitHub에 이슈를 열라고 한다.

## 읽을 때 생각할 점

이 글은 만든 쪽이 자기 도구를 알리는 글이다. 모델 밖에서 검사하니 에이전트가 정책을 바꿀 수 없다는 설명은 설계의 주장이고 이 노트는 실제로 돌려 보거나 우회 가능성을 따져 보지 않았다. 글이 스스로 밝힌 한계도 기억해 둘 만하다. 경로로 옮기지 않은 키는 에이전트에게 보이고 일상 작업에는 느슨한 정책이 필요할 때가 많다. 정책을 에이전트에게 쓰게 하고 사람이 읽어 확인하는 방식은 편하지만 결국 그 규칙을 읽고 승인하는 사람의 몫이 남는다. 예시는 Amazon Bedrock과 AWS MCP 서버를 쓰지만 글에 따르면 Anthropic 같은 다른 모델 제공자 팩도 있다.

권한 확인을 줄이는 다른 접근과 나란히 보면 좋다. Claude Code의 auto mode와 훅을 다룬 [Hallie 노트](https://raphael-shin.github.io/jungseob-blog/posts/hallie-rethinking-claude-code-best-practices/), Codex의 원격 실행과 클라우드 환경을 다룬 [OpenAI Codex 노트](https://raphael-shin.github.io/jungseob-blog/posts/openai-new-ways-of-working-with-codex/), 배경에서 계속 도는 에이전트를 다룬 [always-on 에이전트 노트](https://raphael-shin.github.io/jungseob-blog/posts/anthropic-building-always-on-agents/)가 있다. 같은 프로젝트의 작은 판단 모델 이야기는 [Strands Decider 노트](https://raphael-shin.github.io/jungseob-blog/posts/strands-decider-2b-small-decision-model/)에 있다.

내 일에 가져올 질문은 이렇다. 우리 팀의 에이전트가 지금 읽을 수 있는 키는 어디에 몇 개나 있는가? 코딩용과 운영용 에이전트에게 같은 권한을 주고 있지는 않은가? 에이전트가 같은 도구를 끝없이 부를 때 시간과 호출 수의 상한은 어디에 걸려 있는가?
