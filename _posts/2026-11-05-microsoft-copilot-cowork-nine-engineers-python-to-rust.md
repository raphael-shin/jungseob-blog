## TL;DR

- Microsoft의 작은 팀이 에이전트에게 코드 대부분을 맡겨 Copilot Cowork를 만들었다. 1월 13일 빈 저장소에서 시작해 6월 16일 전 세계 정식 출시까지 약 4개월 반이 걸렸다. 10월 21일에는 엔지니어 9명이 하루에 PR 1,211개를 병합했다.
- 가장 큰 병목은 에이전트가 아니라 "정확히 뭘 원하는지 모르는 것"이었다. 그래서 코드보다 마크다운 명세를 먼저 쓰는 규칙을 만들었다.
- 에이전트는 사용자 인증 정보 없이 컨테이너에서 돈다. 계획은 무엇이든 세울 수 있지만, 실제로 무엇을 실행할지는 바깥의 신뢰할 수 있는 호스트가 정한다.
- 늘 통과하던 검사가 사실 아무것도 검사하지 않은 일이 있었다. 그래서 모든 검사는 몇 개 파일을 봤는지 보고하고, 일부러 실패시키는 테스트를 함께 둔다.
- 운영 중에 런타임을 Python에서 Rust로 옮겼다. Python이 실제로 한 동작을 기록해 Rust가 똑같이 재현하는지 시험했다. 첫 응답까지 걸리는 시간(중앙값)은 7.9초에서 2.7초로 줄었다.

## 무슨 글인가

Microsoft 엔지니어링 블로그 Command Line에 2026년 11월 2일 실린 글이다. 쓴 사람은 Microsoft의 Partner Software Engineer Bas Brekelmans다. 본문을 끝까지 읽었고 글에 실린 그림 세 장 중 월별 PR 차트도 직접 봤다.

Copilot Cowork는 사용자를 대신해 여러 단계의 업무를 실행하는 Microsoft 365의 에이전트 기능이다. 개발자가 쓰는 AI 도구의 능력을 일반 사무직에게 주는 것이 목표다.

일정은 이렇다. 1월 13일 첫 커밋, 3월 30일 일부 기업 고객에게 첫 공개(Frontier 프로그램), 6월 16일 전 세계 정식 출시(GA). 그 뒤 9월 23일부터 10월 10일까지 운영 중인 런타임을 Python에서 Rust로 옮겼다.

필자는 이렇게 말한다. "에이전트가 코드 대부분을 썼다. 하지만 일을 정의하고 결과를 판단하는 책임은 엔지니어에게 남았다." 그리고 이렇게 일할 계획은 없었다고 한다. 몇 주마다 에이전트가 좋아졌고 그때마다 기존 방식 일부가 안 통하게 되어 바꿔 왔을 뿐이다.

## 교훈 1: 코드보다 명세를 먼저 쓴다

첫 몇 주 동안 팀이 배운 것은 이것이다. 속도를 늦추는 건 에이전트가 아니었다. 정확히 무엇을 원하는지 모르는 것이 병목이었다. 막연하게 요청하면, 그럴듯해 보이고 대충 읽으면 통과하지만 엉뚱한 일을 하는 코드가 나왔다. 그걸 고치는 데 제대로 된 요청을 쓰는 것보다 더 오래 걸렸다.

그래서 지금도 지키는 규칙이 생겼다. 마크다운 명세 없이는 코드도 없다. 명세에는 세 가지를 쓴다. 이 변경이 무엇을 하는지, 잘 됐는지 어떻게 알 수 있는지, 무엇을 망가뜨리면 안 되는지다. 에이전트가 빨라질수록 의도와 요구 사항을 정확히 적는 일이 더 중요해졌다.

명세는 말로 시작하는 경우가 많다. 누군가 기능을 말로 설명하면, 에이전트가 그걸 명세 초안으로 바꾸고 사람이 고친다. 필자는 이 방식이 어떤 모델 업그레이드보다 속도에 더 크게 기여했다고 본다.

## 교훈 2: 좁은 에이전트를 경계 안에서 돌린다

다음은 여러 에이전트를 동시에 돌리는 것이었다. 에이전트마다 자기 저장소 사본에서, 명세 하나로, 일 하나만 한다. 에이전트 하나가 다섯이 되고 다섯이 수십이 됐다. 월별 병합 PR은 1월 257개에서 5월 2,754개로 늘었다. 글의 차트를 보면 9월에는 약 6,360개, 10월은 20일 동안 약 1만 300개다.

병렬 작업이 예상보다 잘 된 이유는 두 가지다. 첫째, 일이 좁았다. 잘 정의된 일 하나를 맡은 에이전트는 한꺼번에 여러 일을 맡은 에이전트보다 실수가 적다. 둘째, 일마다 모델을 골랐다. 가장 싼 모델을 쓰려 하지 않고 품질과 비용의 균형으로 판단했다. 어려운 일엔 추론이 강한 모델을, 다른 일엔 빠르고 싼 모델을 썼다.

보안 구조도 중요했다. Copilot Cowork에서 모델은 사용자 인증 정보가 없는 컨테이너 안에서 돈다. 컨테이너 바깥의 신뢰할 수 있는 호스트가 신원, 정책, 승인, 도구 실행을 맡는다. 모든 Microsoft 365 작업은 이 호스트를 거친다. 팀은 에이전트가 시도할 수 있는 일을 제한하지 않았다. 너무 제한하면 쓸모가 없기 때문이다. 모델은 무엇이든 계획하고 요청할 수 있지만 실제로 무엇이 일어날지는 호스트가 정한다.

이 구조를 처음부터 넣은 덕을 나중에 봤다. 에이전트가 정해진 접점으로만 호스트와 말하므로, 에이전트를 바꾸지 않고 호스트 전체를 갈아 끼울 수 있었다. Rust로 옮길 때 실제로 그렇게 했다.

## 교훈 3: 검사가 실제로 검사했는지 증명하게 한다

에이전트가 코드 대부분을 쓰니, 9명이 모든 변경을 읽을 수 없었다. 사람 리뷰를 기다리는 시간이 가장 느린 단계가 됐다.

그래서 엔지니어 몇 명이 각자 자기 리뷰 방식을 본뜬 리뷰 봇을 만들었고 봇끼리 경쟁시켰다. 한 봇이 놓친 문제를 다른 봇이 잡으면, 놓친 봇에게 새 규칙을 더했다. 봇마다 리뷰하고 놓친 것을 돌아보고 나아지는 과정을 최소 1만 세대 거쳤다. 지금은 PR을 열고 몇 분 안에 첫 리뷰가 온다. 최근 병합된 PR 표본에서 중앙값은 약 4분 30초였다. 그 뒤에 더 느리고 전문적인 리뷰가 따른다. 연결이 안 된 코드나 변경을 되돌려도 통과할 테스트를 찾는 리뷰, 재시작 안전성과 지표를 보는 리뷰, 바뀐 파일을 처음부터 끝까지 읽는 리뷰, 바꾸려는 옛 코드와 동작을 비교하는 리뷰다.

그래도 리뷰 봇은 놓친다. 제품에서 가장 민감한 부분의 변경을 리뷰 봇 여러 개가 "깨뜨려 보라"는 지시를 받고 읽었지만 아무 문제도 못 찾았다. 그런데 사람이 같은 변경을 읽고 병합을 막아야 할 문제 4개를 찾았다. 그래서 중요한 변경에는 사람 확인을 최소 한 번 두었다. 리뷰 결과도 두 단계로 나눴다. 정확성, 보안, 데이터 손실, 깨져도 잡아낼 테스트가 없는 새 구조는 병합을 막는다. 나머지는 참고 사항이다.

가장 흥미로운 규칙은 "실패할 수 없는 검사"에서 나왔다. 에이전트가 읽는 지시 파일에는 크기 제한이 있다. 바이트가 늘수록 매번 토큰이 들기 때문이다. 그런데 제한을 넘었는데도 검사는 계속 초록불이었다. 스크립트가 검사 결과를 `tail` 명령으로 넘겼는데, 셸 파이프라인은 마지막 명령의 종료 코드를 돌려준다. `tail`은 늘 성공하니 검사도 늘 성공했다. 찾아보니 비슷한 문제가 더 있었다. 빈 파일 목록을 받아서 아무것도 안 보고 통과한 서식 검사, 커밋하자마자 바뀐 파일 목록이 비어 버리는 경우다.

그래서 두 가지 규칙을 만들었다. 모든 검사는 몇 개 파일을 봤는지 보고한다. 새 검사에는 일부러 실패하게 만드는 테스트가 함께 있어야 한다. 필자는 이것이 에이전트가 있을 때 더 중요하다고 말한다. 에이전트는 검사를 통과할 때까지 일하므로, 아무것도 검사하지 않고 통과하는 길이 있으면 결국 그 길을 찾아낸다.

## 교훈 4: 팀이 배운 것을 저장소에 남긴다

8월이 되자 같은 실수가 자꾸 돌아왔다. 에이전트는 매번 이전 작업의 기억 없이 시작하기 때문이다. 그래서 팀의 규칙을 저장소로 옮겼다. 저장소 최상위와 각 구성 요소에 지시 파일을 두고 주제별 규칙 파일 폴더를 만들었다. 에이전트는 일을 시작할 때 관련 파일을 읽는다. 무언가 잘못되면 수정에는 대개 새 규칙이나 고친 규칙이 포함된다. 지금 규칙 파일은 약 30개이고 가장 오래된 것은 8월 6일에 만들어졌다.

초기 규칙 하나는 병합 충돌에 관한 것이다. 하루 수백 건을 병합하다 보니, 충돌은 거의 실제 로직이 아닌 곳에서 났다. 모든 브랜치가 한 줄씩 덧붙이는 파일이었다. 등록 목록, 자동 생성 파일, "마지막 수정일"이 적힌 문서 같은 것이다. 팀은 사람에게 충돌을 더 조심히 풀라고 하는 대신 파일 구조를 바꿨다. 등록 목록은 항목마다 파일 하나로 나눴다. 자동 생성 파일은 병합 후 다시 생성하고 손으로 병합하지 않는다. 날짜나 개수처럼 PR마다 바뀌는 값은 커밋하지 않는다.

## 교훈 5: 병렬 작업에 맞게 코드 구조를 만든다

저장소의 첫 Rust 코드도 대부분 에이전트가 썼다. 에이전트는 가장 쉬운 곳에 코드를 넣었고 그곳은 대개 가장 큰 크레이트(Rust의 패키지 단위)였다. 한때 주 실행 파일이 약 29만 줄이었다.

8월 20일에 상태를 점검하니 이랬다. 크레이트 86개가 13단계 깊이로 의존하고 있었다. 공통 기반 크레이트 하나를 바꾸면 63개 중 43개를 다시 빌드해야 했다. API 크레이트는 13만 4천 줄로 커졌다. 구현 크레이트끼리 순환 의존이 생겨, 비즈니스 로직 약 1만 2천 줄이 실행 파일 안에 들어가 있었다. 에이전트 여러 개가 동시에 일하는 팀에게 이건 문제였다. 대부분의 변경이 같은 몇 크레이트를 건드렸고 서로 충돌했다.

해결책은 엄격한 역할 규칙이었다. 모든 크레이트는 네 종류 중 하나다. 계약(타입과 인터페이스), 키트(내부 의존이 없는 공용 도우미), 구현, 실행 파일이다. 구현은 계약과 키트에만 의존할 수 있고 다른 구현에는 의존할 수 없다. 실행 파일만 구현에 의존하고 실행 파일에는 연결 코드만 둔다. 새 코드에는 예외가 없다. 과거에 허용한 예외 하나하나가 다음 예외의 핑계가 됐기 때문이다.

정리 작업은 작업 항목 401개, 그 사이 의존 관계 2,225개짜리 프로그램이 됐다. 가장 많을 때는 40~44개 항목이 동시에 진행 가능했다. 같은 파일을 건드리지 않는 묶음으로 나눠 에이전트끼리 충돌하지 않게 했다. 검사 도구의 임시 예외 목록조차 크레이트마다 파일 하나로 나눴다. 안 그러면 에이전트 20개가 한 파일을 동시에 고쳤을 것이다. CI 검사는 처음엔 보고만 했다. 그다음엔 예외 수가 줄어들 수만 있는 "래칫"이 됐다. 결과는 이렇다. 구현 간 의존 예외는 8월 22일 216개에서 10월 7일 0개가 됐다. 허용 의존 깊이는 10단계에서 3단계가 됐다. 크레이트 수는 86개에서 약 176개가 됐다.

빌드 시간 개선은 예상보다 작았다고 필자는 솔직히 쓴다. 컴파일 캐시가 이미 PR 빌드의 약 99%에서 맞고 있어서 빌드 시간의 들쭉날쭉함이 개선 폭보다 컸다. 대신 구조는 분명히 좋아졌다. 기반 크레이트를 바꿨을 때 순서대로 다시 빌드해야 하는 최장 경로가 11개에서 3개로 줄었다.

## 교훈 6: 자동 루프에 목표와 한계를 준다

올해 대부분은 사람이 에이전트에게 지시하고 결과를 읽고 다음을 정했다. 지금은 자동 루프로 도는 일이 늘었다. 루프는 측정할 수 있는 목표 하나를 받고 목표에 닿거나 시도 횟수가 바닥날 때까지 일한다. 사람은 목표를 정하고 무엇이 나빠지면 안 되는지 정하고 운영에 나가는 일은 최종 결정을 한다.

예를 들어 테스트 속도 루프가 있다. 목표는 CI가 테스트에 쓰는 시간이다. 이 루프는 느린 테스트를 빠르게 하거나 다른 테스트가 이미 하는 일을 겹쳐 하는 테스트를 지우는 PR을 연다. PR은 CI 시간 자료에서 해당 테스트가 최소 5% 빨라졌을 때만 병합된다. 리뷰 단계에서 모든 검증문을 원본과 비교해, 빨라진 테스트가 덜 검사하는 테스트가 아닌지도 본다. 9월 중순 이후 이런 PR 약 300개가 병합됐고 해당 테스트 파일의 CI 시간은 약 1만 7,700초에서 약 1,700초로 줄었다.

문서 품질 루프도 있다. 문서를 만드는 스킬을 고친 뒤, 정해진 과제에서 이전 버전과 결과를 비교한다. 세 조건을 모두 지켜야 남긴다. 비교에서 이긴 횟수가 진 횟수보다 많아야 하고 하위 10% 점수가 나빠지지 않아야 하고 필수 검사가 실패하면 안 된다. 10번 중 3번만 남았다. 비교에선 이겼지만 가장 못한 결과가 나빠져서 버린 경우도 있었다.

가장 새로운 루프는 팀이 "공장"이라 부르는 것이다. 공장은 자잘한 엔지니어링 일을 받는다. 새 릴리스가 만든 오류 묶음, 특정 도구를 가리키는 사용자 의견, 한 시간 전에 깨진 메인 빌드, 크기 한도를 넘은 파일 같은 것이다. 하나하나는 작지만 사람이 집어 들 수 있는 속도보다 빨리 쌓인다. 정해진 규칙이 이런 신호를 작업 항목으로 바꾸므로 아무도 티켓을 쓰지 않는다. 경보를 모델에게 맡기지도 않는다. 공장은 고객 콘텐츠에 접근하지 않고 로그와 사용자 의견만으로 문제를 재현한다.

각 항목은 운영 숫자에서 시작한다. 예를 들어 "대화 688개에서 거부된 요청 2,148건" 같은 것이다. 항목은 사람이 밟을 단계를 그대로 거친다. 조사, 설계, 구현, PR이다. 중요한 단계마다 검사 대상과 다른 계열의 모델이 비평가로 붙는다. PR을 열기 전에 공장은 수정을 되돌리고 새 테스트를 다시 돌린다. 수정 없이도 테스트가 통과하면 증거로 치지 않고 내보내지 않는다. 병합이 끝도 아니다. 공장은 병합된 커밋이 릴리스와 첫 운영 단계에 들어갔는지 따라가고 수정이 들어간 빌드에서 신호가 실제로 줄었는지 확인한다. 문제가 돌아오면 새 작업 항목이 된다. 10월 12일 주에는 PR 4,581개, 하루 약 650개가 병합됐고 그중 공장이 만든 비율이 늘고 있다.

팀은 모든 루프를 시작하기 전에 네 가지를 정한다. 변경을 남길지 되돌릴지 정하는 글로 쓴 규칙, 나빠지면 안 되는 지표, 시도 횟수 한계, 여전히 사람이 해야 하는 행동 목록이다. 예를 들어 PR을 병합까지 끌고 가는 에이전트는 20번 시도하거나 같은 CI 실패를 3번 만나면 멈춘다. 운영 배포와 설정 변경은 여전히 사람이 한다.

## 사례: 운영 중에 Python에서 Rust로

필자는 Python 덕에 6월 출시를 맞췄다고 말한다. 다른 언어였다면 못 했을 것이라고 본다. 하지만 출시 뒤 규모가 커지자 세 가지 문제가 생겼다. 첫째, 이벤트 루프 멈춤이다. Python 프로세스마다 이벤트 루프가 하나라서, 부하가 걸리면 최대 11.9초까지 멈췄다. 그동안 잠금 갱신까지 기다리다 보니 일부 작업은 도중에 잠금을 잃었다. 둘째, 숨은 타임아웃이다. 세션 준비의 16.7%가 정확히 5.000초 걸렸는데, 실제 일이 아니라 타임아웃이 터진 것이었다. 셋째, 메모리다. 메모리가 부족하면 강제 종료되는 프로세스는 거의 늘 Python이었다. 한 클러스터에서 일주일에 539번이었다. 막히는 작업을 이벤트 루프 밖으로 빼 보기도 했다. 도움은 됐지만 근본 한계가 하나뿐인 루프 자체라는 것만 확인했다.

앞의 교훈들이 이번 언어 전환에 모두 쓰였다. 트래픽을 옮기기 전에 실행 절차서와 설계 기록을 썼다. 에이전트가 하위 시스템을 동시에 옮겼고 Rust 커밋은 7월 약 200개에서 9월 약 3,900개로 늘었다. 정리된 크레이트 구조 덕에 이 작업들은 대부분 충돌하지 않았다.

어려운 건 옮긴 코드가 맞는지 아는 일이었다. Rust와 Python을 나란히 읽는 방식은 규모가 커지면 안 된다. 그래서 팀은 Python이 실제로 한 일을 기록했다. 옮길 동작마다 작은 생성기가 진짜 Python 코드를 여러 입력으로 돌린다. 그리고 응답 내용, 상태 코드, 로그, 저장 기록을 JSON 파일로 남긴다. 팀은 이것을 "픽스처"라 부른다. Rust 테스트는 이 픽스처를 재생해서 정확히 같은 결과를 내야 한다. 픽스처는 아무도 손으로 고치지 않고 생성기는 픽스처가 Python과 어긋나면 실패하는 검사 모드도 있다. 픽스처는 약 430개다. 테스트는 비교 전에 사례 수부터 확인한다. 사례가 0개여도 통과하기 때문이다. 앞서 말한 "검사가 실제로 검사했는지 증명하라"는 규칙이 여기서도 쓰였다. Python이 지워진 뒤에도 마지막 픽스처는 Rust 코드의 명세로 남는다.

트래픽은 언제든 되돌릴 수 있는 스위치 뒤에서 클러스터 하나씩 옮겼다. 9월 23일 첫 내부 시도는 되돌렸다. 9월 24일 Rust가 처음 운영 요청을 처리했다. 10월 9일 Python 런타임을 지웠다. 테스트와 생성 코드를 포함해 파일 약 8천 개, 490만 줄이었다. 10월 10일 마지막 클러스터를 옮겼다.

결과는 이렇다. 9월 말 같은 12시간 동안 Rust 클러스터와 Python 클러스터를 비교하니, 세션 첫 요청의 첫 응답까지 시간이 중앙값 7.9초에서 2.7초로, 상위 10% 지점에서 14.5초에서 6.2초로 줄었다. 하지만 필자는 이게 다 Rust 덕은 아니라고 분명히 쓴다. 같은 변경에서 에이전트 루프를 시작이 느린 컨테이너 밖 Rust 서비스로 옮겼고 그 영향이 클 것이라고 본다. 이벤트 루프 멈춤과 5초 지연은 사라졌다. 요청당 비용은 아직 제대로 재지 않아서 비용 주장은 하지 않는다고 했다.

잘못된 것도 두 가지 있었다. 첫째, 이벤트 순서다. Python은 아무도 명세하지 않았는데 특정 이벤트를 순서대로 보내고 있었고 첫 Rust 버전은 그러지 않았다. 순서를 기록할 생각을 아무도 안 했기 때문에 픽스처가 잡지 못했다. 둘째, 느린 첫 응답이다. 첫 Rust 버전은 새 메시지를 받았다고 알리는 데 약 6배 오래 걸렸다. 전체 처리를 다 받아 놓은 뒤에 답했기 때문이다. 둘 다 고쳤다.

## 여섯 가지 교훈이 말하는 것

필자는 PR 수를 목표로 삼지 말라고 거듭 말한다. 핵심은 코드가 더 빨리 들어올수록 더 중요해지는 결정과 통제에 사람의 주의를 옮기는 것이다. 지금 팀은 시간 대부분을 네 가지 결정에 쓴다. 무엇을 만들지, 경계를 어디에 그을지, 어떤 테스트가 변경이 맞다는 걸 증명하는지, 통과한 검사가 보이는 그대로의 뜻인지다. 엔지니어는 과정에서 빠지지 않았다. 경계를 정하고 사람 리뷰가 꼭 필요한 곳을 고르고 운영에 나갈 준비가 됐는지 판단하는 데 더 많은 시간을 쓰게 됐을 뿐이다.

처음 시작하는 팀에게 주는 조언은 단순하다. 에이전트 수십 개로 시작할 필요는 없다. 팀이 믿는 검사 하나를 골라 일부러 실패시켜 보고 실제로 실패하는지 확인하라. 그다음 범위가 정해진 일 하나를 골라, 성공이 무엇이고 무엇을 망가뜨리면 안 되는지 적어라. 그리고 에이전트가 그 한계 안에서 일할 때 무엇이 달라지는지 보라.

## 확인해 본 것

글에 실린 월별 PR 차트를 직접 읽었다. 1월 257개, 5월 2,754개로 본문 숫자와 같다. 차트에는 9월 약 6,360개, 10월 1~20일 약 1만 323개도 보인다. 본문의 일정표와 Python·Rust 응답 시간 표(중앙값과 상위 10%)도 원문 그대로 옮겼다.

확인하지 못한 것도 있다. 하루 1,211개 PR, 리뷰 봇의 1만 세대, 테스트 시간 1만 7,700초에서 1,700초, Rust 응답 시간 개선은 모두 Microsoft 팀의 자체 수치이고 외부에서 검증한 자료는 없다. 글은 어떤 모델을 썼는지, 비용이 얼마였는지 밝히지 않는다.

## 읽을 때 생각할 점

이 글은 Microsoft가 자사 제품의 개발 방식을 소개하는 엔지니어링 블로그 글이다. 제품 홍보의 성격도 있다. 다만 필자는 실패와 한계를 꽤 솔직하게 적는다. 리뷰 봇이 놓친 문제 4개, 예상보다 작았던 빌드 시간 개선, Rust 덕만은 아닌 속도 개선, 재지 않은 비용, 놓친 이벤트 순서가 그 예다.

PR 수는 노력의 지표일 뿐 성과가 아니다. 필자 스스로 "PR 수를 따라 하라는 게 아니다"라고 쓴다. 특히 10월 PR 급증은 Rust 이전과 공장 루프가 겹친 시기여서, 작은 변경이 많이 쪼개져 들어왔을 수 있다.

내 일에 가져올 질문은 이렇다. 우리 CI 검사 중에 실제로 아무것도 검사하지 않고 통과하는 것은 없는가? 에이전트에게 일을 맡길 때 "무엇을 망가뜨리면 안 되는지" 적어 주는가? 시스템을 옮길 때 옛 시스템이 실제로 한 동작을 기록해 새 시스템과 비교하는가?
