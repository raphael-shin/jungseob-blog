## TL;DR

- Zakariasson의 출발점은 소프트웨어 공장이 아직 완성되지 않았다는 고백이다. Cursor의 일부 제품과 일부 조직만 상당히 자율적으로 돌고, 공장은 물리 공장처럼 조립 라인과 관리와 관측이 필요하다. 그는 Dan Shapiro의 단계에서 자신이 레벨 4, 곧 가능한 한 많은 일을 에이전트에 넘기고 코드보다 결과물을 먼저 보는 단계에 있다고 한다.
- 공장의 재료는 세 가지다. 에이전트가 쉽게 찾고 그대로 따르는 코드 구조와 사용 패턴, 과하지 않게 풀어 두는 규칙과 훅과 테스트, 그리고 스킬과 외부 맥락과 개발 환경 같은 이네이블러다. 규칙은 미리 많이 설치하는 것이 아니라 에이전트가 어긋나는 것을 보고 그때그때 만들어야 한다.
- 일하는 방식이 바뀐다. 작업자에서 관리자로, 동기에서 비동기로 가며 맥락을 앞에 몰아 주고, 에이전트마다 격리된 환경을 쓰며, 사람이 복사해 붙이는 지점을 찾아 자동화하고, 어긋난 에이전트를 규칙의 단서로 삼아 공장을 개선한다.
- Cursor 내부 사례로 위험도로 PR을 분류해 낮은 위험은 승인하는 에이전틱 코드 오너, 반복 업무를 찾는 분석과 병합된 PR의 리뷰 코멘트에서 배우는 자동화, 대화 기록에서 규칙을 뽑는 지속 학습 플러그인, Linear 이슈마다 클라우드 에이전트를 띄우는 트리아지를 보여 준다. 공식 문서와 블로그가 대부분 확인해 준다.
- 이 워크숍은 2026년 4월, Cursor 3 출시 직후의 이야기다. 이후 Cursor는 SpaceX에 인수되었고 프로젝트와 매니저 에이전트 층이 나왔으므로 제품 세부는 낡았을 수 있고, 발표자는 공급사 직원이며 수치는 대부분 정성적이다.

## 워크숍에 대하여

AI Engineer 채널이 2026년 4월 28일에 올린 1시간 23분 36초 워크숍이다. 발표자 Eric Zakariasson은 Cursor에서 개발자 경험과 제품을 맡는 엔지니어다. 영어 자동자막 전체를 읽었고 마지막 타임스탬프가 영상 길이와 맞는다. 절반쯤은 청중 질의응답이다. 이 블로그의 [Cursor 하네스 토큰 효율 노트](https://raphael-shin.github.io/jungseob-blog/posts/cursor-harness-token-efficiency-and-cache-reuse/)와 [Owain Lewis의 OpenAI 소프트웨어 공장 노트](https://raphael-shin.github.io/jungseob-blog/posts/owain-lewis-openai-software-factory-codex-ci-loop/), [매니저 에이전트 노트](https://raphael-shin.github.io/jungseob-blog/posts/devsibling-manager-agent-standard-agent-management/)가 같은 주제를 다른 회사와 시점에서 본 글이다.

## 자율성 단계와 공장의 이유

그는 Dan Shapiro가 올해 초 쓴 글의 자율성 단계를 쓴다. 맨 아래는 자동 완성을 조금 넘은 수준(Cursor가 2022~2023년에 있던 곳)이고 사람들 대부분은 짝 프로그래머로 에이전트와 주고받는 레벨 2에서 3 사이에 있다. 에이전트가 대부분의 코드를 쓰고 사람이 검토하는 레벨 3을 지나 레벨 4에서는 가능한 한 일을 에이전트에게 넘기고 코드보다 산출물을 먼저 보며 때로 코드를 본다. 마지막은 소프트웨어 공장으로, Shapiro가 말하는 어두운 공장이다. 사람은 의도와 지시와 목표만 주고 에이전트가 코드를 만들고 시험하고 출시하는 과정은 보이지 않는다.

공장을 지으려는 이유는 세 가지다. 처리량이 늘고(에이전트는 24시간 돌고 자고 먹을 필요가 없다), 조립 라인이 일관된 산출물을 내며(에이전트가 확률적으로 느껴지면 가드레일이 부족하다는 신호이고 모델이 나아질수록 지시를 잘 따른다), 취향을 더 잘 활용한다는 것이다.

## 짓는 법: 프리미티브, 가드레일, 이네이블러

프리미티브는 코드 구조와 사용 패턴이다. 모듈화되고 코드가 가까이 모여 있으면 에이전트가 폴더 하나를 열어 관련 파일을 한꺼번에 찾고 사람이 새 코드베이스에 적응하기 쉬우면 에이전트도 그렇다. 인증이나 시작 스크립트, 테스트 작성 같은 보일러플레이트가 있으면 에이전트가 기존 참조를 따라 재현한다. 데모에서 그는 자신이 만든 음악 에이전트 프로젝트를 열어 로컬 서버를 시작하라고 했고 에이전트가 package.json의 시작 스크립트를 바로 찾아 서버를 띄우는 것을 보였다. 모델의 분포에 가까운 패턴을 쓰면 에이전트가 알아서 한다는 점이다.

가드레일은 규칙과 훅과 테스트다. 암호화나 인증처럼 한 번의 실수에 큰 비용이 드는 곳을 에이전트가 건드리지 못하게 하는 훅이 예다. 규칙은 가장 오해되는 개념이다. 스택에 맞는 규칙을 모두 설치하는 것이 아니라 에이전트가 어긋나는 것을 볼 때 그 자리에서 만들어야 하고 모델이 규칙을 잘 따라 갈수록 어긋남이 줄어든다. 에이전트가 자기 일을 검증할 수 있어야 한다. 그의 프로젝트에서는 에이전트가 Playwright 종단 테스트를 만들어 재생 버튼이나 노트 추가가 계속 되는지 확인한다. 백엔드는 계약이 분명해 쉽고 UI는 실제로 클릭해 로딩 스피너까지 봐야 한다.

이네이블러는 에이전트를 풀어 주는 것이다. 스킬과 MCP와 외부 맥락, 그리고 환경이다. Cursor에서는 피처 플래그를 추가하는 스킬을 주어 에이전트가 변경을 플래그로 감싸 PR을 병합하고 켜 보라고 알려 오게 한다. 마음에 안 들면 PR을 되돌리고 좋으면 사용자를 넓힌다. 점검표는 실행 가능한가, 맥락에 접근할 수 있는가(Linear, Notion, Datadog, Slack), 검증 가능한가 순이고 사람들이 검증 가능한 시스템에 시간을 훨씬 더 써야 한다고 말한다.

## 관리자의 일

규칙이 갖춰지면 사고방식을 바꿔야 한다. 코드를 훨씬 적게 보고 작업자에서 관리자로, 동기에서 비동기로 간다. 대부분의 일이 백그라운드에서 일어나므로 에이전트가 늘수록 각각을 이해하기 어렵고 결과를 위로 모으는 방법이 필요하다. 조직과 같아서 작은 팀이 커지면 관리자가 필요하고 관리자의 관리자가 필요해진다. 관리자는 범위를 정하고 병렬화한다. 같은 코드베이스의 같은 부분을 건드리는 두 작업은 병합 충돌을 일으키므로 계획해야 하고 하나의 일 단위는 에이전트 하나다. 코드베이스의 부족 지식, 곧 데이터가 어떻게 흐르고 사용자가 무엇을 원하며 어느 부분이 중요한지는 에이전트에게 넘기지 않는다.

비동기로 가면 에이전트를 더 믿어야 하므로 맥락을 계획이나 긴 명세로 앞에 몰아 준다. 쓰다 보면 모델의 강약점을 느끼게 되고 모델이 나아질수록 프롬프트는 짧아져도 의도는 분명해야 한다. 지름길은 없고 에이전트를 많이 띄워 보는 수밖에 없다. 안전장치가 있으면 그렇게 해도 되지만 곧바로 프로덕션에 올리게 하지는 않는다. 환경에 대한 질문에는 격리를 권한다. 작업트리로 같은 기계에서 사본을 나눠도 데이터베이스와 캐시와 사용자 관리를 따로 가지려면 한계가 있어서 그는 각 에이전트가 VM에서 데이터베이스와 내부 도구와 Cursor 앱까지 돌리는 클라우드 에이전트를 선호한다. 비싸고 세팅이 많이 들지만 한 번 갖추면 100개, 1,000개로 늘릴 수 있고 Cursor는 하루 수천 개를 돌릴 것이라고 짐작한다.

관리자의 일은 시스템 전체를 보는 것이다. 사람이 로그를 복사해 코드베이스에 붙이거나 트위터의 사용자 피드백을 다른 곳에 옮기거나 Notion 명세를 마크다운으로 내보내는 곳을 찾아 스킬이나 MCP나 자동화로 없앤다. 에이전트가 어긋나는 것을 잡는 것은 공장을 개선하는 순환이다. 이름 규칙을 어겨 잘못된 스키마를 만들면 규칙이 필요하고 못생긴 UI를 만들면 디자인 시스템을 알려 준다. 5개에서 100개로 확장하려면 코드를 안 보는 쪽으로 가야 하고 산출물과 결과를 관측하고 에이전트가 스스로 검증하게 한다.

## Cursor 내부 자동화 사례

그는 대화 기록을 분석해 반복 업무를 찾게 하는 시연부터 한다. 이어서 쓰는 자동화는 넷이다. 일일 리뷰는 Slack과 GitHub를 보고 하루에 한 일을 요약해 보낸다. 병합된 PR 코멘트 학습은 메인 저장소에 병합된 PR에서 사람이 남긴 코멘트를 읽는다. 사람이 일부러 리뷰해 남긴 코멘트는 신호와 의도가 높아 나중에 에이전트가 배우도록 저장한다. 에이전틱 코드 오너는 코드 오너가 80% 정도 맞지만 나머지 20%에서 병합이 막히거나 다른 시간대의 소유자를 기다리는 문제에서 나왔다. PR의 위험도를 먼저 평가해 변수명 변경 같은 낮은 위험은 바로 승인하고 높은 위험이면 이전에 그 부분을 바꾼 사람을 찾아 피드백을 받는다. 시스템이 안전해지고 원래 바꾼 사람의 맥락도 새로워지는 두 방향의 이득이라는 설명이다. 지속 학습은 이전 대화에서 사용자가 에이전트를 교정한 것(이 컴포넌트를 쓰라, 설명을 자세히 하라)을 규칙과 기억으로 저장하는 플러그인이다. 그는 본인이 게을러 규칙을 만들지 않아서 만들었다.

질의응답에서는 이슈 관리가 나온다. Cursor는 Linear를 쓰고 첫 번째 통합을 통해 티켓마다 클라우드 에이전트를 띄운다. 피처 플래그가 2주간 100%로 켜져 있으면 시스템이 오래된 플래그로 알리고 Linear 이슈를 자동으로 만들며 클라우드 에이전트가 플래그를 제거하는 코드를 만든다. Slack에 올라온 글도 Slack 에이전트나 Cursor 자동화가 중복을 찾고 쉬우면 바로 수정을 시작한다. 모든 티켓마다 클라우드 에이전트를 띄우는 것은 비싸서 모두에게 권하지는 않는다고 덧붙인다. 방송 전날 출시된 Cursor 워커는 클라우드 에이전트와 같은 인프라와 오케스트레이션을 사용자의 아무 기계(맥 미니나 클라우드 VM)에서 돌리게 하며 agent worker start로 시작한다. 컴퓨터 사용은 아직 조기 접근이다.

## 질의응답에서 나온 어려운 질문

코드 품질과 아키텍처에 대한 질문에는 사람도 같은 문제를 겪되 발견에 시간이 걸린다고 답한다. 에이전트는 기존 참조를 따라가는 완성 기계라서 가리킬 참조가 있어야 하고 없다면 일회성 구현을 허용한 뒤 다른 에이전트가 리팩터링하게 하며 추상화가 맞는지 검증하는 시스템을 만든다. 사람의 일은 아키텍처 리뷰와 범위와 시스템 설계 쪽으로 간다. 팀의 규칙이 개인 서식으로 남는 문제는 인간의 문화 문제라고 인정하고 PR 리뷰처럼 도구에도 정렬 절차가 필요하며 공장에 무엇을 넣을지 토론하는 포럼이나 위원회를 권한다. 미션 크리티컬한 시스템에서는 사람이 책임을 지므로 비용과 토큰을 앞에 많이 써서 핵심 부분의 테스트를 사람이 직접 쓰고 에이전트가 자주 돌리며 보안팀의 센티넬 자동화가 특정 불변식을 열 개씩 검사하는 레드팀 같은 접근을 쓴다. 청중 중 한 명이 속도 대신 품질에 AI를 쓴다고 하자 그는 테스트를 신뢰하면 코드를 안 봐도 출력을 신뢰할 수 있어 그 방향으로 가고 있다고 답했다.

PM이 Claude Code로 만든 프로토타입을 개발팀이 Cursor로 옮겨야 하는 인수인계 질문에는, 청중이 데이터베이스와 스택이 달라 마이그레이션이 고통스러웠다고 말하자, 최소한의 의도 전달은 상호작용 가능한 프로토타입이고 백엔드 없이 프런트엔드만 있어도 되며 엔지니어는 그것을 다시 쓰면 된다고 답한다. 엔지니어가 제품 조직에 원하는 것을 분명히 하고 완성된 SaaS를 만들어 오는 것이 가장 도움이 되지는 않는다고도 한다. 장애와 가동 중단 위험에는 시스템 핵심 영역을 정하고 모든 줄을 사람이 쓰거나 한두 사람이 항상 리뷰하며 관측과 테스트를 갖추라고 답한다. 하루 일과에 대해서는 네 개 영역에서 동시에 일하고 다섯에서 열 개의 클라우드 에이전트를 항상 돌리며 동기로 계획하고 비동기로 실행한다고 말한다. 팀의 미래 구조에 대해서는 코드를 덜 쓰고 덜 보며 에이전트를 더 띄우는 쪽이고 방향을 정하고 고객과 이야기하는 사람과 조립 라인의 발판을 만드는 사람이 중요해질 것이라고 하되 규모는 모르겠다고 한다. Cursor에는 PM과 디자이너와 엔지니어와 데이터 팀이 함께 일하고 디자이너도 코드를 프로덕션에 올린다.

## 대조해서 확인한 점

**자율성 단계.** Dan Shapiro의 글 「The Five Levels: from Spicy Autocomplete to the Dark Factory」(2026-01-23)는 자동차 자율주행 단계에 빗대 레벨 0에서 5까지 쓴다. 레벨 0은 사람이 모든 문자를 승인하는 수동, 레벨 1은 개별 작업을 AI 인턴에 넘김, 레벨 2는 AI 보조 코딩이 대부분의 AI 도입 기업이 있는 곳이다. 발표자가 말한 여섯 단계(0~5)와 맞고 마지막이 어두운 공장이다.

**Cursor 3.** Cursor 블로그와 변경 기록에 2026년 4월 2일 Cursor 3이 에이전트 창과 통합 작업 공간으로 나왔다. 발표자의 "몇 주 전에 출시한 완전한 재작성"과 시점이 맞는다.

**클라우드 에이전트.** Cursor 블로그의 자체 호스팅 클라우드 에이전트 글은 클라우드 에이전트가 터미널과 브라우저와 데스크톱을 가진 격리 VM에서 돌고 저장소를 복제해 환경을 세팅하고 코드를 쓰고 테스트하고 검토용으로 올린다고 쓴다. 다른 글(자체 호스팅 머신)은 클라우드 에이전트가 내부에서 병합하는 PR의 60% 넘게 만든다고 쓴다. 이는 공급사 자체 수치이며 발표의 하루 수천 에이전트라는 추측은 확인하지 못했다. 방송 전날 출시했다는 Cursor 워커의 정확한 날짜는 확인하지 못했다.

**자동화.** Cursor Automations 블로그는 스케줄이나 Slack 메시지, Linear 이슈, 병합된 PR, PagerDuty 사건 같은 이벤트로 도는 상시 에이전트를 소개하며 에이전트가 과거 실행에서 배우는 기억 도구가 있다고 쓴다. 발표의 일일 리뷰와 PR 코멘트 학습이 이 기능 위에 선다.

**에이전틱 코드 오너.** Cursor의 에이전트 SDK 템플릿 문서는 모든 PR의 위험을 등급화하고 소유자를 리뷰어로 요청하며 정책이 허용하는 것을 승인한다고 쓴다. 정책 파일이 없으면 가장 낮은 단계(very-low)와 낮은 단계를 승인하고 중간 이상은 코멘트와 함께 보류하며 정책은 PR의 기반 브랜치에서 읽어 PR이 스스로를 면제할 수 없다. 발표의 낮은 위험 승인 설명과 맞고 정책을 기반 브랜치에서 읽는다는 보안 설계는 발표에 없는 보강이다.

**지속 학습.** cursor/plugins 저장소에 continual-learning 플러그인이 있다. 발표의 대화 기록에서 규칙과 기억을 뽑는 설명과 같은 종류다. 이 노트는 플러그인 코드를 열지 않았다.

확인하지 못한 것은 BugBot의 외관 기능, 센티넬 자동화의 세부, 데모의 비용(발표자 추정으로 한 턴에 1달러), Lovable의 에이전트 불평 도구 일화, Cursor가 지금 몇 개의 에이전트를 돌리는지다. 이 워크숍 이후 6월에 SpaceX가 Cursor 모회사 Anysphere를 인수했고 프로젝트 같은 코디네이터 층이 나왔다는 점은 이 블로그의 다른 노트가 다룬다.

## 읽을 때 유의할 점

첫째, 발표자는 이 제품을 만드는 회사의 직원이고 사례 대부분이 자사 제품 사용이다. 효과는 정성적이고 수치가 드물다. 둘째, 영상은 4월의 스냅숏이다. 이후 제품과 조직이 크게 바뀌었으므로 기능 이름과 한계(컴퓨터 사용이 조기 접근 등)를 현재로 읽으면 틀린다. 셋째, 에이전트마다 VM을 주는 방식은 비용과 세팅 부담이 크다는 점을 발표자도 인정한다. 넷째, 낮은 위험 PR의 자동 승인은 위험 분류의 정확도에 달려 있다. 다섯째, 규칙과 공장을 팀이 어떻게 합의할지는 사람의 문제라고 인정하고 답을 주지 않는다.

가져갈 질문은 선명하다. 지금 팀이 자율성 단계의 어디에 있고 한 단계 올라가는 데 무엇이 막는가, 사람이 복사해 붙이는 곳은 어디인가, 에이전트가 어긋날 때 그것을 규칙이나 검사로 올리는 순환이 있는가, 낮은 위험 PR을 승인하는 정책을 PR이 스스로 면제할 수 없게 설계했는가.
