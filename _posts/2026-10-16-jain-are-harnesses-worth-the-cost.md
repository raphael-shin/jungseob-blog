## TL;DR

- 같은 서비스를 최전선 모델 GPT-6 Sol과 비용 최적화 모델 GPT-6 Luna에게 10번씩 만들게 하고, 행동 하네스(명세와 예시를 주는 가이드, 결과를 되돌려 주는 센서)의 유무를 비교한 실험이다. 외부 인수 테스트 178개를 모두 통과해야 합격으로 쳤다.
- Sol은 하네스 없이도 10번 모두 합격했고, 하네스를 붙이면 토큰이 약 10.5배, 시간이 약 3배, 비용이 약 7배 늘었다. Luna는 하네스 없이 3번, 있으면 10번 합격했다.
- 하네스를 붙인 Luna의 한 번당 비용은 약 0.273달러로, 하네스 없는 Sol의 0.406달러보다 약 33% 쌌다. 필자는 하네스를 모델의 빠진 능력을 채우는 것이 아니라 요구사항이 구현 중에 흐려지는 "주의 공백"을 실행 가능한 피드백으로 되돌리는 장치로 해석한다.
- 필자의 결론은 모델 능력이 바뀌는 것은 독립 검증이 필요한지가 아니라 센서를 언제 돌리느냐라는 조건부 가설이다. 저가 모델은 개발 내내, 최전선 모델은 최종 관문에서 한 번 돌리라는 것이다.
- 표본은 한 가지 신규 Java 서비스에서 모델당 10회뿐이고, 하네스를 만든 도구가 필자 회사의 제품이다. 계약과 예시를 쓰는 사람의 노력은 비용에 들어 있지 않다.

## 글에 대하여

Specmatic과 Xnsio, ConfEngine를 세운 Naresh Jain이 쓴 글로 2026년 10월 13일에 Martin Fowler의 사이트에 실렸다. 시리즈는 Exploring Gen AI다. 글 말미에서 Fowler의 격려와 검토에 감사하고 하네스를 만드는 데 생성형 AI를 썼다고 밝힌다. 이 노트는 본문 전체를 읽었다. 표와 그림 가운데 표의 수치는 직접 다시 계산했고 그림 6장은 읽지 못했다.

## 실험 설계

과제는 상품 탐색용 BFF(backend-for-frontend)를 만드는 것이다. 소비자용 HTTP API를 열고 들어오는 요청과 하류 응답을 검증하고 Order API를 호출하며 가용성 검색에 성공하면 첫 번째 상품만 Kafka에 발행해야 한다. 숨은 규칙도 많다. 상품 생성이 시간 초과되면 202로 응답하고 폴링 링크를 헤더에 주어야 하며 일시적 검색 실패는 복구 간격이 있는 429, 의존성 장애와 발행 실패는 503, 필터를 어기는 하류 응답은 502로 처리한다. 필자는 단순 CRUD가 아니라 HTTP 의미, 비동기 이벤트, 스키마 경계, 장애 허용 정책을 한꺼번에 맞춰야 하는 과제라고 설명하고 요구사항서(brief)를 이례적으로 자세히 써서 에이전트에게 유리한 출발점이었다고 인정한다.

하네스는 Birgitta Böckeler의 용어를 빌려 가이드와 센서로 나뉜다. 가이드는 OpenAPI와 AsyncAPI 명세, 요청과 응답 예시(시간 초과, 깨진 페이로드, 필터 위반, 재시도, Kafka 확인), 의존성 시뮬레이션과 실패 진단을 안내하는 API 개발 스킬이다. 센서는 계약 준수 검사, HTTP 응답 값 검사, 하류 목 호출과 Kafka 발행 같은 관찰 가능한 부수효과 검증이며 테스트 결과와 커버리지 보고서가 에이전트에게 돌아간다. 필자는 가이드와 센서가 서로 모순되지 않게 예시가 명세를 지키는지 먼저 검사하고 에이전트가 기대값을 약화하지 못하게 했다. 구현 에이전트가 요구사항을 해석해 코드와 테스트를 모두 쓰면 같은 오독이 양쪽에 들어가기 때문이다. 이 피드백은 편집마다 자동으로 도는 것이 아니라 에이전트가 프로젝트의 테스트 명령으로 호출해야 도는 구조였다. 평가는 개발 루프와 분리해 격리 컨테이너에서 178개 기능 점검으로 했고 하네스는 정답지를 보지 못했다. 하네스는 Specmatic으로 구현했다.

## 결과

Sol(낮은 추론 강도)은 하네스 유무와 상관없이 10번 모두 178개를 통과했다. 하네스가 있을 때 평균 11,331,970 토큰, 19분 53초, 약 2.679달러이고 없을 때 1,076,371 토큰, 6분 51초, 약 0.406달러였다. 필자는 하네스가 도움이 되고 토큰도 아낄 것이라 기대했는데 결과가 이를 정면으로 뒤집었다고 쓴다. 이 노트가 계산해 보니 토큰은 10.5배, 시간은 2.9배, 비용은 6.6배이며 글의 "약 10.5배, 거의 3배, 약 7배"와 맞는다. Claude Sonnet 4.6, Opus 4.6, Gemini 3.8 Flash로 해 본 탐색 실행에서도 하네스 없이 한 번에 과제를 끝냈다고 한다.

Luna는 달랐다. 같은 설정에서 하네스 없이 3번, 하네스가 있으면 10번 합격했다. 하네스가 있을 때 평균 22,933,648 토큰, 35분, 약 0.273달러이고 없을 때 5,860,736 토큰, 15분 56초, 약 0.086달러다. 하네스가 더한 비용은 토큰 17,072,912개, 19분 4초, 약 0.187달러이고 모두 표와 맞게 계산된다. 하네스 있는 Luna(0.273달러)는 하네스 없는 Sol(0.406달러)보다 32.8% 쌌고 합격률은 둘 다 10 대 10이었다. 필자가 강조하듯 하네스가 Luna에게 없던 능력을 준 것은 아니고 3-in-10을 10-for-10으로 바꾼 것이다.

## 실패는 어디서 났나

하네스 없이 실패한 Luna의 Java 애플리케이션은 문법 오류도, 요구사항 오해도 아니었다. 모두 178개 중 최소 144개를 통과했고 전체 평균 통과율은 94.8%였다. 실패는 프로토콜 경계와 복원 경로, 통합 이음새에 몰렸다. 지연 생성이 시간 초과 경계에서 깨져, 202와 폴링 링크 대신 4개가 503, 2개가 400, 1개가 429를 돌려주었다. 7번의 실행에서는 이 때문에 폴링 URL이 없어 후속 검사가 연쇄 실패했다. Kafka 메시지는 도착했는데 Spring의 직렬화기가 예상치 못한 `__TypeId__` 헤더를 붙이거나(2건), 선택 필드를 `null`로 내보내(1건) 계약 위반이 되었다. 지원하지 않는 미디어 타입에 관례대로 415를 돌려주었지만 요구사항서는 400을 요구했다. 환경 변수 이름이 `ORDER_API_API_KEY`와 `ORDER_API_KEY`로 어긋나 일반 상품 생성이 503이 된 경우도 있었다. 필자는 시간 초과 인식이 좁은 예외 유형 매칭 때문일 가능성이 있다고 하되, 산출물이 실제 예외를 기록하지 않아 확정은 아니라고 쓴다.

## 실행 가능한 주의

필자는 이 현상을 "실행 가능한 주의(executable attention)"로 개념화한다. 요구사항이 요구사항서에 분명히 있어도 구현 중에 영향력을 잃는 것이 주의 공백이고 센서가 붉게 바뀔 때 빠뜨린 세부가 다시 눈에 들어온다는 것이다. 라이브러리 선택, 보일러플레이트, 의존성 주입, 비동기 배선을 커지는 맥락에서 한꺼번에 다루는 부담이 한 원인일 수 있다고 추정하지만 이 실험이 원인을 확인한 것은 아니라고 명시한다. 같은 센서가 개발 중에는 피드백, 완료 시점에는 독립적인 수용 기준이라는 이중 역할을 한다는 점도 짚는다. 검토자 Shunjiro Yatsuzuka가 제안한 구분이다.

## 실무 시사점과 한계

필자의 조건부 결론은 이렇다. 모델 능력이 바뀌는 것은 독립 검증이 필요한지가 아니라 센서를 언제, 얼마나 자주 돌리느냐다. 비용 최적화 모델이 들쭉날쭉하면 개발 내내 행동 하네스를 돌려 일관성을 확보하고 최전선 모델은 한 번에 통과하더라도 독립 수용 검사를 최종 관문으로 한 번 돌리라는 것이다. 센서는 사람이 명세와 예시로 부호화한 기대만 강제하므로 그것을 구현과 함께 검토하고 유지해야 한다. 다음 단계로 "최종 관문만" 조건과 요구사항서의 질, 레거시 코드 수정, 다른 언어, 오픈 웨이트 로컬 실행을 시험할 계획이라고 한다.

필자가 스스로 밝힌 한계도 분명하다. 모델당 10번의 짝지은 실행, 신규 Java 서비스 하나 낮은 추론 강도뿐이다. 하네스를 구성한 가이드와 센서를 함께 더했기 때문에 각각의 기여를 분리하지 못했다. 비용 수치는 토큰 사용량과 모델 가격으로 추정한 API 환산액이며 실제 청구액이 아니다. 계약, 예시, 단언, 하네스를 만들고 검토하고 유지하는 사전 노력과, 실패한 결과를 찾아 진단하고 고치는 노력도 빠져 있다.

## 읽을 때 유의할 점

첫째, 하네스를 구현한 도구가 필자 회사의 제품이다. 필자는 동등한 계약 테스트·서비스 가상화 도구로 같은 구현이 가능하다고 쓰지만 실험을 설계하고 해석한 사람이 도구 공급자라는 이해관계는 남는다. 둘째, 이 블로그의 [에이전트 실패 15가지 노트](https://raphael-shin.github.io/jungseob-blog/posts/adrianstudio-15-ways-coding-agents-fail/)와 [teo의 AI Native FE 회고](https://raphael-shin.github.io/jungseob-blog/posts/teo-ai-native-fe-150-days/)에서도 하네스가 금지 규칙형이면 실패했다는 경험이 나온다. 이 글의 하네스는 금지 규칙이 아니라 계약 기반 피드백이라는 점이 다르며 같은 용어가 서로 다른 것을 가리킨다. 셋째, 합격이 외부 178개 테스트 통과로 정의되어 있어 코드 품질이나 유지보수성은 평가하지 않았다. 넷째, 요구사항서가 이례적으로 상세했다는 점은 일반 업무의 모호한 요청과 거리가 있다.

그럼에도 가져갈 점검 질문은 선명하다. 모델이 일관되게 통과하는 일에도 독립적인 최종 검증을 두었는가, 저가 모델의 들쭉날쭉함을 더 비싼 모델 대신 피드백 루프로 메울 수 있는가, 센서의 기대값이 구현 에이전트의 해석과 독립된 출처에서 나왔는가, 하네스를 만드는 사람의 시간까지 넣으면 비용 비교가 어떻게 달라지는가.
