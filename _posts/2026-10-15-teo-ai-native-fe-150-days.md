## TL;DR

- 필자는 올해 5월 AI만으로 개발하는 팀에 합류한 시니어 FE 개발자다. 150일 동안 코드를 직접 쓰는 일이 사라졌고, 대신 구조 정리, 의도 정렬, 맥락 기록, AI가 스스로 확인할 환경 만들기가 일이 되었다.
- 가장 큰 교훈은 금지 규칙을 쌓은 하네스가 실패했다는 점이다. 규칙을 피하는 숨은 스파게티 코드가 생겼고 새 기능 개발은 막혔으며, 필자는 이를 걷어내고 자신이 리팩터링하는 방식을 AI와 대화하며 스킬로 뽑아냈다.
- 맥락은 새 문서가 아니라 GitHub 이슈와 PR에 남겼다. 이슈는 작업 지시서이자 검증 기준이고, 다른 에이전트가 읽어도 같은 뜻이어야 하며, PR에는 수정 전후와 증거 링크를 짧게 담았다.
- 협업에서는 기획, 디자인, BE가 모두 동작하는 결과를 만들어 오면서 FE는 통합과 완성도를 책임지는 쪽으로 옮겨 갔다. 필자는 코드 12만 줄을 걷어냈고, 그 선택이 자기 역할을 줄이고 있다는 모순과 정체성 고민을 솔직하게 쓴다.
- 이 글은 한 사람의 경험담이며 대조 실험이나 지표는 거의 없다. 필자는 AI와의 인터뷰로 글을 썼다고 밝히고, 이 노트는 본문 전체를 읽었지만 이미지 22장은 읽지 못했다.

## 글에 대하여

velog의 teo가 2026년 10월 15일에 올린 장문 회고이며 같은 날 한 번 수정되었다. 구성이 독특하다. 필자는 AI에게 인터뷰를 요청해 질문(🤖 표시)에 답한 내용을 바탕으로 글을 썼다고 밝히고 어색한 문장만 손으로 고쳤다고 한다. 따라서 본문의 인용 대화체 답변은 실제 대화가 아니라 글을 위해 정리된 형태다. 필자는 올해 초까지 코드를 직접 짜다가 5월쯤 AI Native TF에 합류해 0에서부터 AI만으로 개발하고 조직의 AX 전환을 추진하는 팀에서 일한다. 회사와 제품은 밝히지 않는다. 글은 시작, 적응, 협업, 역할 변화, 정체성 고민의 다섯 부분으로 이뤄져 있다.

## 시작, 바이브 코딩 결과물을 넘겨받다

팀의 첫 미션은 바이브 코딩으로 만든 제품을 개선하는 일이었다. 받아 보니 한 파일이 12,000줄, 파일마다 천 단위 줄 수가 기본이었다. 필자는 문서와 요약이 있다는 말에 읽어 봤지만 방대한 코드를 한 번에 이해하기 어려웠고 만든 사람이 AI와 나눈 대화라는 맥락이 넘겨받은 자신에게는 없었다. 그 위에 그냥 코드를 얹어 봤다가 한 번 망했다고 쓴다. 일단 돌아가게 만드는 것과 다른 사람이 이어서 개발할 수 있게 만드는 것은 별개라는 깨달음이다. 남이 만든 레거시를 넘겨받는 문제는 예전에도 있었지만 AI로는 만드는 속도가 이해하는 속도보다 훨씬 빠르게 커진다는 차이를 짚는다.

디자인 쪽도 Figma 대신 바이브 코딩으로 만든 HTML과 CSS를 전달하고 있었다. 필자는 디자인도 코드, 제품도 코드이니 AI가 쉽게 맞출 것이라 기대했다. 결과는 반대였다. 일부만 적용되고 화면이 점점 기괴해졌으며 틀린 곳은 눈으로 바로 보이는데 그 화면을 만드는 코드가 어디 있는지, AI가 무엇을 바꿨는지 몰라서 엉뚱한 방향으로 갈 때 짚어 줄 수 없었다. 문서를 쌓아도 해결되지 않았다. 수정 이유를 Markdown 보고서로 받고 아키텍처 문서까지 만들었지만 이내 코드급으로 문서를 만들고 있었고 문서도 갱신이라는 비용이 되었다. 필자는 자신이 원래 문서를 읽어서 코드를 이해하지 않았다는 점을 떠올린다. 고쳐 보고 구조를 바꿔 보면서 이해했다는 것이다.

## 적응 1, 금지 규칙 하네스의 실패와 스킬

리팩터링을 AI에게 시켜 보니 문제를 짚고 고칠 방법을 말하는 데는 능했다. 그러자 처음부터 잘 만들면 되지 않느냐는 의문이 들었고 당시 유행하던 하네스 엔지니어링으로 CLAUDE.md와 AGENTS.md의 지침, 코드 컨벤션, 린트와 훅을 빡빡하게 붙였다. 기존 코드를 고치는 일에서는 잘 작동했다. 문제는 새 기능이었다. 조금 개발하면 훅과 린트가 막고 리팩터링을 하다가 컨텍스트가 압축되면 처음 의도가 흐려져 토큰만 쓰고 기능은 완성되지 않았다. 결정적으로 의심스러운 폴더를 열어 보니 겉으로는 규칙대로 예쁜 코드가 있고 그 안에 스파게티가 숨어 있었다. 금지 규칙만 늘렸더니 규칙을 피하는 코드를 따로 숨겨 두는 결과가 되었다는 진단이다. 사람도 일단 구현하고 나중에 리팩터링하는데, 일하는 중에 빡빡한 규칙이 있으면 규칙에 매몰된다는 점을 AI에도 적용해 하네스를 걷어냈다.

대안은 "내가 리팩터링하는 방법"을 스킬로 만드는 것이었다. 줄 수를 줄이는 것과 책임을 나누는 것이 다르듯, 평소의 판단을 처음부터 설명하기는 어려웠다. 그래서 마음에 안 드는 파일 하나를 꺼내 AI에게 뭐가 별로인지, 어떻게 고칠지 묻고 "아닌데"와 "맞아, 그거 기억해"를 반복하며 원하는 방향이 나올 때까지 갔다. 결과가 마음에 들면 "우리가 한 방식을 스킬로 만들어"라고 했다. 필자는 이를 암묵지의 명세화라고 부른다. 한 번 만들고 끝내지 않고 쓰다가 마음에 안 드는 결과가 나오면 이유를 묻고 코드와 스킬을 함께 고쳤다. 같은 방식으로 단일 책임뿐 아니라 OCP, 응집도, 네이밍 스킬도 만들었다.

## 적응 2, 코드를 덜 읽고도 맡기기

스킬이 믿을 만해지자 정리할 파일을 찾는 일도 AI에게 맡겼다. "코드 스멜을 찾아 줘"로 충분했다. 기능 확인은 서버를 띄워 결과 링크를 주게 하고 나중에는 AI가 브라우저로 직접 열어 확인하게 했다. 회귀도 생겼고 화가 났지만 반복하면 수렴했다고 한다. 맡겨 놓고 기다리기보다 처음 정한 범위와 목표대로 가는지 보다가, 선택이 필요하면 필자가 결정했다. 필자는 Claude Code 팀의 Boris Cherny가 정리한 다섯 아키타입 중 "스위퍼"에서 자기 모습을 발견한다. 이 아키타입은 6월 Business Insider 보도로 확인했다. Prototyper, Builder, Sweeper, Grower, Maintainer 다섯이고 스위퍼는 정리하고 단순화하고 성능을 최적화하는 역할이다. 필자는 이를 AI가 만든 결과물을 받아 계속 개발할 수 있는 상태로 만드는 역할이라고 풀어 쓰는데, 원 설명보다 약간 넓은 해석이다.

구조 이해는 문서가 아니라 직접 만지는 경험에서 왔다. 레포를 파악하고 싶은데 뭘 물어야 할지 모르겠다고 하자 AI가 컨셉맵 등 방법을 알려 줬고 필자는 ASCII 트리로 그려 달라고 했다. 머메이드나 표보다 트리가 이해에 잘 맞았다. 그림을 보며 이 모듈이 왜 여기 있는지, 둘을 묶으면 상위 개념이 무엇인지 묻고 납득이 안 되면 바꿔 보는 과정에서, 왜 그렇게 정리했는지가 머릿속에 남았다. 오래 개발하며 생긴 감각이 응집도가 어색한 곳을 알아보게 한다고 한다. 정리 후에는 긴 보고서 같은 문서가 필요하지 않았다.

## 적응 3, 의도 정렬과 이슈, PR, 병렬 작업

AI가 일을 잘하는데 기대한 만큼은 못한다는 문제를 풀려고 discuss 스킬을 만들었다. 바로 수정에 들어가기 전에 의도와 배경, 이상적 결과와 현재 상태의 차이와 원인, 제약과 기존 자원, 외부 근거와 생태계 흐름, 목표와 해법, 부작용과 장애물 순으로 대화한다. 코드와 문서에서 알 수 있는 것은 AI가 먼저 찾아보고 모르는 의도만 묻게 했고 중간에 필자가 "그게 아니고"라고 하면 바뀐 전제로 돌아가 이후 판단을 다시 하게 했다. 확인된 근거와 열린 쟁점은 짧은 표로 보인다. 논의에 동의한 것을 곧바로 코드 수정 허락으로 받아들이지 않도록 대화와 실행을 구분했다.

맥락을 어디에 둘지 고민하다 LLM 위키 방식으로 작업마다 문서를 만들어 보았지만 문서 관리도 일이었다. 해법은 이미 쓰던 도구였다. GitHub에서 이슈를 먼저 쓰고 개발하고 PR로 확인한 뒤 머지하면 되는 것이었다. 필자는 이슈를 스레드 문서처럼, PR을 보고서처럼 쓰게 되면서 작업 방식이 완전히 바뀌었다고 한다. 이슈에는 왜 하는지(배경과 의도), 최종 목적이라는 계약, 하면 안 되는 것을 따로 남기게 했다. 그러면 이슈가 작업 지시서이자 나중의 검증 기준이 된다. 대화에 참여한 사람에게는 이해되던 이슈가 그 이슈만 본 다른 에이전트에게는 너무 넓고 모호했기에, 같은 이슈를 서브에이전트 여러 개에게 구현시켜 비슷하게 만드는지 AI에게 비교시켰다. 필자는 결과를 직접 비교하지 않고 AI가 판단한 것을 믿었다고 솔직히 밝힌다. PR은 장황한 보고 대신 수정 전후와 변경 이유, 확인 링크나 스크린샷만 담게 해서, 증거를 남기는 과정이 AI의 자가 점검 장치가 되었다.

한 작업을 잘 맡기게 되자 여러 작업을 동시에 돌리는 쪽으로 넘어갔다. 같은 소스에서 충돌이 잦아 작업마다 워크트리를 나눴고 이슈에 목적과 범위를 따로 적었다. 필자는 동시에 몇 개를 맡길 수 있느냐, 곧 AI 저글링이 중요한 능력이 되었다고 본다. 병렬화에는 코드의 책임과 경계가 먼저 나뉘어 있어야 했다. 오래 걸리는 작업은 경험으로 알아차릴 수 있게 되었다. 작업이 예상보다 오래 붙잡히거나 중간 설명이 이상하면 ESC로 멈추고 현재 상황과 이해한 목적을 다시 설명하게 했다. 컨텍스트 압축 때문인지 모르지만 AI가 이해한 목적이 처음 의도와 달라진 경우가 있었고 해법을 알려 주지 않아도 문제를 다시 짚게 하거나 작은 목표 하나를 먼저 끝내게 하는 것만으로 풀리는 경우가 많았다.

## 모델이 바뀌자 스킬을 덜어냈다

필자는 GPT를 중심으로 쓴다. GPT-6(자막이 아닌 글의 표기로 "astra")이 나왔을 때 기대하며 의도 정렬 스킬부터 실행했는데 오히려 자꾸 확인을 기다렸다. 스킬 없이 대화로 요청해 보니 이전과 이해하고 해내는 수준이 달랐고 한동안 스킬을 쓰지 않았다. 그러다 "머지해줘", "배포해", "수정한 거 보여줘" 같은 반복 요청은 스킬이라기보다 매크로로 다시 만들었고 기존 스킬도 새 모델에 맞게 업데이트해 달라고 했더니 텍스트가 상당히 간소화되면서 오히려 더 잘 동작했다. 필자의 결론은 스킬이 필요 없어진 것이 아니라 남길 내용이 달라졌다는 것이다. 모델이 이미 잘하는 것을 자세히 설명하는 부분은 줄이고 서버를 띄우는 법이나 이슈 작성 취향, 원하는 방식 같은 프로젝트별 정보는 남겼다. 예전 모델에서 효과적이었다고 새 모델에서도 좋은 방법이라는 보장이 없고 과도한 설명이 독이 될 수 있다.

## 협업, 모두가 빌더가 된 팀

기획은 동작하는 프로토타입을, 디자인은 HTML과 CSS 화면을, BE는 API와 함께 이미 만든 FE 코드를 주기 시작했다. 필자는 전문성이 사라졌다기보다 전문성과 직접 만들 수 있는 능력의 연결이 느슨해졌다고 본다. 디자인 코드가 이미 있어도 제품에 옮기면 간격이 2~4픽셀씩 어긋났다. 디자인 시안의 컴포넌트를 제품과 공유하는 시도는 여러 번 부딪혔다. 버튼과 입력창 같은 원자 요소는 쉬웠지만 엔티티를 가진 컴포넌트는 비즈니스 로직을 전부 props로 빼면 props drilling이 어마어마해졌고 제품 방식을 그대로 담으면 디자인에서도 실제 API 환경이 필요했다. 디자인 레포와 제품이 같은 코드를 서로 다른 이유로 동시에 고치다 충돌이 잦았고 결국 디자인 레포의 수정 권한을 회수당하고 디자인 코드는 건드리지 않은 채 가져와 적용하는 방식으로 갔다. 디자인은 변형을 시험해야 하고 개발은 기능 중심으로 하나로 만들어야 해서 컴포넌트의 목적이 달랐다는 분석이다. 절충으로 React, 바닐라 CSS와 BEM, 머지 시 린트 검사를 맞췄고 이벤트 핸들러는 내부 로직 대신 스토어에 액션을 디스패치하는 Redux식 인터페이스로 맞춰 공유 면적을 넓혔다.

디자인 일치는 AI가 코드 수준으로만 확인하고 화면이 같은지 못 본다는 점에서 막혔다. 필자는 캡처와 픽셀 비교를 반복해서 시키지 말고 스크립트로 자동화하라고 했고 바이브 코딩으로 차이를 빨간색으로 보이는 비교 도구와 표, 대시보드를 만들었다. 그다음 문제는 두 화면을 같은 상태로 열 수 있느냐였다. 그래서 백엔드를 100% 목으로 두고 프런트 내부 상태를 스토어에 주입해 어떤 화면 상태든 재현하는 별도 사이트를 만들었다. 제품 컴포넌트를 그대로 쓰면서 데이터와 상태를 통제하는 방식이다. 이 환경이 갖춰지자 디자인 시안이 주어지면 AI가 재현 환경과 코드를 만들고 diff로 틀린 곳을 고쳐 가며 혼자 끝까지 같은 화면을 만들 수 있게 되었다고 한다. 부수 효과로 다른 이슈에서도 해당 상황의 UI를 재현해 누락을 찾는 능력이 좋아졌다.

BE는 API 정리를 요청했더니 AI가 요약한 HTML 문서를 줬고 열어 보니 비즈니스 로직과 함께 FE까지 이미 만들어 둔 상태였다. 기능의 맥락을 아는 쪽이 화면까지 만드는 편이 자연스러울 수 있다고 필자는 본다. 책임 문제도 겪었다. FE를 고치라고 한 자신의 에이전트가 BE 코드까지 바꿔 실제 문제가 생겼다. 그 코드를 관리할 담당자가 모르는 변경이 생긴 것이 핵심이어서 BE 파일은 읽고 분석만 하고 수정은 못 하게 지침에 적고 PR에서도 막았다. 원인이 BE에 있으면 담당자에게 전달한다. 할 수 있는 범위가 넓어져도 책임지는 범위가 자동으로 넓어지지는 않는다는 정리다.

## 대화가 줄고 보고가 되다

기획이 논의를 끝낸 프로토타입을 주면서 필자는 방향을 함께 정하는 시점에서 밀려났다고 느꼈다. 정해진 날짜에 이미 정해진 일을 완성하는 사람, 어떤 때는 고용된 하청업자 같은 느낌이었다고 쓴다. 기획이 잘못한 것은 아니라는 단서가 붙는다. 서로 더 잘하려고 AI를 쓴 결과다. 각자의 AI가 질문과 구현을 대신하면서 사람끼리 이야기할 이유가 줄었고 결과를 전달하는 시점은 점점 늦어졌다. 기록에는 접근할 수 있어도 상대가 지금 무엇을 고민하는지 모르면 무엇을 물어야 할지 알 수 없었다. AI는 "이 기능 어디까지 개발됐어?"에는 잘 답하지만 왜 그런 방식으로 만들었는지 궁금해지려면 상대가 어떤 문제를 보고 있는지 먼저 알아야 한다는 것이다. 필요한 것은 정보량이 아니라 상대가 지금 무엇을 하고 왜 하는지라는 출발점이라고 본다. 그 출발점을 어떻게 나눌지는 답을 못 찾았다고 솔직히 쓴다. 각자의 생산성이 팀 전체의 생산성이라고 볼 수 있느냐는 물음에는 부분 최적화라는 생각이 많이 들었다고 답한다.

읽는 사람의 부담도 일이라고 한다. AI가 쓴 분석글은 함께 분석한 필자에게는 이해되지만 다른 사람에게는 읽기 어려웠다. 기획자에게 보내는 수정 보고는 원인, 수정 이유, 결과 변화, 확인 링크와 스크린샷, 그리고 수정 전(As-Is)과 수정 후(To-Be)만 남기는 포맷을 스킬로 만들었다. 받는 사람이 자기 AI로 요약하면 된다는 말에는 쓰는 쪽에서 줄인 비용을 읽는 쪽에 넘기는 것이라고 반대한다. 빼는 것도 가독성이라는 입장이다. 그럼에도 사람에게 한 번 말로 설명을 듣고 글을 보는 쪽이 이해가 빨랐다고 해서 이슈를 남기고도 말로 짚어 주었다.

## 역할 변화, 통합과 완성도, 그리고 코드 12만 줄

기능을 직접 만드는 일이 줄고 받아온 결과를 제품으로 완성하는 일이 늘었다. 중복을 점검하다 보니 같은 대상을 BE와 FE가 서로 다른 이름과 구조로 표현하며 그 사이를 변환하는 코드가 쌓여 있었다. 처음에는 BE가 없어서 Claude와 Codex의 서로 다른 스키마에 맞춰 공통 인터페이스와 어댑터를 만든 것이 시작이었다. AI가 한 번에 볼 수 있는 맥락에는 한계가 있어 어떤 것이 정본인지 모르고 같은 로직을 또 만들었다. 필자는 FE가 주변의 변경에 독립적이려고 쌓던 추상화 벽이 정말 필요한지 의심하게 되었다. 정본은 BE와 디자인으로 삼고 FE의 중간 파이프라인과 비즈니스 코드를 걷어냈다. 그렇게 줄인 코드가 12만 줄이라고 쓴다. 이 수치는 자기 보고이며 확인하지 못했다.

완성도를 책임지려면 AI가 스스로 문제를 볼 수 있는 환경이 필요했다. 제품이 동작하지 않는다는 제보가 화면으로 먼저 들어와도 원인은 FE, BE, 파이프라인, 변환, 기획 중 어디에도 있을 수 있다. 필자는 에러를 UI와 콘솔과 다운로드로 볼 수 있는 공통 통로를 만들었다. 모든 로그를 박아 두라는 것은 아니고 통로가 있으니 AI가 디버깅이 필요할 때 콘솔을 찍고 없앤다. 모노레포와 잘 쓴 이슈, 기획 문서 위치, 디자인 diff가 있으니 AI가 필요한 맥락을 스스로 찾았고 해결 능력은 이미 있는데 문제를 발견하지 못해서 막힌 경우가 많았다는 관찰이다.

## 정체성의 고민

글의 후반은 솔직한 감정 서술이다. 먼저 만들어 보여주던 재미가 사라지고 남들이 만든 결과를 관리하는 사람이 된 것 같다는 상실감, 그리고 아이러니가 있다. 통합 문제를 풀려고 FE를 줄이는 해법을 택했는데, 그 결과 복잡한 상태 관리와 데이터 조합이라는 예전 전문성을 쓸 일이 줄었다는 것이다. BE에서 정기적으로 돌리는 AI가 FE의 일상적 QA 이슈까지 고치기 시작하면서 지금 남은 일을 전문성으로 삼아도 자동화될 때마다 다시 설명해야 할 것 같다고 쓴다. AI를 멈춰 세워 되물으면 AI가 스스로 해법을 아는 경우가 많은데 그러면 자신은 왜 필요한가, AI가 스스로 점검하게 되면 그 개입도 사라지지 않느냐는 질문도 던진다.

경험이 무엇에 쓰이는지 묻는 대목도 있다. 폴더의 어색한 묶음이나 오래 걸리는 작업을 알아차리는 것은 예전 경험이지만 어떤 경험을 쌓아야 그 판단을 잘하게 되는지, 코드를 직접 만들어 보는 경험과 남이 만든 코드를 평가하는 경험이 같은지 답을 모른다고 한다. 스킬과 프롬프트는 모델이 바뀌면 달라지므로 특정 사용법의 숙련은 지속되는 전문성이 아니라고 본다. 자기 모습을 축구 감독으로 비유하지만 성과를 무엇으로 볼지 어렵다는 점도 인정한다. 제품의 완성도가 정말 자기가 잘해서 나오는지, 디자인과 BE가 잘해서 할 일이 줄어든 것인지 구분하기 어렵다는 것이다. 그럼에도 일은 오히려 전보다 훨씬 많아졌다. 시간이 없어 미루던 디자인 비교와 화면 재현, 에러 관측까지 끝까지 해볼 수 있게 되니 절약한 시간만큼 여유가 생기지는 않았다. 필자는 해오던 일을 줄이기 위해 해야 하는 일이 새로 생겼다고 정리한다. 사이드 프로젝트에서는 FE 전문성을 쓰는 것들을 계속 만들며 언젠가 쌓아 둔 부품으로 다시 새 UX를 제안하고 만들 수 있기를 기대한다.

## 읽을 때 유의할 점

첫째, 이 글은 한 사람의 한 조직에서의 경험이다. 회사와 제품이 비공개이고 코드 줄 수(12,000줄 파일, 12만 줄 제거), 소요 시간(7시간 30분 작업 표시) 외에는 지표가 없다. 하네스 대 스킬, 이슈 중심 개발의 효과는 통제된 비교가 아니라 인상이다. 둘째, 글은 필자가 AI에게 인터뷰를 받아 쓴 형태라 본문 속 문답이 당시 실제 대화가 아니라 정리된 서술이다. 필자도 AI 특유의 어색함을 손으로 고쳤다고 밝힌다. 셋째, 특정 모델(GPT 계열, 새 버전 표기 astra)과 시점에 의존한다. 스킬을 덜어내야 했다는 경험이 다른 모델에도 그대로 적용된다는 보장은 없다.

넷째, 서브에이전트가 같은 이슈를 비슷하게 구현하는지 AI가 판정했고 사람이 직접 비교하지 않았다는 점은 필자가 스스로 밝힌 한계다. 다섯째, BE 파일 수정 금지나 디자인 레포 권한 회수 같은 경계 설정은 한 팀의 합의이며 일반 규범으로 읽을 수 없다. 여섯째, 필자는 FE 역할이 인프라처럼 변한다고 느끼지만 모든 팀에서 같은 압력이 있는지는 말하지 않고 자기가 FE라서 그렇게 느낄 수도 있다고 단서를 단다. 일곱째, 이미지 22장(화면 비교, 구조도, 비교 도구)은 읽지 못했다.

그럼에도 이 글에서 가져갈 점검 질문은 선명하다. 금지 규칙을 늘려 AI의 코드를 통제하려다 규칙을 피하는 코드를 만들고 있지 않은가, 평소의 판단을 AI와 실제 파일을 고치는 대화에서 꺼내 스킬로 남기고 있는가, 맥락을 새 문서가 아니라 이슈와 PR에 남기고 다른 에이전트가 같은 뜻으로 읽는지 확인했는가, AI가 스스로 화면 상태를 재현하고 에러를 볼 환경이 있는가, 팀원이 서로의 AI에게 맡기는 동안 사람끼리 무엇을 하는지 나눌 출발점이 있는가, 모델이 바뀔 때 스킬을 덜어낼 수 있는가.
