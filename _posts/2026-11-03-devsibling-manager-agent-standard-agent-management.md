## TL;DR

- 주장의 뼈대는 에이전트는 빠른데 병목은 사람이라는 것이다. 사람이 모든 세션의 승인과 검토를 맡지 않도록 사람과 코딩 에이전트 사이에 매니저 에이전트와 코디네이터 에이전트 두 층을 두고, 이 두 층은 코딩하지 않고 일을 나눠 주고 결과를 확인하게 하자는 구조다.
- 근거 수치는 본인이 센 한 번의 실측이다. 쉬는 세션 28개 중 결정을 기다리던 것이 13개였고, 그중 직접 판단할 것은 6개, 기준만 있으면 통과할 수 있는 것은 7개였다.
- 구조의 사례는 Lauren Tan이 공개한 흐름이다. 바깥 루프(Grok Bot)가 Slack과 Linear에서 일거리를 모으고, 안쪽 루프(Cursor Projects)가 클라우드 에이전트에 위임하며, 수정은 에이전트 떼로 깨뜨려 보고 1시간 뒤 자동 병합한다. 공식 글과 X 게시물이 이 구조를 확인해 준다.
- 맡길 범위는 신뢰 역피라미드로 정한다. 코드 구조, 정적 분석, 프롬프트, 사람 리뷰의 순서로 노력을 위에 몰고, pstack의 correct 스킬로 반복 실수를 CI 검사로 올린 뒤 16분 만에 다른 세션의 같은 실수를 잡은 경험을 든다.
- 한계는 두 가지다. 한 달 2,500개와 날짜별 도입 시점 등은 대부분 본인 발표이고, 제목의 "표준"은 영상 제작자의 전망이다. 관제실 역할의 두 층이 뚫리면 연결된 에이전트가 함께 열리므로 사설망 안에서만 쓰라는 경고가 구조만큼 중요하다.

## 영상에 대하여

개발동생 채널이 2026년 11월 3일에 올린 22분 55초 영상이다. 한국어 사람 자막 전체를 읽었고 마지막 타임스탬프가 영상 길이와 맞는다. 영어 사람 자막도 있었지만 원본이 한국어라 한국어 쪽을 썼다. 설명란은 협찬이 아니라고 밝히고 Lauren Tan이 Grok Bot을 만드는 SpaceXAI 소속이라 자사 제품 이야기이기도 하다고 적는다. 이 블로그의 [Lauren Tan 가이드 해설 노트](https://raphael-shin.github.io/jungseob-blog/posts/leo-xiaolei-lauren-tan-grok-bot-team-guide-commentary/)와 [신뢰 곡선 노트](https://raphael-shin.github.io/jungseob-blog/posts/tan-trust-curve-verification-agents/), [Miller 강연 노트](https://raphael-shin.github.io/jungseob-blog/posts/miller-agent-conf-grok-bot-software-factory/)가 같은 인물과 제품을 다른 시점에서 본 글이다.

## 문제: 에이전트는 빠른데 병목은 나

진행자는 동시에 다섯에서 열 개의 세션을 띄워 쓰는데, 작업이 끝나거나 확인이 필요할 때마다 사람이 모두 해결하는 구조에서는 코드 생성이 빨라져도 더 나아가지 못한다고 말한다. 최근 직접 세어 보니 쉬는 세션이 28개였고 그중 결정을 기다리는 것이 13개였다. 이 13개를 들여다보면 직접 판단할 것은 6개뿐이었고 기준을 설계해 두면 통과할 수 있는 것이 약 7개였다. 기준으로 승인하거나 병합을 허용하는 역할을 가운데 두면 생산성이 오르고 인지 부하가 줄어든다는 것이 핵심 주장이다.

이 생각이 혼자만의 것이 아니라는 근거로 석 달 사이에 나온 세 제품을 든다. 8월 11일 Grok Bot, 9월 29일 OpenAI dots, 10월 21일 Claude Duet이며 모두 24시간 돌아가고 사람과 대화한다. 그는 이 구조가 앞으로 표준이 될 가능성이 아니라 이미 표준이 되고 있다고 개인적으로 본다.

## 3단 구조

가장 아래는 Claude Code, Codex, Cursor 같은 코딩 에이전트 층이다. 그 위에 코디네이터 층을 두는데, 프로젝트 단위로 작업을 받아 아래의 코딩 에이전트에게 알맞게 분배만 하며 직접 코딩하지 않는다. 제품으로는 Cursor Projects와 Claude Code Projects가 있고 OpenAI는 별도 제품이 없어 dots가 이를 겸한다고 그는 본다. 가장 위가 매니저 에이전트 층으로, Grok Bot과 OpenAI dots와 Claude Duet처럼 꺼지지 않고 Slack과 Gmail과 이슈를 끌어와 일거리를 찾고 사람과 직접 대화한다.

위의 두 층이 코딩하지 않는 이유는 비용과 컨텍스트 창이다. 코딩 맥락까지 매니저의 컨텍스트 창에 쌓이면 매니징 성능이 떨어지고 혼란이 온다는 설명이다. 각 층의 일은 위로 올라오는 결정의 양을 줄이는 것이다. 작업을 만들고 분배하고 결과를 받아 대부분의 결정을 위에서 처리하며 사람은 정해 둔 기준 밖의 결정만 본다.

## Lauren Tan의 흐름

영상은 사례로 Lauren Tan이 한 달에 PR 2,500개를 올렸다고 소개한다. 30일 내내 해도 하루 83개이고 사람이 하나하나 리뷰하면 나올 수 없는 수치라 결국 에이전트 층으로 사람의 인지 부하를 줄인 구조라는 해석이다. 그가 소개하는 하루는 다음과 같다. Slack에 피드백이 오면 Linear 티켓이 되고 클라우드 에이전트가 버그를 재현해 고치며 여러 에이전트를 띄워 그 수정을 일부러 깨뜨려 본다. 문제가 없으면 1시간 뒤 병합한다.

Lauren은 Grok Bot을 바깥 루프, Cursor Projects를 안쪽 루프라 부른다. 바깥 루프는 Slack과 Linear와 X와 Sentry 같은 커넥터로 맥락을 모으고 루틴으로 정해진 시간이나 사건마다 깨어난다. 안쪽 루프는 맥락으로 개발 계획을 세우고 클라우드 에이전트에게 위임하며 필요할 때만 로컬 에이전트를 쓴다. 클라우드를 기본으로 두는 이유는 노트북을 닫아도 작업이 멈추지 않기 때문이다. 검증은 Cursor가 공개한 pstack의 검증 스킬 묶음으로 하고 사람이 개입하는 곳은 바깥 루프에 맥락을 넣을 때와 안쪽 루프의 계획을 검토할 때다.

## 진행자의 구성과 승인 카드

진행자는 매니저로 Grok Bot을, 코디네이터로 Paseo를 쓴다. Paseo는 여러 코딩 에이전트를 한 곳에서 다루는 통합 환경이고 Orca나 Herdr도 같은 자리를 채울 수 있다. 자리에 앉아 있을 때는 Paseo에 띄운 매니저 세션에 직접 시키고 세션이 보내 오는 완료 보고 중 자신이 정의한 규칙으로 처리할 수 있는 것은 매니저가 처리하고 나머지만 알려 주게 한다. 이때 가장 중요한 설계가 승인 카드다. 모든 일을 알아서 처리하라고 하면 위험하므로 무엇은 알아서 무엇은 보고하라고 정해 두고 보고된 것을 승인할 수 있는 시스템을 만들어야 한다.

그 기준은 Lauren의 신뢰 역피라미드를 따른다. 첫째가 구조가 잘 짜인 코드로, 별도 비용이 들지 않는다. 둘째가 린트와 테스트와 CI의 안전장치로 규칙 기반이라 필수다. 셋째가 구조와 CI가 잡지 못하는 것을 AGENTS.md 같은 프롬프트로 지시하는 것이다. 마지막이 사람 리뷰인데, 효율을 늘리기 어렵고 현실적으로 불가능한 부분이 많으므로 위쪽에서 최대한 검증해 사람은 핵심만 보게 한다. 에이전트를 1개에서 5개로 늘리기는 쉽지만 5개에서 100개로 늘리기 어려운 이유는 신뢰가 없기 때문이라고 그는 본다.

## 실수를 검사로 바꾸기와 관제실 보안

pstack의 correct 스킬은 에이전트의 과거 실수를 유형별로 묶고 자주 나오는 유형은 글이 아닌 CI 검사로 올리게 한다. 그가 만들고 있는 영상 편집 앱에 돌리자 커밋 1,054개와 리뷰 777개를 분석해 실수 13유형을 뽑았고 그중 둘을 검사로 올렸다. 하나는 번역하지 않은 화면 문구를 직접 넣는 실수였고 다른 하나는 조건에 따라 버튼 자리가 사라지는 문제였다. 둘 다 AGENTS.md에 규칙으로 적어 둔 것이었다. 검사를 만들고 16분 뒤 다른 세션에서 같은 실수가 나왔는데 새 CI 단계가 그것을 잡았다고 한다.

보안 사례는 본인의 설정 실수다. 세 기기(Mac mini, MacBook, iPhone)에서 같은 Paseo 세션을 공유하려고 릴레이를 열어 둔 것을 닫고 접속에 비밀번호를 걸고 외부에서는 Tailscale로 연결된 기기끼리만 접속하게 고쳤다. 매니저와 코디네이터는 관제실이라 뚫리는 순간 연결된 에이전트와 호스트가 함께 열리므로, 인터넷으로 문을 열지 말고 사설망 안에서만 쓰라는 것이 마지막 조언이다.

## 대조해서 확인한 점

**Lauren Tan의 게시물.** 영상이 인용한 X 게시물은 맞다. 2026년 9월 21일 게시에서 Lauren은 지난달 프로덕션에 PR 2,500개를 올린 방법이라며 Cursor Compile 런던 행사에 가지 못해 영상으로 무료 공개한다고 쓴다(좋아요 약 2만 1천, 조회 약 448만). 10월 6일 게시는 Slack 피드백을 보고 Linear 티켓을 만들고 Cursor 클라우드 에이전트가 pstack으로 재현하고 재현되면 수정을 올리고 에이전트 떼로 PR을 퍼징하며 문제가 없으면 Slack으로 알리고 1시간 뒤 사용자가 변경을 요청하지 않는 한 리베이스해 자동 병합한다는 다섯 단계를 제시한다. 영상의 하루 흐름과 일치한다. 10월 16일 게시는 코드베이스 개선, 정적 분석, 프롬프트, 사람 리뷰의 네 단계 역피라미드를 설명한다. 영상의 순서와 설명이 같다. 다만 "한 달 2,500개"와 "Slack 피드백에서 병합까지 사람은 개입하지 않는다"는 본인의 서술이고 이 노트는 PR 수를 저장소로 확인하지 못했다. Lauren의 X 팔로워가 3만에서 25만으로 늘었다는 영상의 서술도 확인하지 못했다.

**제품들.** Cursor Projects의 공식 글은 코디네이터가 직접 코딩하지 않고 코딩하는 에이전트를 지휘하며 기본이 클라우드이고 노트북을 닫아도 계속된다고 쓴다. Cursor는 신규 사용자가 병합하는 PR이 30% 늘고 Projects를 주로 쓰는 사용자는 6배 병합한다고 주장하는데 이는 공급사 자체 수치다. Claude Code Projects 문서는 일마다 스레드를 만들거나 이미 그 영역을 맡은 스레드에 넘기고 개요 화면에서 끝난 일을 본다고 쓴다. Claude Duet 글은 2026년 10월 21일 게시되었고 능동적으로 할 일을 가져오고 사용자가 자리를 비워도 일하며 대신 행동하기 전에 확인한다고 설명한다. 영상의 날짜와 맞다. Grok Bot은 8월 11일 출시가 다른 노트에서 확인되었다. OpenAI dots 페이지는 접근이 막혀 9월 29일 날짜를 확인하지 못했다.

**pstack.** 저장소 소개는 Lauren(poteto)이 만든 스킬 묶음이고 품질 있는 코드를 위한 것이며 poteto-mode로 여러 에이전트를 병렬로 돌린다고 쓴다. 10월 16일 게시도 correct와 architect와 sharpen 같은 스킬을 쓰라고 안내한다. 영상 속 correct의 결과(커밋 1,054개, 리뷰 777개, 13유형, 2개 승격, 16분 뒤 재발 차단)는 진행자의 경험이다.

**Paseo 보안.** Paseo 보안 문서는 데몬이 사용자의 기기에서 돌고 클라이언트가 연결하는 구조이며 릴레이가 가장 쉬운 연결 방식이지만 새 설치에서는 꺼져 있고 기기를 짝지을 때 켤지 묻는다고 쓴다. 릴레이를 끄면 직접 TCP나 Tailscale 같은 VPN으로 연결할 수 있다. 진행자의 "릴레이를 열어 두었던 것은 내 설정 실수"라는 설명은 문서와 어긋나지 않는다.

**SpaceX의 Cursor 인수.** 영상은 매니저와 코디네이터 층을 한 회사가 함께 가지게 된 점에서 인수가 좋은 선택이었다고 평가한다. 2026년 6월 Reuters 등이 인수를 600억 달러 전액 주식 거래로 보도했다. 평가 부분은 진행자의 의견이다.

**진행자의 실측.** 세션 28개와 결정 대기 13개, 직접 판단 6개와 기준 통과 7개는 한 번의 셈이며 일반화할 근거가 없다. 매니저가 기준에 따라 승인하는 방식의 오승인 비율은 영상에 나오지 않는다.

## 읽을 때 유의할 점

첫째, 제목의 "표준"은 진행자의 전망이다. 세 제품이 비슷한 구조를 택했다는 것은 사실이지만 표준이 된다는 것은 아직 판단할 수 없다. 둘째, 사례 중심의 Lauren은 해당 제품을 만드는 회사의 엔지니어이고 영상도 이를 밝힌다. 한 사람이 1시간 뒤 자동 병합까지 신뢰하는 환경은 검증 스킬과 CI와 에이전트 떼를 이미 갖춘 경우의 이야기다. 셋째, 두 층이 코딩하지 않는다는 설계는 컨텍스트 창 논리에 기대는데 영상은 이를 실험으로 보이지 않는다. 넷째, 승인 카드의 기준 설계가 핵심이라고 하면서 구체적인 기준 목록은 보여 주지 않는다. 다섯째, 관제실 층이 곧 보안 경계라는 경고는 구조의 대가로 가볍게 넘길 수 없다. 매니저가 Slack과 Gmail과 코드 저장소에 모두 연결될수록 침해 시 피해가 커진다.

가져갈 질문은 선명하다. 내 세션 중 사람 판단이 필요한 것은 몇 퍼센트인가, 나머지를 통과시킬 기준을 코드와 CI로 쓸 수 있는가, 매니저에게 준 권한을 침해당했을 때 어디까지 번지는가, 반복 실수를 글이 아니라 검사로 올리는 습관이 있는가.
