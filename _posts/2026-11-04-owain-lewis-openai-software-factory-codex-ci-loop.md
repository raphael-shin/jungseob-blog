## TL;DR

- 영상의 요지는 OpenAI의 소프트웨어 공장이 이미 대부분의 팀이 짓는 방식과 비슷해서 단계별로 가져다 쓸 수 있다는 것이다. 과제를 말하는 빌더, 구현하는 Codex, 빌드와 테스트를 하는 CI가 한 루프를 돌고, 변경이 준비될 때까지 에이전트가 반복한다.
- 눈에 띄는 요소는 세 가지다. 데이터와 인프라와 클라우드와 보안 전문가 역할의 여러 리뷰 에이전트, 변경을 낮은 위험과 높은 위험으로 나누어 낮은 위험은 에이전트가 병합하는 분류, 운영을 지켜보다 장애를 조사해 권고하는 에이전트다.
- 진행자는 두 가지를 직접 만들어 보였다. Codex 자동화가 열린 PR에 위험 라벨을 붙이고 CI가 통과한 낮은 위험만 병합하는 것, Google Cloud에서 알림이 Pub/Sub을 거쳐 ADK 에이전트로 가서 로그와 지표와 리비전을 보고 이전 정상 리비전으로의 복원을 권고하는 것이다.
- 원문과 튜토리얼 저장소를 대조하면 영상이 몇 군데에서 원문보다 앞서 나간다. 원문에서 자동 승인은 낮은 위험 영역이 옵트인한 경우이고, 배포는 사람이 승인한 뒤 에이전트가 지켜보는 구조이며, 장애 대응 봇 Sevbot은 완화책을 정하되 실행하지 않는다. 데모의 에이전트도 읽기 전용 도구만 갖고 롤백 도구가 없다.
- 원문은 유료 구독 글이라 이 노트는 무료로 공개된 앞부분(소프트웨어 공장 절을 포함한 약 2만 자)만 읽었고, 진행자는 OpenAI와 무관한 제3자이며 데모는 가르치기용 구현이다.

## 영상에 대하여

Owain Lewis가 2026년 9월 21일에 올린 10분 48초 영상이다. 영어 자동자막 전체를 읽었고 마지막 타임스탬프가 길이와 맞는다. 설명란은 개인 커뮤니티와 소프트웨어 거래 모음 홍보 링크, 해설 대상인 The Pragmatic Engineer 글, 프롬프트와 자료가 든 GitHub 저장소 링크를 둔다. 진행자는 클라우드 운영 경력이 있다고 말하며 이 영상은 OpenAI 공식 자료가 아니라 한 외부 개발자의 해설이다. 이 블로그의 [Lethain의 소프트웨어 공장 패턴 노트](https://raphael-shin.github.io/jungseob-blog/posts/lethain-software-factory-pattern/)와 [Kapur와 Osmani의 검증 노트](https://raphael-shin.github.io/jungseob-blog/posts/kapur-osmani-who-verifies-the-software-factory/)가 같은 질문, 곧 에이전트가 쓴 코드를 누가 어떻게 믿는가를 다룬다.

## 구조: 빌더와 Codex와 CI 루프

진행자가 가리키는 도식은 대부분의 팀이 이미 짓는 흐름과 닮았다. 과제를 설명하는 소프트웨어 빌더가 있다. 빌더라는 말을 쓴 것은 엔지니어일 수도 있고 제품 관리자 같은 다른 팀원일 수도 있기 때문이다. 요청은 Codex로 가서 코드가 만들어지고 지속적 통합 시스템이 빌드하고 테스트하며 에이전트가 이 순환을 몇 번 돌아 변경이 준비될 때까지 간다. 코드 리뷰에도 AI 에이전트를 쓰는 것은 흔하지만 OpenAI는 데이터와 인프라와 클라우드와 보안 전문가 에이전트로 나눠 서로 다른 면을 본다.

진행자가 가장 흥미롭게 보는 요소는 분류다. 에이전트가 만드는 코드가 늘면 PR이 쌓여 사람이 따라가지 못하므로, 변경이 낮은 위험인지 높은 위험인지 분류해 에이전트가 병합하고 배포할지 결정한다. 사람들은 사람의 리뷰 없는 병합에 반발하지만 문서 변경이나 사소한 버그 수정에 큰 리뷰가 필요하지 않을 때가 있고 위험은 상대적이다. 혼자 GitHub에 올리는 개발자의 실수 비용은 낮지만 Amazon처럼 변경 하나가 한 리전의 수천 고객을 멈출 수 있는 곳은 다르다. 인프라나 데이터베이스를 건드리는 변경은 높은 위험으로 보아 사람이 본다.

운영 쪽에서는 장애 대응 봇을 언급한다. 에이전트가 운영을 지켜보고 오류를 찾아 사건을 조사하고 온콜 엔지니어가 해결하도록 돕는다. 하루에 수백 번 호출되는 클라우드 운영 경험에서 이것이 강력한 활용이라고 말한다. 성능 공장은 운영에서 성능 시험을 돌리고 퇴행이나 오류가 나오면 Codex로 되돌려 보내므로, 공장 전체가 코드를 밀어 올리고 운영에서 버그와 장애를 티켓으로 되돌리는 자기 개선 루프라는 설명이다.

## 데모 1: 위험 분류와 자동 병합

첫 데모는 열린 PR을 읽어 위험을 분류하고 라벨을 붙인 뒤 낮은 위험이고 테스트가 통과하면 병합하는 자동화다. 높은 위험(데이터베이스나 인프라 변경)은 사람의 승인을 기다린다. 진행자는 작은 PR을 하루에 많이 올려 일일이 검토하고 어느 것이 검토 대상인지 기억하기 번거로우므로 주기를 줄이려 한다고 말한다. 구현은 단순한 Codex 자동화로, 모든 열린 PR을 검토해 위험 라벨 하나를 붙이고 병합 가능한 것을 병합한다. 실행해 보면 사소해 보이는 낮은 위험 PR이 있으나 CI가 실패해 병합하지 않는다. CI가 통과했다면 자동으로 병합했을 것이다. 오래된 PR 중 리베이스나 갱신이 필요한 것은 코드가 달라질 수 있어 더 위험하다고 보고 병합하지 않으며 안전한 것만 병합한다.

## 데모 2: 온콜 알림 에이전트

둘째 데모는 SRE 에이전트다. 진행자는 대부분의 앱을 Google Cloud에서 돌리므로 알림이 큐(Pub/Sub)에 들어가고 Agent Development Kit(ADK)로 만든 에이전트가 로그와 지표와 리비전을 보고 상황을 판단해 검토할 수 있는 곳에 기록을 저장하게 했다. 새벽 2시에 호출된 지친 사람이 정보를 찾고 지표를 대조하기는 어렵고 기계는 빠르다는 이유다. 시스템이 500 오류를 내는 상황에서 에이전트가 권고한 조치는 이전의 정상 리비전으로 트래픽을 되돌리는 것, 곧 롤백이었다. 진행자는 이것이 정확히 옳은 조치이며 온콜 엔지니어가 에이전트에게 롤백하는 법을 물을 수 있다고 한다.

배포에 에이전트를 쓰는 것도 소개한다. 12개월 전이라면 무모하다고 했겠지만 지금은 이치에 맞고 본인도 많이 쓴다. 결정론적 코드로 변경을 내보내되 에이전트가 사람이 어려워하는 방식으로 운영을 지켜보며 자기 대시보드를 만들고 지표와 로그와 텔레메트리를 보다가 오류를 감지하면 변경을 되돌려 바로 해결할 수 있다는 설명이다.

## 대조해서 확인한 점

**원문의 범위.** The Pragmatic Engineer의 글 「Inside OpenAI's agentic software factory」는 2026년 9월 15일 게시된 유료 구독 글(약 7,700단어)이다. 이 노트는 무료로 공개된 앞부분 약 2만 자를 읽었고 소프트웨어 공장 절은 거기에 포함되어 있다. 이후 절(엔지니어링 도구, 인프라, API 신뢰성, 직무 변화)은 읽지 못했다.

**구조 단계.** 원문은 공장을 아홉 단계로 설명한다. 사람 빌더가 결과를 정의하고 Codex가 문서와 Git과 Slack과 Notion과 내부 데이터 소스에서 맥락을 모으고 구현하고 빌드와 테스트 뒤 PR을 만들고 CI가 초록이 될 때까지 에이전트가 돌보며 성능 영향이 있는 PR은 A/B 프레임워크로 보낸다. 이어서 에이전트 리뷰, 에이전트 배포, 운영 관찰, 운영의 피드백, 장애 대응이다. 영상의 빌더, Codex, CI 순환과 맞는다. 원문에서 빌더는 엔지니어나 제품 관리자라고 설명한다.

**전문가 리뷰.** 원문은 일반 AI 리뷰어 하나가 아니라 도메인 전문가 구성을 가진 여러 에이전트를 띄우며 관련 인프라 팀의 사람 전문가가 모든 변경을 보는 것과 같다고 본다. 글쓴이는 클라우드 인프라 전문가 역할을 준 에이전트가 일반 에이전트와 다른 리뷰를 내는지 회의적이었으나 모든 Codex 에이전트가 OpenAI 코드와 문서에 접근하므로 맥락이 쌓인 타깃 피드백이 가능하다고 본다. 영상의 데이터, 인프라, 클라우드, 보안 네 가지 목록 중 이 노트가 읽은 범위에서 확인된 것은 클라우드 인프라와 보안이고 데이터 전문가는 확인하지 못했다.

**위험 분류와 자동 승인.** 원문은 변경을 위험도로 분류해 높은 위험은 더 엄격한 과정(더 많은 AI 리뷰나 사람 리뷰)을 거치고 낮은 위험은 코드베이스의 영역이 옵트인하면 낮은 위험 PR을 자동 승인하는 에이전트를 쓴다고 쓴다. 영상이 말한 병합과 배포 결정 중 병합 쪽은 맞지만 원문에서 자동 승인은 옵트인한 영역에 한정된다.

**배포.** 원문에서 에이전트 배포 단계는 사람이 변경의 운영 반영을 승인한 뒤 시작한다. 에이전트는 변경을 안전하게 완전히 롤아웃할 때까지 지켜보는 임무를 받고 기능 플래그 뒤의 변경이면 플래그 위치를 찾고 성공과 실패 신호를 정해 스스로 대시보드를 만들어 지켜본다. 원문은 변경마다 자율 SRE에 가까운 것이 장기 목표라고 쓴다. 영상이 말한 오류 감지 시 변경을 되돌려 해결한다는 서술은 원문의 읽은 범위에서 확인되지 않았다.

**장애 대응 봇.** 원문의 Sevbot은 사건이 감지되면 깨어나 맥락을 모으고 가능한 완화책을 정하지만 실행하지는 않으며 개발자의 질문에 답하고 엔지니어가 시키면 특정 완화책을 적용한다. 장기적으로 일상적 장애를 자율 처리하게 하는 것이 목표이나 지금은 온콜이 사라지지 않았다. 영상이 말한 대로 조사와 권고를 하되 스스로 조치한다는 부분은 아직 목표 단계다.

**성능 공장.** 원문은 알림과 대시보드를 훑어 신호를 중복 제거하고 실제 지연 퇴행을 찾아 원인을 분석하고 수정을 제안한다고 쓴다. 영상의 설명과 맞는다. 원문은 이런 에이전트 루프로 CI/CD에 걸리는 부하가 엔지니어당 PR 수의 급증으로 어떤 시스템에서는 약 10배, 6개월 만에 늘었다고도 쓴다.

**튜토리얼 저장소.** 진행자의 GitHub 저장소(MIT 라이선스) 튜토리얼은 이 데모들이 OpenAI 내부 도구가 아니라 원문 보도에서 영감을 받은 가르치기용 구현이라고 밝힌다. PR 데모의 프롬프트는 기본 모드가 시험 실행(드라이런)이고 아주 좁은 정책에 맞는 변경만 설명하며 라이브 모드는 라벨 붙이기와 병합을 원할 때만 켠다. 위험 라벨은 평가의 표시일 뿐 영구적 허가가 아니라서 새 커밋마다 새 평가가 필요하고 테스트 통과와 낮은 위험은 별개의 조건이며 인증과 데이터베이스와 인프라와 배포 변경은 사람의 검토가 필요하다. 알림 데모는 합성 결제 API가 Cloud Run에서 돌고 ADK 에이전트가 읽기 전용 도구 세 개를 쓰며 셸이나 배포나 롤백 도구가 없다. 모델이 자기 권고가 통했는지는 판단하지 않고 모니터링이 복구 여부를 판단한다. 저장소는 실제 워크로드에는 별도 프로젝트를 쓰라고 안내한다.

확인하지 못한 것은 영상 속 데모 화면의 구체적 동작(자막만 읽었다), 영상이 말한 데이터 전문가 에이전트, 원문의 유료 부분이다.

## 읽을 때 유의할 점

첫째, 영상은 OpenAI가 아닌 제3자의 요약이고 일부 문장이 원문보다 앞선다. 자동 병합과 자동 배포와 자동 되돌리기를 OpenAI가 이미 한다고 읽으면 과장이다. 둘째, 진행자의 데모는 장난감 규모의 가르치기용 구현이고 저장소가 밝히듯 PR 데모는 좁은 정책이며 알림 데모는 읽기 전용이다. 셋째, 위험 분류는 분류기의 오분류가 곧 자동 병합 사고라서, 라벨이 평가일 뿐 허가가 아니라는 저장소의 구분이 영상보다 신중하다. 넷째, 원문이 말하는 공장은 OpenAI 내부 시스템과 무제한 토큰 예산에 연결된 환경이므로, 외부 팀이 같은 효과를 얻을지는 별개다. 다섯째, 영상 설명란에 개인 커뮤니티와 거래 모음 홍보가 있어 상업적 맥락이 있다.

가져갈 질문은 선명하다. 우리 변경 중 사람 검토 없이 병합해도 되는 영역은 어디까지인가, 위험 평가가 새 커밋마다 다시 이루어지는가, 장애 대응 에이전트에게 읽기 전용에서 쓰기 권한으로 넘어가는 기준은 무엇인가, 분류기가 틀렸을 때 되돌리는 경로가 있는가.
