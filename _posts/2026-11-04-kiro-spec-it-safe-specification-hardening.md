## TL;DR

- 글의 전제는 명세 주도 개발의 명세가 보이는 기능은 쓰지만 오용에 견디는 법은 쓰지 않는다는 것이다. 로그인이 깨지면 누가 알아채지만 인젝션이나 인가 결함은 아무도 실행하지 않아 기능 검사를 모두 통과하므로, 명세에 보안 제약이 없으면 에이전트는 프레임워크 기본값에 기대게 된다.
- 해법은 요구사항(EARS)이 끝난 뒤 계획 전에 끼우는 Kiro Power 하나다. 요구사항 문장에서 사용자 입력, 인증, 데이터 처리 같은 단서를 찾아 CWE 매핑 60개 중 해당하는 약점을 판정하고, 명세가 이미 다룬 것은 빼고 빠진 보안 의무만 추적 가능한 EARS 항목으로 요구사항 파일에 끼워 넣는다.
- 예시는 의사가 환자 이름으로 임상 노트를 찾는 요구사항이다. 엔진이 SQL 인젝션(CWE-89)과 인증 누락(CWE-306)에 대해 일곱 개 제약을 쓰고, 검토 단계가 데이터 최소화(CWE-200)와 진료 관계 기반 인가(CWE-862)를 더한다. 인가 누락은 키워드로 잡히지 않아 사람이나 에이전트의 판단이 필요했다.
- 글이 스스로 밝히는 한계가 크다. 이 도구는 생성된 코드를 검증하지 않고 취약점이 없음을 증명하지 않으며 SAST와 DAST와 사람 검토를 대체하지 않는 연구 시제품이다.
- 이 노트가 확인한 것은 공개 저장소의 존재와 구조, 임계값과 매핑 수의 일치뿐이고, 환자 예시의 코드와 효과는 글의 설명이다. 도구의 탐지율이나 오탐률은 글에 없다.

## 글에 대하여

Kiro 블로그에 2026년 10월 30일 게시된 글이다. 파워의 저자는 저장소의 스킬 메타데이터에 Rajdeep Mukherjee로 적혀 있고 글 자체의 저자란은 페이지에 따로 없다. 영어 본문 약 1만 6천 자와 다이어그램 설명을 전부 읽었다. 같은 날 수집한 짝 글인 [Kiro의 Lean 하네스 증명 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-proves-harness-properties-in-lean/)가 에이전트가 만든 코드를 증명으로 검증하는 쪽이라면, 이 글은 코드가 생기기 전의 명세 쪽에서 위험을 줄이려는 접근이다. 이 블로그의 [Kiro 워크플로 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-workflows-dependency-upgrade/)가 같은 제품의 다른 기능을 다룬다.

## 명세의 사각지대

명세 주도 개발은 프롬프트 하나가 아니라 명세로 에이전트를 설계와 작업과 구현으로 이끈다. 글은 이 흐름을 명세, 계획, 실행으로 줄여 부른다. 문제는 대부분의 명세가 소프트웨어가 해야 할 일을 쓰고 오용을 견디는 법을 쓰지 않는다는 점이다. 기능 요구사항은 스스로 증명되지만 보안 요구사항은 그렇지 않다. 앱이 모든 기능 검사를 통과하면서 인젝션이나 인가 결함을 열어 둘 수 있는데 실패 경우를 실행하는 것이 아무것도 없어서다. 명세에 보안 제약이 없으면 에이전트에게는 쌓아 올릴 보안 목표가 없다.

저자들은 해법을 더 나은 모델이나 마지막의 보안 검토가 아니라 일을 더 앞으로 당겨 직접 통제할 수 있는 층, 곧 명세에 두자고 한다. 보안 의무를 명세에 쓰면 코드가 생긴 뒤 검토자가 잡아내도록 두는 대신 에이전트가 만들고 반복할 구체적인 목표가 생기고 보안 요구를 일찍 말하면 맞추기 쉬운 구조의 설계로 이끌기도 한다는 설명이다.

## 명세 강화: 엔진의 구조

도구는 Kiro Power, 곧 플러그인이다. 기능 요구사항이 끝난 뒤 계획 전에 EARS 요구사항을 읽어 문구가 시사하는 약점 유형을 표시하고 추적하고 시험할 수 있는 보안 의무를 제안한다. 제안은 모델의 추측이 아니라 MITRE의 CWE 약점 분류를 재사용 가능한 보안 의무에 연결한 선별 라이브러리에서 나온다. 요구사항 문구가 약점을 시사할 때만, 곧 사용자 입력이나 인증이나 데이터 처리 같은 단서가 있을 때만 제안하므로 앱이 하는 일에 맞는 제약만 보인다. 라이브러리는 여덟 개 보안 영역(인젝션, 인증, 인가, 데이터 노출, 암호, 입력 검증, 보안 설정 오류, 비즈니스 로직)에 걸친 CWE 60개 매핑을 결정론적 TypeScript 라이브러리와 CLI로 제공하며 약점 선별과 탐지 패턴은 주로 OWASP Top 10:2021과 Amazon Q Developer Detector Library를 따른다. 각 매핑에는 OWASP 범주와 수동으로 매긴 심각도가 있다.

엔진은 요구사항 파일마다 세 단계를 돌리고 같은 도구 버전과 매핑과 옵션과 입력에는 같은 결과를 낸다. 첫째로 트리거 탐지는 각 요구사항을 60개 매핑과 부분 문자열 키워드(예를 들어 database, upload, session)와 정규식 두 어휘 신호로 대조해 한정된 점수로 합치고 점수가 기본 0.3을 넘으면 해당 CWE를 표시한다. 어휘 매칭이라 문구에 명시되지 않은 약점은 놓칠 수 있다. 둘째로 커버리지 확인은 표시된 CWE마다 명세가 필요한 프리미티브, 곧 매개변수화 질의 문장이나 소유권 검사나 출력 인코딩을 이미 말하는지 본다. 빠진 것만 제안이 되지만 확인이 파일 전체에 걸친 어휘 기반이라, 한 요구사항에 있는 통제가 다른 요구사항의 제안을 막을 수 있다. 셋째로 제약 제안은 차단하지 않고 빠진 제약을 EARS 항목으로 삽입한다. 가능하면 원 요구사항에서 자리표시자를 채우고 못 채우면 일반 표현으로 돌아가며 삽입된 줄마다 제안 ID와 보안 태그가 붙어 작성자가 차이(diff)로 검토한다.

엔진은 명세만 읽고 코드는 읽지 않는다. 제안한 제약을 작성자가 실제 시스템에 비추어 확인해야 하고 글은 이를 코드 수준의 검증이 아닌 상류의 통제점이라고 선을 긋는다.

## 예시: 환자 기록 검색

디지털 헬스 스타트업의 환자 포털에서 의사가 환자 이름으로 임상 노트를 찾는 요구사항을 든다. 요구사항은 완결돼 보이지만 일치 방식과 반환 필드와 실행 권한에 대해 아무 말이 없다. 에이전트가 만든 Express 엔드포인트(글의 설명용 의사 코드)에는 SQL 문자열 보간이 있어 전형적인 CWE-89가 되고 인증 검사가 아예 없으므로 CWE-306이 된다.

같은 요구사항을 엔진에 돌리면 어휘 탐지기가 두 약점 부류를 표시하고 일곱 개의 번호가 붙은 EARS 제약을 요구사항 안에 써 넣는다. 1.1과 1.2는 CWE-89의 매개변수화 질의, 1.3과 1.4는 CWE-89의 입력 검증, 1.5부터 1.7은 CWE-306의 인증이다. ID는 SEC 접두와 요구사항 번호와 EC로 시작하는 템플릿 번호로 읽는다. 검토 단계에서 Kiro 에이전트(CLI에서는 사람)가 두 제약을 더한다. 1.8은 반환 필드를 제한하는 데이터 최소화(CWE-200)이고 1.9는 요청한 의사가 환자와 활성 진료 관계가 있을 때만 노트를 반환하게 하는 인가(CWE-862)다.

중요한 점은 엔진이 쓰지 않은 것이다. 인증된 의사가 아무 환자의 노트나 읽을 수 있다는 인가 누락은 점수가 임계값 아래라서 쓰지 않고 의미적 후보로 검토자에게 올렸다. 도메인에 맞게 구체화된 1.9가 최종 문장이 되고 쿼리는 인가 범위로 좁혀진다. 글은 이렇게 결정론적 강화가 두 CWE에 걸친 일곱 의무를 냈고 데이터 최소화 규칙과 도메인 고유 인가 규칙은 검토에서 나왔다고 정리한다. 중간 단계의 구현 후보는 1.9를 아직 강제하지 않아 실제 환자 데이터에는 안전하지 않다고 글이 직접 표시한다.

## 쓰는 법과 적용 범위

파워는 GitHub의 sample-kiro-spec-security-hardening 저장소에 있고 두 가지로 쓴다. Kiro Power로는 요구사항이 확정된 뒤 harden my specs라고 요청하면 harden-spec 스킬이 번들 엔진을 찾아 처음에 빌드하고 .kiro/specs 아래 요구사항 파일에 돌리며 키워드가 보지 못하는 인가 누락을 의미적으로 검토하고 추가한 제약과 주의할 경고를 요약한다. CLI로는 컴파일된 도구를 명세 파일이나 디렉터리에 절대 경로로 가리킨다. 의미적 후보 플래그는 약한 인가 일치를 출력만 하고 파일에는 쓰지 않는다. 두 방식 모두 요구사항 파일을 제자리에서 고치므로 버전 관리와 코드 리뷰에 들어가며 엔진은 줄을 더하기만 하고 요구사항을 바꾸거나 쪼개거나 순서를 바꾸지 않는다. 엄격한 EARS가 아닌 요구사항은 고치지 않고 보고한다. 다시 돌리면 숨은 검토 표식이 이미 강화한 요구사항을 기록해 새로 바뀐 것만 강화하고 검토자가 지운 제약을 다시 제안하지 않는다.

적용은 세 경우로 나뉜다. 그린필드에서는 코드를 쓰기 전 명세 흐름의 한 단계로 보안 태그 제약을 더해 첫 커밋부터 보안 의도가 들어간다. 브라운필드에서는 요구사항을 추가하거나 바꿀 때 다시 돌려 새 요구사항만 강화하고 제약이 기능 작업과 함께 검토 가능한 차이로 나타난다. 명세만 읽으므로 제안된 의무를 기존 시스템의 실제 동작과 비교해야 하고 다르면 코드의 틈이거나 제약을 고쳐야 한다는 신호다. 현대화에서는 AWS Transform 같은 도구로 레거시에서 EARS 명세를 추출한 뒤 재구현 전에 일괄 강화해, 재구축된 시스템이 원본의 틈을 물려받지 않게 한다.

## 대조해서 확인한 점

공개 저장소는 확인된다. aws-samples 아래 sample-kiro-spec-security-hardening 저장소가 2026년 10월 16일에 만들어졌고 MIT-0 라이선스이며 README는 이 저장소가 Agent Plugins 1.0.0 명세로 패키징된 파워 자체라고 설명한다. 구성은 plugin.json과 harden-spec 및 security-primitives-reference 두 스킬, 번들 엔진 cwe-to-spec-mapping-library다. README는 라이브러리가 8개 보안 영역에 걸쳐 60개 CWE 매핑을 포함한다고 쓰고 임계값 기본 0.3과 의미적 후보 하한 0.05, 후보 출력 전용 동작이 글의 설명과 같다. 엔진은 컴파일된 채 배포되고 런타임 의존성이 없어 Node.js만 있으면 돌아간다. 다만 글의 워크플로 도식 설명에는 매핑이 61개로 적혀 있어 본문의 60개와 어긋난다. README가 60개이므로 도식이 오래된 수치일 가능성이 크지만 이 노트가 확정하지는 못했다.

확인하지 못한 것은 환자 예시의 코드 전체(글이 의사 코드라고 밝힌다)와 일곱 제약의 실제 문장 형태, 엔진의 탐지율과 오탐률, CWE 선별이 OWASP Top 10:2021과 Amazon Q Developer Detector Library를 따른다는 서술의 세부, 실제 프로젝트에서 보안 결함이 줄었는지 여부다. 글은 효과 수치를 제시하지 않는다. 저장소의 스타 수는 2개로, 아직 널리 쓰이는 단계가 아니다.

## 읽을 때 유의할 점

첫째, 글 스스로 이 도구가 연구 시제품이고 가설이며 생성된 코드를 검증하지 않는다고 말한다. 보안을 증명하는 도구로 읽으면 안 된다. 둘째, 탐지가 어휘 기반이어서 문구에 단서가 없으면 놓치고 파일 전체 커버리지 확인은 한 요구사항의 통제가 다른 요구사항의 제안을 가릴 수 있다. 가장 위험한 인가 누락이 점수 임계값 아래로 빠진 예시가 이 한계를 직접 보여 준다. 셋째, 의미적 검토를 AI 에이전트가 하므로 이 단계는 결정론적이지 않다. 넷째, 제약이 명세에 있어도 에이전트가 구현했는지는 별도로 검증해야 하며 글도 SAST와 DAST와 의존성 스캔과 사람 검토를 함께 권한다. 다섯째, 제품 회사의 글이고 저자들이 자기 가설을 주장하는 형태라 독립 평가가 없다.

가져갈 질문은 선명하다. 우리 명세에 실패 경우와 오용 경우가 적혀 있는가, 보안 제약이 기능 요구사항과 같은 추적 ID를 가지는가, 키워드로 안 보이는 인가 문제를 누가 어느 단계에서 묻는가, 명세의 보안 문장을 구현이 지켰는지 확인하는 검사가 따로 있는가.
