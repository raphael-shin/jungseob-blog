## TL;DR

- Claude Code 팀은 코드의 약 90%를 Claude가 쓰는 상황에서 코드 리뷰를 없애지 않고 대부분의 읽기를 자동화해 사람 시간을 아끼는 쪽으로 바꿨다고 쓴다. 6월부터 9월 사이 병합된 PR은 두 배 넘게 늘었고 되돌려진 PR의 비율은 40% 넘게 줄었다.
- 목표는 대부분의 PR이 되돌림이나 사고가 늘지 않으면서 사람 한 명(작성자일 수 있음)만 거쳐 병합되는 것이다. 사람 시간은 리뷰 시간과 나쁜 코드를 고치는 시간의 이중 비용이므로 되돌림과 사고율을 가드레일로 둔다.
- 변경은 PR 전 검증, 모든 PR의 AI 리뷰, 차단하는 보안 리뷰, 차단 검사, 위험에 따른 사람 승인, 병합 큐와 기능 플래그, 빠른 피드백과 롤백의 층을 거친다. 승인 단계는 작성자가 아니라 변경의 위험으로 정하고 에이전트의 승인은 사람 승인으로 치지 않는다.
- 리뷰어는 실제 사고를 일으킨 PR 모음으로 매일 평가하고, 에이전트 작성자와 에이전트 리뷰어가 밤새 50회 넘게 오간 사례 때문에 3회 뒤 접근 재고, 변경분만 재검토, 중복 지적 금지 규칙을 뒀다.
- 이 노트는 X 글 전체와 원본 블로그 글(10월 15일)을 읽고 대조했다. 모든 수치는 Anthropic 자사 팀의 보고이며 외부 검증은 없다.

## 글에 대하여

Addy Osmani가 2026년 10월 26일 X Article로 올린 글이다. 프로필은 Claude Code(Anthropic)로 표시되고 조회수는 약 150만 회로 보인다(수집 시점 기준). 글 끝에는 "원래 글을 다시 쓴 것이며 Pangram로 확인했다"는 문장이 있다. 원본은 claude.dev 블로그의 같은 제목 글(10월 15일, 공저 Addy Osmani, Morgan Westlee Lunt, Qing Wang)이다. 두 글의 본문을 모두 읽었다. 숫자는 두 글이 일치한다(하루 병합 변경 약 2,500건에서 3만 건 넘게, 내부 PR의 실질 코멘트 비율 16%에서 54%, 지적의 약 59%가 처음부터 있던 코드). 이 블로그의 [리뷰 에이전트의 반복을 끝내는 운영 규칙 노트](https://raphael-shin.github.io/jungseob-blog/posts/review-agent-convergence/)는 원본의 수렴 부분만 다루었고 이 노트는 글 전체를 구조대로 정리한다. [Katz 하네스 노트](https://raphael-shin.github.io/jungseob-blog/posts/katz-is-the-agent-harness-dead/)와 [Lauren Tan 신뢰 곡선 노트](https://raphael-shin.github.io/jungseob-blog/posts/tan-trust-curve-verification-agents/)도 같은 검증 논의를 다룬다.

## 리뷰의 목적을 다시 정하다

글은 에이전트가 코드를 쓰면 변경량이 급증한다고 말한다. 모노레포에서는 하루 병합 변경이 5월 약 2,500건에서 9월 3만 건 넘게 늘었고 줄 단위 수작업 리뷰는 사실상 불가능해졌다. 코드 리뷰는 배포 전에 버그를 찾아 고치는 일과 코드베이스에 대한 공유된 이해를 만드는 일, 두 가지 목적이 있고 글은 앞쪽을 주로 다룬다. "누군가 코드를 읽었는가"를 "이 변경에서 무엇이 잘못될 수 있고, 어떤 검사(자동이든 사람이든)가 그것을 잡을 올바른 방법인가"의 부정확한 대용 지표로 본다. 이에 따라 리뷰 시점도 바뀌었다. 사후 점검이 아니라 쓰는 도중에 계속 도는 맞춤법 검사에 가깝고 사람이 보기 전에 Claude가 최소 한 번 검토하고 고친다.

사람의 시간은 이중 비용이다. 리뷰에 쓰는 시간뿐 아니라 나쁜 코드가 만든 버그를 고치는 시간도 센다. 앞쪽만 줄이고 뒤쪽을 줄이지 않으면 시간을 아낀 것이 아니라 옮긴 것이다. 팀은 PR당 사람 승인 횟수의 중앙값과 95분위, 사람 코멘트 수, PR이 사람을 기다리는 시간을 추적하고 되돌림과 사고율을 가드레일로 쓴다.

## 변경이 거치는 층

글은 여섯 겹의 검사와 롤백 장치가 있다고 쓰지만 본문 번호는 일곱 개다. 마지막 일곱 번째가 빠른 피드백과 롤백이다. 첫째는 PR 전 검증이다. 대부분의 리뷰가 PR 생성 전에 끝난다. Claude에게 완료를 선언하는 대신 실행 가능한 증거(테스트, 빌드, 디자인과 스크린샷 비교)를 보이게 하고 새 맥락의 하위 에이전트가 diff를 검토한다. 많은 사람이 PR 전에 버그 사냥, diff 축소, 종단 간 검증, UI 가이드 준수 점검 스킬을 돌린다. Claude Code의 창시자 Boris Cherny는 검증 과정이 결과 품질을 2~3배 높이는 가장 큰 열쇠일 것이라고 추정한다고 글은 전한다. 자동 리뷰어가 같은 문제를 반복해 지적하면 스킬, 린트 규칙, CLAUDE.md 같은 문서를 고쳐 근원을 막는다. CLAUDE.md는 프로젝트 설명 파일이고 REVIEW.md는 코드 소유자가 리뷰어에게 무엇이 중요한지 알리는 파일이다. 좋은 REVIEW.md는 프로젝트 실패를 정의하고 사소한 지적을 제한하고 무시할 경로를 정하고 파일과 줄 번호를 요구하며 문제 개수와 "문제 없음" 문장을 담은 요약을 요구한다.

둘째는 모든 PR의 AI 리뷰다. diff를 전체 코드베이스와 작성자가 밝힌 의도에 비춰 변경이 이슈를 해결하는지, 시스템에 맞는지, 다른 부분을 깨지 않는지 본다. 공개 제품 Code Review for Claude Code는 Team과 Enterprise 고객에게 제공되고 로컬용 가벼운 판은 `/code-review`다. 연구 미리보기 이후 내부 PR 중 실질 코멘트를 받은 비율이 16%에서 54%가 되었다. 지적은 여러 에이전트가 병렬로 찾고 별도 투표로 유효 여부를 가리고 스타일이나 정리에 불과한 것은 걸러서 중요, 사소, 기존 문제(작성자에게 불리하지 않게)로 표시한다. 모든 지적은 고치거나 이유를 달아 해소해야 하고 에이전트가 밤새 고쳐 두기도 한다. 셋째는 열린 지적이 있으면 병합할 수 없는 보안 리뷰다. 넷째는 린트, 타입, 모든 플랫폼 테스트, 빌드 같은 차단 검사이고 PR 템플릿은 어떻게 테스트했고 어떻게 되돌릴지를 묻는다.

다섯째는 위험에 따라 정해지는 사람 승인이다. 문서 수정과 자동 업데이터 변경은 위험이 다르다. 등급은 작성자가 아니라 변경으로 정하고 분류기가 위험을 판정하며 다른 분류기가 추가 승인이 필요한지 확인한다. 소유자가 민감하다고 표시한 경로와 CI 워크플로 파일은 항상 추가 승인이 필요하다. 신뢰 목록의 작성자만 완화된 요건을 받고 나머지는 두 번째 사람이 승인해야 한다. 에이전트 승인은 사람 승인으로 치지 않으며 에이전트가 쓴 PR에서는 그 에이전트의 운영자가 필수 리뷰어다. 승인은 커밋 하나에만 유효하다. 여섯째는 병합 큐(변경이 적용된 main에서 모든 검사 실행), 기능 플래그와 직원 우선 출시, latest 채널에서 stable 채널로의 단계 출시다. 일곱째는 빠른 피드백과 롤백이다. 플래그 뒤의 변경은 배포 없이 끌 수 있고 주간 당직이 있으며 사고 검토는 어느 층이 잡았어야 하는지 되짚는다. 되돌림이나 사고율에 따라 승인 요건을 조정하는 회로 차단기는 아직 없다고 인정한다.

## 리뷰어를 개선하는 법

팀은 사고를 평가 지표로 쓴다. 사고를 일으킨 PR과 후속 수정, 되돌림을 모으고 코드를 아는 엔지니어가 버그의 위치와 정확성을 확인하며 리뷰 시스템을 이 모음으로 매일 평가한다. 사고가 생길 때마다 모음에 추가되고 리뷰 시스템을 바꿀 때마다 전체에 다시 평가한다. 소음은 사람이 지적에 어떻게 반응하는지로 잰다. 고침, 거부, 의도된 동작이라 설명, 중요하지 않다고 판단의 네 가지로 분류하고 깨끗한 PR에 리뷰어를 돌려 해로운 변경을 유발할 지적을 얼마나 내는지도 본다. 우선순위는 첫째 실제 버그 탐지, 둘째 리뷰 횟수 감소다. 에이전트 작성자에게는 지적 하나가 새 커밋과 새 리뷰를 뜻하므로 사소한 지적 비용이 훨씬 크다.

리뷰는 수렴해야 한다. CLI 프로젝트의 한 PR은 작성 에이전트와 리뷰 에이전트가 밤새 50회 넘게 오갔고 수동으로 멈췄다. git blame으로 보니 계속 지적되던 것의 약 59%가 첫 리뷰 때부터 있던 코드였다. 새 버그가 아니라 오래된 버그를 조금씩 더 찾고 있었다. 팀은 3회 뒤 작성자에게 접근법 재고를 요청하고 초기 몇 회 이후에는 변경분만 재검토하며 버그 유형을 명시해 한 줄이 아니라 같은 부류를 모두 고치게 하고 이미 보고한 지적을 반복하지 않게 했다. 리뷰 에이전트는 밤마다 현재 코드를 점검해 오래된 버그도 미리 찾는다. 원본 블로그의 그림은 수렴 규칙 이후 첫 리뷰와 수정 라운드에서 통과한 비율이 65%에서 78%로, 다섯 번 이상 필요한 비율이 8.9%에서 1.5%로, 통과까지의 평균 리뷰 횟수가 2.08에서 1.32로 줄었다고 보인다. X 글에는 같은 그림이 이미지로만 있어 이 숫자는 본문에 없고 이 노트는 원본 블로그의 그림 설명으로 읽었다.

## 사람이 남는 일, 소유, 방향 전환

사람의 리뷰가 필수인 일은 다섯 가지다. 이것을 만들어야 하는가라는 비전과 취향의 결정, 결제와 자동 업데이터와 CI 워크플로 같은 위험한 코드 감사, 후속 규칙이 되는 아키텍처 검토, 증명(테스트 출력, 실행 명령, 스크린샷, 리뷰어 코멘트) 검증, 그리고 책임이다. 어떤 검사가 놓칠 것을 설명할 수 없다면 엄지 이모지를 요청하지 말고 진짜 리뷰를 받으라고 쓴다. 한 팀은 코드 리뷰 병목을 해결했다고 주장하면서도 팀 밖 변경은 사람이 검토해 무엇을 만들어야 하는지 확인한다.

코드베이스 이해를 어떻게 공유하느냐는 문제에 대한 공식 장치는 없다. 누구도 Claude Code 전체의 머릿속 모델을 갖고 있지 않고 그럴 필요도 없다는 입장이다. 바꾸려는 부분을 Claude에게 설명 문서로 만들게 하면 몇 분 만에 최신 설명을 얻고 일부는 그 영역을 시각화하는 작은 결과물도 만든다. 한 줄 문구 수정 같은 사소한 diff를 읽는 것보다 바꿀 모듈의 설명서를 만드는 편이 더 많이 배운다고 본다. 소유 원칙은 "병합한 사람이 책임진다"다. 작거나 중간 크기의 변경이 문제를 일으키면 병합한 사람이 고치며 작은 변경, 되돌릴 수 있는 구조(플래그, 단계 출시), 폭발 반경에 따른 기준, 텔레메트리와 내부 사용, 비난하지 않는 사고 검토가 이를 받친다. 에이전트로 일을 시작하는 비용이 싸서 방향 전환도 쉬우므로 스레드 초반에 잘못된 경로라고 부르는 것이 중요하다.

## 대조해서 확인한 점

글과 원본의 구조와 숫자는 일치한다. 이 노트가 직접 확인한 외부 자료는 Anthropic의 제품 문서와 보도다. Code Review는 Claude가 각 변경을 검토하고 지적을 검증해 인라인으로 남기는 Team과 Enterprise 플랜 기능이고 최근에는 연구 미리보기에서 정식 출시되었다는 Anthropic의 글이 있다. `/security-review` 명령과 GitHub Action도 Anthropic 문서와 저장소에 있다. Claude Code 코드의 약 90%를 Claude Code가 쓴다는 서술은 2026년 1월 Fortune이 Boris Cherny의 발언으로 보도했다.

확인하지 못한 것은 핵심 결과 수치의 원자료다. 병합 PR이 두 배 넘게 늘고 되돌림 비율이 40% 넘게 줄었다는 서술, 2,500건에서 3만 건 넘게라는 모노레포 수치, 16%에서 54%, 약 59%, 그리고 Boris Cherny의 2~3배 추정은 모두 Anthropic 내부 데이터나 발언이며 공개 자료로 재현할 수 없다. PR 수가 늘어난 이유가 품질 향상인지 작업량 증가인지, 되돌림 감소가 실제 품질 개선인지 되돌림을 피하는 행동 변화인지도 글만으로는 알 수 없다. 두 글은 한 팀이 한 기간에 한 환경에서 얻은 결과로 일반화되지 않는다.

## 읽을 때 유의할 점

첫째, 필자는 Code Review 제품을 파는 회사의 팀이다. 글은 운영 사례이면서 제품과 하네스 기능(CLAUDE.md, 스킬, 하위 에이전트, `/code-review`)의 사용 설명서 역할을 한다. 둘째, 지표를 되돌림과 사고율에 두지만 두 지표는 결함이 늦게 드러나는 경우나 사용자에게 보이지 않는 결함을 놓칠 수 있다. 셋째, 에이전트의 승인이 사람 승인으로 치지 않는다는 원칙과 일부 저위험 변경을 자동 병합하는 방향이 함께 있다. 글도 이 경계가 계속 바뀐다고 쓴다. 넷째, 코드 이해의 공유를 설명서 생성에 맡기는 접근은 설명서가 틀릴 위험에 대한 점검 방법이 제시되지 않는다. 다섯째, 글은 필자가 AI 문장 탐지기 Pangram로 확인한 재작성이라고 밝히는데, 이는 문장 출처 표시이지 내용 검증이 아니다. 여섯째, 일곱 층을 여섯 겹이라 쓴 불일치가 있다.

그래도 가져갈 질문은 선명하다. 우리 변경에서 무엇이 잘못될 수 있고 어떤 검사가 그것을 잡는가를 PR 유형별로 적어 본 적이 있는가, 에이전트 작성자와 에이전트 리뷰어가 수렴하도록 반복 횟수와 중복 지적의 상한을 두었는가, 리뷰어를 사고 모음으로 평가하고 있는가, 에이전트 승인과 사람 승인을 구분하는 규칙이 문서와 도구에 모두 있는가.
