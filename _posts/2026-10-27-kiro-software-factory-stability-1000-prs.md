## TL;DR

- Kiro Crew 팀은 읽지 않은 코드에도 사람이 책임질 수 있는가라는 질문에, 확신은 예전에도 모든 줄을 읽는 데서 오지 않았고 테스트에서 왔다고 답한다. 파이프라인은 모든 변경을 매번 같은 방식으로 시험할 수 있으므로 자동 검사를 자기 눈으로 읽는 것보다 더 믿을 수 있게 만드는 것이 목표이고, 시간의 약 20%를 자동화 인프라에 쓴다.
- 사람이 PR을 "아는" 방식도 바뀌었다. 요약을 에이전트에게 물어 증거(스크린샷, 영상, 데이터)와 리뷰 기록으로 확인하며, 책임지는 대상은 모든 변경이 같은 리뷰와 테스트와 관문을 거쳤다는 기록이다.
- 품질은 다섯 단계로 올랐다. 사람 리뷰는 하루도 못 갔고, 이후 자동 리뷰어, 심각도 등급과 두 번째 리뷰어, 오픈소스 CI와 역할별 리뷰어, 하나의 준비 상태 신호로 도는 자동 수정 루프, 병합 뒤 검사가 차례로 붙었다.
- 가장 큰 낭비는 과잉 설계다. 리뷰어가 짚은 경계 사례마다 에이전트가 장치를 더해 열 줄짜리 수정이 하위 시스템이 되므로, 회고와 비례 검사와 지휘 에이전트를 뒀다.
- 노트는 글 전체를 읽고 공개 저장소의 워크플로 이름으로 일부를 대조했다. 모든 수치는 자사 팀의 보고이며 외부 검증은 없다.

## 글에 대하여

Kiro 블로그가 2026년 10월 26일에 올린 글이다. 본문 전체를 읽었고 그림 네 장(단계별 검사, 포크 격리, PR 준비 상태 신호, 과잉 설계 회고)은 이미지라 읽지 못했으며 캡션만 확인했다. 앞선 글 「How we built a software factory with Kiro Crew to merge 1,000 PRs in a week」는 풀타임 엔지니어 세 명이 7일에 PR 1,000개를 병합했고(하루 120개 이상), 약 500명의 커뮤니티 기여자가 함께한다고 썼다. 이 글은 그 뒤에 가장 많이 받은 질문에 대한 답이다. Kiro는 AWS의 에이전트형 개발 도구이며 Kiro Crew는 그 위의 오픈소스 프로젝트다. 이 블로그의 [Claude Code 팀 코드 리뷰 노트](https://raphael-shin.github.io/jungseob-blog/posts/osmani-claude-code-team-code-review/)와 [리뷰 에이전트의 반복을 끝내는 운영 규칙 노트](https://raphael-shin.github.io/jungseob-blog/posts/review-agent-convergence/)가 같은 문제를 다른 팀에서 다룬다.

## 확신은 어디서 오는가

글은 에이전트가 변경을 몇 분에 쓰므로 속도는 쉬운 부분이고 읽지 않은 변경이 맞고 안전하며 병합할 가치가 있음을 아는 것이 어렵다고 말한다. AI 이전에도 확신은 리뷰어가 모든 if와 else를 읽고 승인하는 데서만 오지 않았다. 수동 리뷰는 필요했지만 충분하지 않았고 그 뒤에 더 많은 테스트와 실제나 모의 환경에서의 수동 실행이 있었다. 사람의 테스트는 해피 패스나 뻔한 경계 사례만 시험하므로, 세 엔지니어 중 한 명이 전에 운영한 서비스도 수동 테스트 뒤 릴리스 파이프라인의 자동 테스트를 거쳤다. 그래서 질문은 바뀐다. 읽는 것보다 더 믿을 만한 자동 테스트와 검사를 어떻게 만드는가다. 사람은 모든 변경을 읽을 수 없지만 파이프라인은 모두를 같은 방식으로 매번 시험한다. 팀은 시간의 약 20%를 자동화를 늘리는 인프라에 쓴다.

"PR을 안다"의 뜻도 달라진다. PR 번호를 받으면 diff를 외우는 대신 크루에게 물어 코드와 테스트 증거와 리뷰 기록에 근거한 쉬운 말 요약을 1분 안에 받는다. 리뷰 기록은 CI가 모든 PR에 남기는 흔적으로, 각 리뷰어의 지적과 그것을 고치거나 증거로 반박한 과정, 모든 검사 결과, 최종 준비 상태 판정이다. 팀이 책임지는 대상은 이 기록이다. 그래서 품질은 CI/CD와 테스트 문제가 되고 테스트 커버리지를 90% 위로 올리고 100%를 목표로 하며 회귀 방지를 두고 에이전트가 실제 앱을 사용자처럼 조작하는 에이전트 테스트를 더했다.

## 다섯 단계

3월 초 팀은 모든 변경을 손으로 리뷰하려 했고 하루도 못 갔다. 1단계는 사내 빌드와 리뷰 시스템의 자동 리뷰 봇이었고 모든 AI 코멘트를 우선순위와 상관없이 해소해야 병합한다는 엄격한 규칙이 있었다. 세 가지 문제가 곧 나왔다. 종단 간 테스트가 없어 코멘트를 다 해소하고도 앱이 깨질 수 있었고 사람이 직접 테스트해 스크린샷을 붙였으며 놓친 것은 핫픽스로 돌아왔다. 코멘트가 라운드마다 새로 쏟아져 작은 변경이 하루치 왕복이 되었고 고칠 때마다 새 코드가 생겨 새 코멘트를 불렀다. 리뷰어를 제어하기 어려워 규칙이 발동했는지와 이유를 볼 수 없었다. 교훈은 엄격한 규칙이 완전하고 조정 가능한 피드백과 실제 제품 종단 간 시험을 전제로 한다는 것이다.

2단계는 심각도 등급과 두 번째 리뷰어다. 차단 지적과 실제 우려는 같은 PR에서 고치고 사소한 지적과 스타일은 후속 이슈로 넘긴다. 이는 기준을 낮추는 것처럼 보이지만 루프를 끊지는 못해서, 이미 있는 봇 옆에 자체 리뷰 에이전트를 두었다. 여러 번에 걸쳐 변경을 훑되 앞선 패스가 찾은 것은 건너뛰게 해 한 라운드에서 실제 코멘트를 모두 내놓게 한다. 이 시기에 AI 리뷰어가 사람이 보통 잡는 것보다 깊은 문제를 찾는다는 데 놀랐고 이것이 줄 단위 수동 리뷰를 포기하게 만든 계기라고 한다. 그러나 사람이 매 라운드 수정을 밀어야 했고 몇 번 돌다 기여를 그만둔 사람이 있어서 로컬에서 같은 테스트와 AI 리뷰를 돌리는 내장 스킬을 냈다.

3단계는 GitHub로 옮겨 오픈소스가 되면서 얻은 CI다. 모든 PR이 빌드, 단위 테스트, 종단 간 테스트를 자동으로 받고 내장 테스트 포드가 격리 환경에서 코드를 돌려 관련 기능의 스크린샷과 영상을 PR에 붙인다. 리뷰어는 역할별로 나뉜다. 설계 리뷰어는 구조에 맞는지와 더 단순한 해법이 있는지, 제1원리 리뷰어는 근본 원인을 고치는지와 사용자가 정말 필요로 하는지, UX 리뷰어는 사용자에게 보이는 변경을 본다. 모델 계열도 섞는데 자기 계열의 코드를 보는 모델은 같은 사각지대를 갖기 때문이다. 테스트는 단위, 통합, 프런트엔드, 데스크톱 패키징, 번들 크기 예산, 커버리지 하한, 종단 간으로 나뉘며 에이전트는 통합에서 가장 자주 틀린다고 한다. 차단의 정의도 하나다. 차단 지적은 구체적 위치, 인용 증거, 발동 조건, 결과를 가져야 하고 무엇이 어떻게 깨지는지 말하지 못하면 권고다. 설계 우려는 되돌릴 수 없는 결정(일방통행 문)을 설명할 때만 차단이다. 포크에서 오는 코드를 신뢰하지 않는 경계도 두었다. 포크의 코드와 신뢰하는 리뷰 워크플로를 서로 반대편에서 돌린다.

4단계는 루프를 닫는 것이다. 3단계에서도 사람이 CI 실패 내용과 AI 리뷰 제안을 크루에 복사해 고치게 했다. 팀은 AI 제안을 믿어야 할 것이 아니라 더 깊은 로컬 분석의 입력으로 대한다. 그래서 내장 스킬 prepare-pr이 PR이 녹색이 될 때까지 루프를 돈다. 80개가 넘는 검사를 매번 훑는 것은 비싸므로 모든 CI/CD 결과를 하나의 판정으로 모으는 PR 준비 상태 검사를 만들었다. 이 판정은 아무것도 빨갛지 않은 상태가 아니라 기대한 모든 액션이 실행되어 통과한 상태여야 한다. 새 PR에서는 "실패 없음"과 "아직 아무것도 안 돌았음"이 같아 보이기 때문이다. 스킬은 실패한 액션과 리뷰 지적을 가져와 진짜인 것은 고치고 아닌 것은 증거로 답한 뒤 다시 푸시하고 판정이 녹색이면 멈춘다. 사람과 에이전트가 "끝"의 같은 정의를 공유한다. 승인 클릭도 PR이 많으면 시간이 드는 일이라, 먼저 PR을 등급으로 나눠 단순 등급은 자동 승인과 병합하고 나머지는 AI가 리뷰 초안을 써 준다. 에이전트는 PR 설명을 고정 템플릿과 쉬운 말과 도식으로 매번 다시 써서 사람이 몇 초에 이해하게 하고 설명이 코드와 엄밀히 일치하는지 CI가 검사한다.

5단계는 병합 뒤다. 리뷰가 놓치는 버그가 있어 병합이 끝이 아니다. 릴리스 전에는 에이전트가 설치한 실제 앱으로 세션 시작, 작업 실행, 메모리 사용, 작업 예약 같은 핵심 흐름을 조작하는 시험을 한다. 보안은 병합 코드에 대한 매시간 준수 검사, 내부 보안 에이전트의 일일 스캔, 실제로 보안 가드레일을 뚫어 보는 상시 보안 봇, 외부 제보를 받는 관리형 보안 수신함의 여러 층이다. 주기적 리팩터링으로 큰 파일과 중복과 죽은 코드를 정리하고 최신 모델이 더 나은 코드를 쓰게 한다. 검사 자체의 확장도 문제였다. 하루 100개 정도의 PR에 수십 개 자동 검사를 돌리자 GitHub 속도 제한에 걸려 값싼 검사를 먼저 돌리는 빠른 관문을 두었고 리뷰를 AWS CodeCommit으로 옮기고 일부 테스트를 자체 호스트로 옮겼다. 개발 과정도 바꿨다. 코딩이 쉬우면 기능에 예라고 하기도 쉬워서, 요청을 먼저 분류해 단순한 것은 바로 만들고 중간은 한 쪽 설계, 복잡한 것은 팀 전체 리뷰를 받는다. 가장 비싼 버그는 사용자가 필요 없던 기능에서 나온다는 판단이다.

## 과잉 설계와 보안 수정

자동 수정 루프가 돌기 시작하면 가장 큰 낭비는 과잉 설계다. 리뷰어가 경계 사례를 짚으면 에이전트가 장치를 더하고 다음 리뷰가 그 장치의 경계 사례를 짚어 또 더한다. 다섯 라운드 뒤 열 줄 수정이 필요 없는 작은 하위 시스템이 된다. 팀은 prepare-pr과 CI에 회고를 넣었다. 같은 영역에서 여러 라운드가 돌면 루프가 자기 이력, 곧 무엇이 바뀌었고 리뷰어가 무엇을 말했고 변경이 수렴하지 않고 커지는지를 돌아보고 중단, 되돌림, 더 단순한 접근을 권한다. 먼저 하는 일은 더 이상 필요 없는 장치를 빼는 것이다. 또 모든 제안 수정의 비례를 본다. 지적이 옳아도 요구가 과할 수 있으므로 수정은 PR 설명이 말하는 문제를 푸는 직접적 코드 변경이어야 하고 더 큰 것은 후속으로 넘긴다. 예외는 도달 가능한 크래시, 보안 구멍, 데이터 손실이다. 회고는 새 문제도 만들었다. 코딩 전략 변경을 사람이 결정해야 한다는 점인데 권고가 대개 명확해도 질문이 자동화를 멈춘다. 그래서 두 번째 에이전트인 지휘자(conductor)가 회고의 권고를 읽고 먼저 판단하며 결정하지 못할 때만 사람을 부른다.

보안도 같다. AI는 보안에 열성적이어서 진짜 지적 하나에 방어층 세 개와 새 설정 플래그와 실행되지 않는 검증 단계를 더한다. 글은 두 사례를 든다. 라운드마다 에이전트 샌드박스를 조금씩 조이다가 빌드나 파일 읽기 같은 일상 작업이 실패하게 된 사례, 그리고 실행 파일을 자기 폴더에 복사해 잠가 둠으로써 이미 컴퓨터를 장악한 공격자의 교체를 막으려는 제안이다. 후자는 깨질 수 있는 복사와 권한 검사와 갱신 경로를 더하면서 아주 드문 경우만 막는다. 그래서 규칙은 사용자가 닿을 수 있는 실제 문제를 가장 작은 코드 변경으로 고치는 것이다.

## 바로 적용할 일곱 가지

글의 제안은 이렇다. 리뷰 코멘트를 등급으로 나누고 한 라운드에 모든 코멘트를 요구하고(느리지만 완전한 리뷰어가 조금씩 흘리는 리뷰어보다 싸다), 역할과 모델 계열로 리뷰어를 나누며 모든 검사를 "모두 돌아 통과"를 뜻하는 하나의 준비 상태 신호로 압축하고 릴리스 전에 실제 흐름을 조작하는 단계로 제품 전체를 시험하며 에이전트 루프에 회고를 넣고 두 번째 에이전트가 먼저 판단하게 하며 보안 수정을 합리적으로 작게 유지하라는 것이다. 워크플로, 리뷰 프롬프트, prepare-pr 스킬이 공개 저장소에 있다고 한다.

## 대조해서 확인한 점

공개 저장소(kirodotdev/KiroCrew)는 Apache-2.0 라이선스이고 2026년 7월 16일에 생성되었으며 별 약 4,600개, 마지막 푸시는 10월 27일이다. `.github/workflows`에는 design-review, first-principles-review, fork-ux-review, fork-opus-review, fork-gpt-review, claude-review, codex-review, fast-gate, pr-readiness, pr-readiness-sweep, merge-queue-readiness, merged-readiness-audit, nightly, gui-user-test, codeql, dependency-review, fork-workflow-guard 같은 파일이 있어 글이 말하는 역할별 리뷰어와 준비 상태 검사, 빠른 관문, 포크 격리, 병합 뒤 감사의 존재와 맞는다. prepare-pr 스킬 파일은 이 노트가 찾지 못했다(스킬 위치를 탐색하지 않았다). 앞선 글의 수치(풀타임 세 명, 7일 PR 1,000개, 하루 120개 이상, 기여자 약 500명)는 두 글이 일치한다.

확인하지 못한 것은 핵심 수치의 원자료다. 1,000개 PR 병합, 테스트 커버리지 90% 이상, 시간의 20%, 80개가 넘는 검사, 하루 100개 PR은 팀의 보고다. 병합된 PR의 되돌림률, 사고율, 병합 뒤 발견된 버그의 수는 글에 없다. 따라서 이 파이프라인이 실제로 "안정적"이라는 증거는 서술적이다. 글의 제목이 약속한 안정성의 정량 지표가 제시되지 않았다.

## 읽을 때 유의할 점

첫째, 필자는 에이전트 개발 도구와 이 프로젝트를 만드는 팀이다. 글은 사례이자 제품 홍보이며 AWS의 다른 서비스(CodeCommit)를 쓴 사실도 그 맥락이다. 둘째, 주 1,000개 PR이라는 수치는 PR 수이며 변경 크기, 가치, 되돌림은 보여 주지 않는다. 앞선 글에서도 PR 수를 성과 지표로 삼았다. 셋째, 사람이 읽지 않아도 된다는 결론은 테스트와 리뷰 기록이 충분하다는 가정에 기댄다. 테스트 자체가 틀리거나 빠뜨리는 경우, 에이전트가 쓴 테스트가 에이전트가 쓴 코드를 통과하도록 맞춰지는 위험을 글은 다루지 않는다. 넷째, 자동 승인과 병합 등급의 분류 기준과 오분류율은 공개되지 않았다. 다섯째, 지휘 에이전트가 먼저 판단한다는 설계에서 사람이 개입하지 못한 결정의 오류율은 제시되지 않았다. 여섯째, 병합 후 감시의 많은 층이 있지만 각 층이 실제로 잡은 사고의 수는 없다.

그래도 가져갈 질문은 선명하다. 우리 PR의 "끝"을 하나의 신호로 정의했는가, 그 신호가 "모두 통과"와 "아직 안 돌았음"을 구별하는가, 자동 수정 루프에 회고와 비례 검사가 있는가, 리뷰어마다 차단 지적의 증거 기준이 같은가, 보안 수정이 사용자가 닿는 문제 대신 가능한 모든 공격을 막으려고 커지고 있지 않은가.
