## TL;DR

- 글의 문제 설정은 로컬 에이전트의 모든 명령이 사용자의 권한으로 돌고, 에이전트가 고른 명령과 사용자가 직접 친 명령을 운영체제 수준에서 가르는 것이 없다는 것이다. 지금까지의 통제 수단은 사람의 주의였고, 에이전트를 여럿 돌리거나 긴 작업을 맡기면 승인 피로 때문에 이 통제가 가장 먼저 무너진다.
- 해법은 에이전트가 실행하는 명령과 그 자식 프로세스만 운영체제가 강제하는 샌드박스에 넣는 것이다. 쓰기는 프로젝트 디렉터리와 임시 공간으로 가두고, 흔한 자격 증명 경로의 읽기는 커널이 거부하며, 네트워크는 도메인을 거르는 로컬 프록시를 거친다.
- 설계의 핵심은 에이전트 자신을 샌드박스 밖에 둔 것이다. 모델을 부르는 머신 신원이 샌드박스에 들어가지 않고, 로컬 MCP 서버는 그대로 돌며, 세션 중에도 켜고 끌 수 있다. 같은 permissions.yaml 정책이 도구 호출에서 한 번, 커널 시스템 호출에서 한 번 집행된다.
- 기본값은 꺼짐이고 승인 요구도 없애지 않는다. 샌드박스는 승인된 명령이 할 수 있는 일을 줄일 뿐이며, 공식 문서도 완전한 격리를 보장하지 않으니 계속 명령을 검토하라고 쓴다.
- 공식 문서와 변경 기록이 글의 지원 환경과 버전을 확인해 주고, 한 일본 블로그의 Linux 실험이 설치 스크립트의 쓰기와 전송이 막히는 것을 독립적으로 재현했다. 다만 의도적 우회 공격에 대한 검증은 없다.

## 글에 대하여

Kiro 블로그에 2026년 10월 14일 게시된 글로, 필자는 엔지니어링의 Mike Landi와 제품 책임자 Doug Clauson이다. 영어 본문 약 7천 자를 전부 읽었고 설정 파일 예시와 permissions.yaml 예시는 코드 블록이라 수집되지 않았다. 대신 공식 문서와 변경 기록, 제3자 실험으로 대조했다. 이 블로그의 [Kiro 소프트웨어 공장 안정성 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-software-factory-stability-1000-prs/)와 [Lean 하네스 증명 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-proves-harness-properties-in-lean/)가 같은 제품의 다른 면을 다룬다.

## 왜 에이전트의 주의가 병목인가

로컬에서 도는 에이전트는 사용자와 같은 파일 시스템과 도구 체인과 로컬호스트 서비스를 보므로 프로젝트를 멀리서 추측하지 않고 직접 빌드하고 테스트한다. 대가는 에이전트가 실행하는 모든 명령이 사용자의 권한을 갖는다는 점이다. 전체 파일 시스템과 전체 네트워크 접근이 열려 있고 에이전트가 고른 명령과 사용자가 직접 입력한 명령을 운영체제에서 구분하는 장치가 없다. 이를 막아 온 것은 세션을 지켜보고 명령을 읽고 승인하는 사용자의 주의다.

에이전트가 유능해지고 병렬 세션이 늘면 사용자의 주의가 시스템의 병목이 된다. 작업이 길수록 명령이 많아지고 명령이 많을수록 승인 피로가 생기며 두 번째 세션을 시작하거나 리팩터링 중 자리를 비우면 명령이 막히거나 사용자가 더는 읽지 않게 된다. 위험은 악의가 필요하지 않다. 잘못된 도구 호출 하나나 잘못 이해한 의도가 실제 사고가 될 수 있고 가능한 동작의 폭이 넓었다. 글의 예는 Kiro의 신뢰 모델이 에이전트의 read_file 도구가 ~/.aws와 ~/.ssh를 읽는 것을 이미 막고 있지만 끈질긴 에이전트가 셸로 스크립트를 돌려 같은 파일을 읽을 수 있다는 것이다. 요청은 막혔는데 에이전트가 다른 길을 찾았다. 클라우드 샌드박스는 에이전트를 격리 환경에서 돌리는 것으로 답했지만 데이터 상주 규칙이나 VPN 뒤의 로컬호스트 서비스, Xcode가 필요한 iOS 빌드처럼 로컬에 남아야 하는 일이 많다.

## 동작 방식과 설계

로컬 샌드박싱에서는 에이전트가 여전히 네이티브로 돌고 사용자를 대신해 실행하는 명령이 커널이 집행하는 샌드박스를 거친다. 구현은 macOS의 Seatbelt, Linux의 bubblewrap, Windows의 AppContainer다. 이 제한은 Kiro의 도구 호출 권한 검사에 더해 운영체제가 집행한다. 기본 정책은 쓰기를 프로젝트 디렉터리와 임시 공간으로 가두고 흔한 자격 증명 경로의 읽기를 커널에서 거부한다. 에이전트가 ~/.ssh/id_rsa를 요청하면 판단 없이 거부되고 read_file이든 셸 한 줄이든 읽기용 스크립트든 같은 거부가 적용된다. 네트워크는 도메인으로 거르는 로컬 프록시를 통과해야 하며 이는 클라우드 샌드박스가 이미 쓰는 모델이고 패키지 레지스트리 같은 승인된 서비스만 닿는다.

에이전트 자체를 샌드박스 밖에 둔 것이 의도적 결정이다. 제한되는 것은 에이전트가 실행하는 명령뿐이므로, 세션 중에 샌드박싱을 켜거나 끄고 정책을 바꿔도 다음 명령을 감싸는 방식만 바뀌어 세션을 다시 시작할 필요가 없다. 여기서 세 가지가 따라온다. 에이전트가 모델을 부르고 Kiro 백엔드에 닿을 때 쓰는 머신 신원이 샌드박스에 들어가지 않아, 샌드박스 안의 프로세스가 폭주해도 그 신원으로 외부에 호출하지 못한다. 로컬 MCP 서버는 호스트 네이티브 프로세스로 그대로 돌고 원하면 샌드박스를 거치게 할 수도 있다. 그리고 전통적 의미의 샌드박스가 없고 제한된 자식 프로세스만 있으므로, 주입할 대상이 없고 첫 명령 전에 띄울 컨테이너나 이미지나 VM도 없다.

## 켜는 법과 정책 모양

샌드박싱은 현재 기본값이 꺼짐이다. sandbox.json으로 켜며 전역 기본값은 ~/.kiro/settings에, 프로젝트 재정의는 프로젝트 루트의 .kiro/settings에 둔다. 파일을 고치지 않고도 켤 수 있다. Kiro CLI에서는 로컬 세션에서 /sandbox on을 실행하거나 /sandbox로 전역과 프로젝트 범위, 네트워크 모드를 고르고 IDE에서는 명령 팔레트의 사용자 샌드박스 설정 명령을 실행하면 상태 표시줄에 명령 샌드박스 활성이 뜬다. Windows에서는 한 번의 관리자 설정이 먼저 필요하다. 기본 정책은 프로젝트 디렉터리 쓰기 가능, 흔한 자격 증명 경로 거부, 로컬 프록시 경유 네트워크다.

더 세밀하게 고르려면 이미 도구 권한을 다스리는 permissions.yaml에 규칙을 더한다. 글은 두 번째 권한 체계를 만들지 않는다고 강조한다. 같은 fs_read, fs_write, 네트워크 능력 규칙이 도구 경계에서만이 아니라 운영체제 커널에서도 집행된다. ~/.ssh/id_rsa 읽기를 거부하는 규칙은 에이전트가 정중하게 요청하는 도구 호출에서 한 번, 운영체제가 실제 시스템 호출을 보는 곳에서 한 번 작동한다. 도구 호출 검사는 필요하지만 정책 엔진이 아는 도구를 거치는 요청만 잡으므로 충분하지 않고 커널 검사는 파이썬 스크립트 우회까지 모두 잡는다. 정책을 기존에서 읽으므로 관리자, 사용자, 워크스페이스, 에이전트, 세션 범위가 모두 이어진다.

글의 질의응답은 짧다. 기본 상태는 꺼짐이고 지원은 macOS가 Seatbelt, Linux가 bubblewrap(socat과 함께 배포판 패키지로 설치), Windows가 AppContainer다. 승인 요구는 없어지지 않으며 샌드박스는 승인된 명령이 할 수 있는 일을 제한한다. Kiro IDE 1.3 이상, Kiro CLI 2.31 이상(로컬 V3 세션)에서 쓴다.

## 대조해서 확인한 점

공식 문서(Local command sandbox)는 글의 설명과 같다. 샌드박스는 에이전트 하네스가 실행하는 셸 명령과 모든 자식 프로세스를 감싸고 하네스와 모델과의 대화와 내장 파일 도구와 원격 MCP 서버는 밖에 있으며 내장 파일 도구는 권한 규칙이 계속 통제한다. 로컬 세션에만 적용되고 클라우드 세션은 관리형 클라우드 샌드박스를 쓴다. 지원은 IDE 1.3 이상과 CLI 2.31 이상의 로컬 V3 세션이고 기본값은 꺼짐이다. macOS는 별도 설치가 필요 없고 Linux는 bubblewrap을 직접 설치해야 하며 일부 네트워크 모드는 socat도 필요하다. Windows는 일부 모드에 한 번의 관리자 설정이 필요하다. 문서도 샌드박스가 완전한 격리를 보장하지 않으며 거부 규칙을 계속 두라고 쓴다.

변경 기록으로는 CLI 2.31(2026-10-13)과 IDE 1.3.0(같은 날)이 로컬 명령 샌드박스를 내놓았다. 두 기록 모두 네트워크를 차단, 일반 개발 호스트로 제한, 개방 중에서 고르게 하고 로컬 stdio MCP 서버도 같은 샌드박스에 넣을 수 있다고 쓰며 에이전트와 내장 파일 도구와 원격 MCP 서버는 밖에 남는다고 밝힌다. CLI 변경 기록은 /autonomous on이 기본 에이전트로 바꾸고 로컬 샌드박스를 먼저 켠다고 쓴다. 즉 승인 없이 일하는 자율 모드의 안전장치로 샌드박스가 쓰인다.

독립적인 실험으로 한 일본 개발 블로그가 Kiro CLI 2.31.0을 Linux(bubblewrap 0.12.0)에서 시험했다. 홈 디렉터리에 쓰고 로컬 포트로 데이터를 보내려는 더미 패키지를 설치하게 했더니, 샌드박스가 없으면 쓰기와 전송이 모두 성공하고 DEFAULT_BLOCKED에서는 둘 다 막혔다. DEFAULT_ALLOWED에서는 전송은 성공하고 쓰기만 막혔다. 로컬 MCP 서버는 샌드박스 설정에서 MCP 래핑을 켜기 전에는 쓰기와 연결과 이름 해석이 모두 성공했고 켠 뒤에는 모두 막혔다. /autonomous on은 sandbox.json이 없어도 샌드박스를 활성화했다. Linux에서 COMMON_DEPENDENCIES는 socat이 없으면 어느 목적지에도 닿지 않았다. 이는 글의 서술과 공식 문서의 필수 조건 설명과 어긋나지 않는다.

확인하지 못한 것은 설정 파일과 permissions.yaml의 예시 코드 전체, Windows AppContainer와 macOS Seatbelt에서의 동작, 의도적으로 샌드박스를 회피하려는 공격(예를 들어 허용된 도구 안의 취약점이나 허용된 호스트를 통한 유출)에 대한 견고함, 사용자가 쓰는 도구 체인 중 샌드박스 때문에 깨지는 경우의 비율이다. 글은 성능 영향이나 호환성 수치를 제시하지 않는다.

## 읽을 때 유의할 점

첫째, 이 기능은 기본값이 꺼짐이다. 켜지 않으면 아무 것도 달라지지 않는다. 둘째, 샌드박스는 에이전트의 모든 것을 가두지 않는다. 에이전트 하네스와 내장 파일 도구와 원격 MCP 서버는 밖에 있고 이들은 권한 규칙과 별개로 다뤄야 한다. 셋째, 네트워크 허용 목록은 데이터 유출 경로를 줄일 뿐 허용된 호스트를 통한 유출을 막지 못하며 이는 글이 다루지 않는 한계다. 넷째, 자격 증명 경로 거부는 흔한 경로 목록에 기대므로, 기본 목록에 없는 비밀 파일은 정책에 직접 넣어야 한다. 다섯째, 제품 회사의 발표이고 독립 검증은 일부 시나리오에 한정된 제3자 실험뿐이다.

가져갈 질문은 선명하다. 내가 쓰는 에이전트에서 도구 호출 검사와 운영체제 수준 검사가 같은 정책을 읽는가, 자율 모드를 쓰기 전에 어떤 안전장치가 먼저 켜지는가, 샌드박스 밖에 남는 구성 요소(에이전트, 파일 도구, 원격 MCP)는 어떻게 통제하는가, 자격 증명이 기본 경로 목록 밖에 있지는 않은가.
