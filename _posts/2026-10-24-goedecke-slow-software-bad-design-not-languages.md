## TL;DR

- Sean Goedecke는 AI가 소프트웨어를 빠르게 만들 것이라며 C나 Rust로 다시 쓰라고 시키는 흐름이 진지한 최적화가 아니라고 본다. 대부분의 프로그램은 언어 속도가 아니라 I/O와 설계가 성능을 정한다는 것이다.
- 근거는 세 가지다. CRUD 요청 시간의 절반이 DB 대기라면 언어를 바꿔도 이론상 2배, 실제로는 1.5배 안팎이 한계이고, 느린 언어는 이미 C로 짠 라이브러리에 무거운 일을 넘기며, 필자가 낸 큰 개선은 거의 전부 일을 덜 하도록 바꾼 재설계였다.
- 실무 처방은 에이전트에게 프로파일링, 핫스팟 식별, 설계 변경 제안을 시키는 것이다. 정말 CPU에 묶인 구간이 남을 때만 그 부분을 빠른 언어로 다시 쓴다.
- 대조해 보면 암달 법칙과 Cantrill의 측정은 주장과 맞고, 글이 덧붙인 편집 노트가 가장 큰 약점을 스스로 밝힌다. "CRUD는 I/O 바운드"가 필자의 Ruby 플레임그래프 경험에 근거한 경험적 주장이며 댓글 다수가 반대한다는 것이다.
- 이 노트는 본문 전체와 편집 노트, 인용된 Cantrill 글과 tokenizer 저장소를 읽고 대조했다. 퍼센트 수치는 모두 필자의 경험적 추정이다.

## 글에 대하여

Sean Goedecke가 2026년 10월 23일에 자기 블로그에 올린 글이다. 소개 문장이 논지를 모두 말한다. AI가 더 빠른 언어로 다시 써서 소프트웨어를 빠르게 할 것이라고들 하지만 대체로 사실이 아니며 대부분의 프로그램은 C나 Rust로 다시 써도 의미 있게 빨라지지 않는다는 것이다. 구성은 I/O 바운드, 느린 언어의 위임, 재설계, 결론, 그리고 Lobsters 댓글에 대한 편집 노트다. 이 노트는 본문과 각주 네 개, 편집 노트를 모두 읽었다. 글의 길이는 짧지만 AI 에이전트에게 무엇을 시킬지에 관한 실무 지침이라서 이 블로그의 [Katz 하네스 노트](https://raphael-shin.github.io/jungseob-blog/posts/katz-is-the-agent-harness-dead/)처럼 AI 활용의 방향을 다룬 글과 함께 읽을 만하다.

## 논증 하나: 대부분은 I/O에 묶여 있다

필자는 DB가 있는 단순한 CRUD 웹사이트를 예로 든다. 요청 시간의 50%를 쿼리가 쓴다고 하면(현재 사용자, 요청된 레코드, 멤버십과 설정 조회 등), 사이트 전체를 C로 다시 써도 나머지 50%만 빨라진다. 이는 속도 향상의 상한을 정하는 암달 법칙으로, 이상적으로 2배, 실제로는 1.5배 안팎이다. 대부분의 실제 프로그램은 데이터를 입출력하며 기다리는 I/O 바운드이고 DB 말고도 외부 API 응답이나 디스크 읽기·쓰기를 기다린다. curl의 코드를 100배 빠르게 해도 curl은 시간을 네트워크 대기에 쓰므로 알아채지 못한다는 예도 나온다. 첫 각주는 50%라는 비율이 인터프리터 언어에서 최소한 그럴듯한 범위라고 한다.

## 논증 둘: 느린 언어는 이미 빠른 언어에 일을 맡긴다

I/O가 아닌 일, 곧 위키가 마크다운을 HTML로 바꾸는 작업은 어떤가. 필자는 그런 응용이 cmark-gfm 같은 라이브러리를 부르므로 이미 빠른 언어가 처리한다고 답한다. Python이 느려도 기계 학습과 수학 같은 CPU 바운드 작업에서 경쟁력이 있는 것은 무거운 연산이 C 코드로 넘어가기 때문이다. GPU에서 행렬 곱을 하는 데 80%를 쓰는 프로그램은 C로 바꿔도 빨라지지 않는데, 행렬 곱이 이미 최적화된 C나 어셈블리에서 돌기 때문이다. 필자는 CPU 바운드 작업을 느린 언어로 하는 프로그램도 있다고 인정한다. 그런 프로그램은 대개 공학적 관심을 받지 못해 낮게 매달린 과일이 많지만 중요했다면 AI가 쉽게 만들기 전에 누군가 최적화했을 것이라는 반문이 붙는다. Actual Computer가 tiktoken을 어셈블리로 다시 써서 상당한 속도 향상을 낸 사례를 인정하되, 토큰화는 추론 시간의 일부일 뿐이라 분야를 바꾸지는 못한다고 본다. 네 번째 각주는 저장소가 4~23배라고 하는데 필자 노트북에서 약 5배였고 이 가속은 언어의 본질적 느림이 아니라 정규식 의존을 없앤 재설계에서 왔다고 덧붙인다.

## 논증 셋: 빨라지는 것은 재설계다

필자는 대부분의 소프트웨어가 가능한 것보다 훨씬 느리다고 보며 속도 향상이 AI의 도움 여부와 무관하게 크게 가능하다고 낙관한다. 다만 그 속도는 언어를 바꿔서가 아니라 설계를 바꿔서 나온다. 근거는 Bryan Cantrill의 2018년 글이다. C 프로그램을 Rust로 옮기려다 최적화된 C 설계가 Rust의 빌림 검사기와 맞지 않아, Cantrill은 포기하고 Rust로 순진하게 짰는데 20% 느려질 것이라는 예상과 달리 30% 빨랐다. 이유는 Rust의 표준 라이브러리가 이진 탐색 트리 대신 B-트리를 쓰는데 이것이 캐시 효율이 더 좋다는 데 있다. 필자는 이를 CPU 바운드 작업에서도 성능이 언어가 아닌 설계에 달려 있다는 증거로 읽는다.

필자 자신의 경험은 고수준 언어에서 큰 개선을 낸 사례로 정리된다. 느린 연산을 캐시한다(대개 외부 API 호출). 느린 연산을 요청 수명 밖의 백그라운드 작업으로 옮긴다. 순차 작업을 병렬로 바꾼다. 여러 SQL 쿼리를 하나로 줄여 N+1 문제를 없앤다. 느린 SQL을 빠른 SQL로 바꾼다. 불필요한 느린 연산을 건너뛴다(페이지가 있는 화면에서 현재 페이지 항목만 부가 데이터를 가져오는 식). 이 모두가 언어 속도와 무관하다. 오히려 느린 고수준 언어에서는 프로그램이 무엇을 하는지 한눈에 보여 N+1 쿼리나 API 호출을 작업으로 옮길 수 있음을 알아채기 쉽다는 것이 필자의 주장이다. 처음부터 웹 서버를 어셈블리로 짰다면 이를 알아채기 어려웠을 것이라는 대조도 든다.

## 결론과 편집 노트

결론은 지금 모두가 AI 에이전트에게 프로그램을 Rust, C, 어셈블리로 다시 쓰라고 시키는데 재미는 있어도 진지한 최적화가 아니라는 것이다. 에이전트에게는 프로파일링하고 핫스팟을 찾고 프로그램이 하는 일을 다시 설계하는 방법을 제안하라고 시켜야 한다. 정말 CPU에 묶여 더 줄일 수 없는 구간이 나오면 그 부분만 빠른 언어로 다시 쓴다. 이식성, 효율, 유지보수성 같은 다른 이유로 언어를 옮기는 것은 타당하지만 순수한 속도만 보면 설계에 집중하는 편이 낫다는 말이다.

편집 노트가 이 글에서 가장 정직한 부분이다. 많은 댓글이 CRUD가 I/O 바운드라는 데 반대하는 근거는 DB 쿼리가 약 5ms인데 응답은 약 500ms라는 것이다. 필자는 이것이 경험적 질문이며 자기 입장은 수천 개의 Ruby 플레임그래프를 본 경험에서 나온다고 답한다. 한 요청이 수십, 수백 개의 쿼리를 내거나 5ms보다 훨씬 느린 큰 쿼리와 내부 API 호출에 의존하는 일이 흔하다는 것이다. 다만 Rails 엔드포인트를 프로파일링한 곳이 몇 회사뿐이어서 다른 모놀리스는 다를 수 있다고 인정한다. 최상위 댓글은 브라우저 레이아웃 엔진, 3D 렌더러, 워드 프로세서, 신경망 같은 CPU 바운드 프로그램을 든다. 필자는 이들을 모두 합쳐도 CRUD 프로그램의 5% 정도일 것이며(틀릴 수 있다) 공개 토론의 50% 넘게 차지하는 것은 더 흥미로운 문제이기 때문이라고 본다. 언어가 생태계를 통해 성능을 쉽게 또는 어렵게 만든다는 지적에는 그것도 설계에 속한다고 답한다. 어떤 언어에서는 빠른 설계가 더 자연스러우며 언어를 바꿔 설계를 바꾸기 쉬워진다면 속도도 빨라질 수 있다.

## 대조해서 확인한 점

Cantrill의 후속 글(2018년 9월 28일, C와 Rust의 상대 성능)은 필자의 요약과 맞는다. 측정한 성능 카운터에서 Rust 버전의 CPU 사이클이 28.1% 줄었고 실행한 명령 수는 0.7%밖에 차이 나지 않았다. 사이클당 명령 수 지표(CPI)가 0.65에서 0.47로 내려갔다. 즉 같은 일을 하는 명령 수는 같고 메모리 접근 방식이 달랐다는 것이 Cantrill의 설명이다. 그는 이 차이를 BTreeSet이 더 효율적인 자료 구조이기 때문으로 읽으면서도 Rust 쪽 성능이 들쭉날쭉한 이유(해시 맵 확장 직전의 탐색 증가)를 따로 분석한다. 따라서 이 사례는 필자의 논지(설계가 지배한다)를 지지하되 "30% 빨랐다"는 한 프로그램의 측정이라는 점을 놓치면 안 된다. 이 노트는 Cantrill 글에서 30%라는 표현을 직접 찾지 못했고 사이클 28.1% 감소와 일치한다고 판단했다.

tokenizer 사례는 저장소의 설명과 맞는다. toks 저장소는 tiktoken보다 4~23배 빠르다고 주장하고 정규식 엔진 대신 SIMD 스캐너 템플릿으로 패턴을 처리한다고 쓴다. 필자의 각주(5배, 정규식 의존을 없앤 재설계)는 이 설명과 방향이 같다. 이 저장소의 수치는 개발사의 자체 벤치마크이며 이 노트가 재현하지 않았다. 암달 법칙은 표준 개념으로 필자의 계산(50% → 최대 2배)과 맞는다.

## 읽을 때 유의할 점

첫째, 핵심 전제인 "대부분의 프로그램은 I/O 바운드"는 필자도 인정하듯 경험적이며 반례가 있다. 직무와 도메인에 따라 다르다. 둘째, 50%, 1.5배, 5% 같은 수치는 설명용 추정이다. 셋째, 필자는 AI 에이전트로 재작성하는 흐름을 비판하지만 재작성 실험을 하지 않았다. 반례(AI가 재작성해 크게 빨라진 사례)와의 비교는 없다. 넷째, 글이 말하는 "프로파일링부터"는 방법론으로서 널리 알려진 조언이다. 새로운 점은 에이전트에게 설계 변경을 제안하게 하라는 방향이지만 그 방법의 효과는 제시되지 않았다. 다섯째, 실제로 N+1이나 캐싱 같은 개선은 정확성 위험(오래된 데이터, 순서 의존)을 동반하는데 글은 이 비용을 다루지 않는다.

그래도 가져갈 질문은 선명하다. 우리 서비스의 요청 시간 중 DB와 외부 호출이 차지하는 비율을 프로파일로 본 적이 있는가, 에이전트에게 맡길 최적화 지시는 "다시 쓰라"인가 "프로파일하고 설계를 바꿔 보라"인가, 병목이 정말 CPU에 묶인 구간이라면 그 구간만 분리해 다시 쓸 수 있는가.
