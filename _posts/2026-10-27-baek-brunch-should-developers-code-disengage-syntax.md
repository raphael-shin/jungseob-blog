## TL;DR

- 백명석의 답은 둘로 갈라진다. 코딩을 할 줄 알아야 하는가에는 그렇다고, 코드를 직접 작성해야 하는가에는 아니라고 답하며, 코딩을 하지 않더라도 해야 할 때는 잘해야 한다고 쓴다. 코딩을 못하면 설계도 에이전트를 부리는 개발도 잘할 수 없다는 이유다.
- 프로그래밍 언어의 추상화 수준이 올라올 때마다 사람이 보지 않게 된 단계가 늘었다. 종이테이프의 구멍에서 어셈블리로, C에서 트랜스파일러로 올라왔고, Uncle Bob은 에이전트 시대에는 사람이 쓰는 명세가 소스 코드이고 AI가 낸 Java 코드는 컴파일러 출력과 같다고 말한다.
- 손을 떼는 대상은 함수 바디 안의 라인, 곧 문법뿐이다. 함수 목록, 이름, 크기, 호출 관계, 모듈 배치라는 코드의 형태는 계속 사람이 지켜야 하고, 이를 CRAP과 DRY 도구와 리팩터링이 받친다.
- 장벽은 프롬프트나 CLAUDE.md 규칙이 아니라 도구여야 한다. 단위 테스트와 높은 커버리지, 사람이 소유하는 Gherkin 인수 테스트, 돌연변이 테스트, CRAP과 의존성과 린트가 그 예이고, 그래도 사람이 루프 안에서 직접 써 봐야 한다.
- 노트는 본문 전체와 인용 출처 일부를 읽었다. 강의에서 가져온 게임 사례의 수치(여섯 에이전트, 두 시간, 남은 버그 열 개)는 유료 강의라 확인하지 못했다.

## 글에 대하여

개발자 백명석이 브런치 매거진 「지속 가능한 소프트웨어 개발하기」에 2026년 10월 27일 올린 글이다. 작성자 소개는 Java, OOP, TDD, 리팩터링, 클린 코드, 코드 리뷰에 관심이 많은 개발자다. 이 글은 같은 매거진의 앞선 글 「AI 시대, 소프트웨어 엔지니어는 무엇을 해야 하나?」(9월 20일)와 「AI와 일하는 방식, 데자뷔」와 이어진다. 앞선 글들이 업계가 탐색 단계로 돌아왔다는 불안과 이해 없이 책임만 남는다는 불안을 다뤘고 이번 글은 코딩을 안 하게 되었다는 불안을 다룬다. 본문과 댓글 영역 밖의 부가 요소를 제외하고 전체를 읽었고 그림 세 장(추상화 수준 변화, C 컴파일 파이프라인, 실행 가능한 명세의 변환 단계)과 Wumpus 예제 코드는 브라우저 텍스트에 포함되지 않아 읽지 못했다. 이 블로그의 [에이전트가 쓴 코드에 대한 책임 노트](https://raphael-shin.github.io/jungseob-blog/posts/good-abstractions-and-responsibility-for-agent-written-code/)와 [Claude Code 팀 코드 리뷰 노트](https://raphael-shin.github.io/jungseob-blog/posts/osmani-claude-code-team-code-review/)가 같은 질문을 다른 쪽에서 다룬다.

## 코딩을 해야 하나

필자는 먼저 일정 비율로 불안을 상대화한다. Fred Brooks의 『The Mythical Man-Month』(1975)에 따르면 IDE도 없던 시절에 전체 일정에서 코딩의 몫이 6분의 1(계획 3분의 1, 코딩 6분의 1, 구성 요소 테스트 4분의 1, 시스템 테스트 4분의 1)이었다. 그런데도 코딩을 안 하게 되어 상실감을 느끼는 이들이 있다. 필자도 한 줄씩 원칙을 지키며 코딩하던 시절이 그립다고 인정한다.

그래도 지금 코딩 역량이 필요하다는 것이 그의 입장이다. Martin Fowler가 「Is Design Dead?」에서 설계자가 코딩하지 않으면 도구와 재료의 변화를 놓치고 프로그래머의 신뢰를 잃는다고 한 것처럼, 코딩에 능하지 않은 사람이 코딩하는 사람이 따라야 할 설계를 한다는 것은 말이 안 된다. 예를 들어 tmux가 있고 pane 사이에 메시지를 전달할 수 있다는 것만 알아도 에이전트 간 메시지 전송 기능을 AI에게 요청할 수 있지만 이를 모르면 상상력이 아주 뛰어나야 한다. 주말에 바이브 코딩으로 동작하는 무언가를 만들 수는 있어도, Brooks가 말한 프로그램에서 프로그래밍 제품, 프로그래밍 시스템 제품으로 올려 배포하고 운영하는 일은 엔지니어링 지식과 경험의 영역이다. Brooks는 프로그램을 시스템 제품으로 만드는 데 아홉 배의 비용이 든다고 했다.

비유는 장수다. 예전 장수는 주 업무가 전략 논의라서 업무 시간에 검술을 연습하지 않지만 실전의 일합에서 확실히 이기고 병사에게 멋짐을 보이려고 밤마다 홀로 검술을 익혔다. 코드 작성을 AI에게 넘겨도 어려운 문제를 풀고 AI에게 제대로 지시하려면 코딩 역량이 필요하다는 뜻이다.

## 추상화 수준의 역사

필자는 수준이 올라올 때마다 이전 단계를 보지 않게 되는 일이 반복되었다고 정리한다. 처음 프로그래머는 손으로 쓴 프로그램을 종이테이프에 구멍으로 뚫었고 컴퓨터를 기다려야 해서 책상에서 머리로 검증하는 desk checking이 필수였다. 어셈블러가 나오면서 구멍을 뚫는 일이 사라졌다. FORTRAN과 COBOL 같은 컴파일러가 나왔을 때도 처음에는 불신했지만 신뢰가 쌓이자 생성된 어셈블리를 보지 않게 되었다. 지금은 TypeScript와 ClojureScript가 JavaScript를 생성해도 개발자가 생성된 JavaScript를 보지 않는 트랜스파일러 단계까지 왔다.

여기서 Uncle Bob(Robert C. Martin)의 「Clean AI: Agentic Discipline」 강의가 한 단계 더 올린다. 사람이 쓰는 텍스트 명세가 소스 코드이고 AI가 생성한 Java나 Ruby 코드는 컴파일러 출력과 같다는 것이다. 필자는 단계마다 바뀐 것은 하나 의도를 나타내는 수단이라고 말한다. 구멍으로, 어셈블리로, C로 의도를 표현하던 사람이 이제 시나리오로 의도를 표현한다. 그는 이 글이 앞선 글의 이야기(제조가 공짜이고 설계도가 코드였다)에서 한 단계 위, 곧 코드 작성 자체가 싸졌다는 이야기라고 설명한다.

## 즐거움과 문법에서 손 떼기

필자는 불안의 뿌리를 인정한다. 튜토리얼을 따라 타이핑하고 설계한 대로 동작하는 것을 볼 때 기쁘고 Brooks가 『Mythical Man-Month』 1장에서 꼽은 프로그래밍의 즐거움 다섯 가지 중 첫째가 만드는 순수한 기쁨이다. 다만 최근 수년 그에게는 구현을 끝까지 하는 일이 귀찮아졌다. 그에게 만드는 즐거움은 제조가 아니라 문제 이해, 분해, 해결책 수립(종종 테스트 코드에 중요한 로직을 구현해 실행해 보는 것)까지였고 이후의 뻔한 구현을 AI에게 넘길 수 있었다. 조건은 둘이다. 이해하고 싶을 때 이해할 수 있어야 하고 기능 검증에 문제가 없어야 한다.

Uncle Bob의 강의 구호는 "코드에서 손을 떼라, 대신 에이전트를 관리하라"다. 필자는 그가 손을 떼라는 대상이 정확히 문법, 곧 함수 바디 안의 라인이라고 해석한다. 설계, 아키텍처, 모듈 구조, 함수 구조, 이름과 하는 일, 관계, 어느 정도 호출 인자까지는 여전히 신경 쓴다. 근거는 사람과 AI의 강점 차이다. AI는 문법과 낮은 수준 코드에 사람보다 낫고 사람에게는 경험과 비전과 의지가 있다. 필자가 인용한 세 가지 사람의 강점은 수년간 배운 지혜, 잘하려는 내적 동기인 야망, 지식이 아닌 경험으로 얻은 통찰이다.

손을 떼지 말아야 할 것은 코드의 형태(shape of the code)다. 필자의 정의로는 함수 목록, 이름, 크기, 호출 관계, 생성자 인자, 모듈 배치다. 모든 라인을 읽지 않아도 이 형태가 익숙한 모양으로 유지되어야 이해가 쉽고 IDE의 구조 보기와 호출 계층으로 읽는다. 그는 Hunt the Wumpus 게임의 플레이어 이동 함수로 Before와 After 코드를 만들어 보여 준다(그의 코드이며 Uncle Bob의 것이 아니라고 밝힌다). After는 하위 함수 바디를 읽지 않아도 위험 요소의 우선순위가 명세와 맞는지, 박쥐가 옮긴 방에서 위험을 다시 해소하는지, Random을 생성자로 주입받는지 같은 확인할 점이 바로 보인다. 이 형태를 지키는 것이 CRAP과 DRY 도구와 정리와 리팩터링이다. AI 코드를 AI 테스트로 돌렸으니 괜찮다는 길과 AI 코드를 읽고 이해하는 길 사이에 세 번째 길이 있다는 것이 그의 주장이다. 윤곽은 보고 검증은 장벽에 맡긴다.

## 장벽은 도구여야 한다

코드에서 손을 뗐을 때 엔지니어가 할 일은 AI를 안전하게 제어하는 물리적 장벽을 세우는 것이다. 필자는 장벽을 프롬프트로 구현할 수 없다고 못 박는다. CLAUDE.md에 적는 규칙은 지침으로 취급되어 자주 어겨지고 컨텍스트가 압축될 때 빠진다. 도구 장벽의 목록은 이렇다. 단위 테스트와 높은 커버리지는 실패하면 통과시킬 때까지 다음으로 못 넘어가게 한다. 인수 테스트(Gherkin)는 사람이 소유하는 명세로 AI가 허가 없이 수정하지 못한다. 돌연변이 테스트는 커버리지가 못 잡는 단언의 구멍을 찾는다. CRAP, 의존성 검사기, 린트는 함수 크기와 의존 방향을 잰다.

인수 테스트는 Dave Farley가 주장해 온 실행 가능한 명세다. 단위 테스트만으로는 정확성을 검증하기 부족하고 에이전트는 모든 테스트를 통과시키려고 단위 테스트 자체를 고치기도 한다. 한때 핵심이던 기능이 어느 순간 동작하지 않게 되는 이유다. Uncle Bob은 Given-When-Then 시나리오를 프로젝트의 헌법으로 두고 에이전트가 수정하지 못하게 하며 시나리오를 파서로 자동 실행 테스트로 바꾸는 환경을 유지한다. 시나리오에서 테스트까지의 거리가 길어서 AI가 글자 하나를 바꿔 통과시키는 길을 택하지 않는다는 설명이다.

그래도 사람은 루프 안에 있어야 한다. 필자가 전하는 강의 사례에서 여섯 에이전트가 두 시간 동안 만든 게임에 버그가 열 개쯤 남았다. 그중 다섯 개쯤은 에이전트가 쓴 명세를 사람이 제대로 검토하지 않아서 생겼고 나머지는 에이전트가 화면을 보지 않고 게임을 플레이하지 않아서 무엇을 기대해야 하는지 몰랐던 문제다. 또 에이전트는 컨텍스트를 너무 많이 가져 무엇이 일어나야 하는지 안다고 가정한다. 테스트는 명세에 적힌 것만 지키고 명세에 없는 기대는 사람만 안다. 같은 일을 에이전트 하나에게 시키면 10분이면 끝나지만 단위 테스트도 인수 테스트도 QA도 하드닝도 리팩터링도 없었을 것이다. 필자는 두 시간짜리 결과물이 완전하지는 않아도 모든 측면에서 테스트된 엔지니어링 결과물이라고 평가한다.

## 결론

필자는 개발을 잘한다는 뜻이 코드를 잘 쓰는 사람에서 문제를 이해하고 해결책을 찾고 분해하고 팀이 풀게 돕는 사람으로 바뀐다고 쓴다. 코딩을 못하게 되는 것이 아니고 설계, 명명, 구조, 문제 풀이는 남으며 의도를 명세로 쓰고 장벽을 도구로 세우는 일이 더해진다. Brooks가 만드는 기쁨이 특히 자기가 설계한 것일 때 더 크다고 한 말을 들어 즐거움의 위치가 한 단계 올라갈 뿐이라고 맺는다.

## 대조해서 확인한 점

Brooks의 일정 비율(계획 3분의 1, 코딩 6분의 1, 구성 요소 테스트 4분의 1, 시스템 테스트 4분의 1)은 『The Mythical Man-Month』 8장에 해당 문장이 있다. 프로그램에서 프로그래밍 시스템 제품으로의 비용 증가는 1장의 그림에서 확인된다. Uncle Bob이 에이전트가 쓴 코드를 리뷰하지 않고 테스트 커버리지, 의존 구조, 순환 복잡도, 모듈 크기, 돌연변이 테스트로 잰다고 쓴 X 게시물(2026년 4월 14일)이 있고 사람이 코드에서 손을 떼고 더 높은 수준에서 관리해야 한다는 말도 그 글에 있다. 「Clean AI: Agentic Discipline」은 Clean Coders와 O'Reilly의 유료 강의 시리즈(2026년 2월 공개)로 존재한다.

확인하지 못한 것도 있다. 강의를 직접 보지 못해 "여섯 에이전트, 두 시간, 남은 버그 열 개, 그중 다섯 개는 명세 검토 부족"이라는 수치는 필자의 전달이다. Uncle Bob이 2026년 5월 29일에 올린 Hunt the Wumpus 비교 데이터는 다른 실험으로 보인다. 사람 5명이 만족할 때까지 평균 146.6분이 걸렸고 에이전트 네 역할의 군집(swarm-forge, codex)은 명세 24개 시나리오와 코딩과 리팩터링과 하드닝으로 총 62분, 사람 시간은 15분이었다. 필자가 말한 두 시간짜리 실행과는 시간 구성이 다르므로 같은 실행이라고 볼 수 없다. Fowler의 「Is Design Dead?」 인용문과 Dave Farley의 주장은 이 노트가 원문을 읽지 않았다. 본문 첫머리의 "주변에서 상실감을 느낀다"는 관찰은 필자의 일화다.

## 읽을 때 유의할 점

첫째, 이 글은 TDD와 클린 코드 진영 개발자의 해석이며 Uncle Bob의 주장에 크게 기댄다. 둘째, 코드를 보지 않는 접근은 높은 커버리지와 돌연변이 테스트와 사람이 소유한 인수 테스트라는 장벽이 갖춰진 환경을 전제하고 그런 환경이 없는 코드베이스에는 그대로 옮기기 어렵다. 셋째, "10분 대 두 시간"의 비교는 필자의 가정이며 측정이 아니다. 넷째, 장벽을 세운다는 처방은 이미 테스트가 두터운 프로젝트에서 효과를 낼 수 있고 테스트 부채가 큰 레거시에는 먼저 장벽을 만드는 일이 큰 비용이다. 다섯째, 형태를 본다는 방법은 필자가 직접 읽을 수 있는 Java 계열의 구조를 가정한다.

그래도 가져갈 질문은 선명하다. 지금 AI에게 넘기고 있는 것은 문법인가 설계인가, 내가 지키는 코드의 형태는 무엇인가, 장벽 중 프롬프트에만 맡긴 것은 무엇인가, 사람이 소유한 인수 테스트가 있는가, 에이전트가 모르는 기대를 어떻게 확인하는가.
