## TL;DR

- Sally-Ann DeLucia(Arize 제품 책임자)는 컨텍스트 관리를 엔지니어링뿐 아니라 제품과 UX의 문제로 본다. 에이전트가 올바른 데이터를 보지 못하면 나쁜 답을 내고, 나쁜 답을 내는 제품은 쓰이지 않는다는 논리다.
- Arize의 에이전트 Alyx는 자기 추적 데이터를 분석하다 스팬이 늘어 컨텍스트 한계에 걸리고 실패하는 악순환에 빠졌다. 처음 시도한 앞부분만 남기는 자르기는 후속 질문을 새 대화로 만들었고, LLM 요약은 무엇이 중요한지 통제할 수 없어 일관성이 없었다.
- 지금 쓰는 해법은 앞뒤만 남기고 중간을 잘라 원본을 저장소에 두며, 에이전트가 필요하면 도구로 되찾는 방식이다. 데이터가 많은 검색 작업은 하위 에이전트가 맡고 요약만 돌려준다.
- 긴 세션의 실패는 늦게 나타나므로 10턴을 미리 채우고 11턴을 시험하는 평가를 만들었다. 진짜 장기 메모리, 컨텍스트 예산, 품질 지표는 아직 없다고 인정한다.
- 이 노트는 영어 자막 전체(16:16), AI Engineer 페이지, Arize 블로그, Claude Code 소스 분석 글을 읽고 대조했다. 모든 수치와 효과는 Arize의 자기 보고이며 독립 검증이 없다.

## 영상에 대하여

AI Engineer 채널이 2026년 5월 10일에 올린 16분 16초 영상이다. 영어 자동생성 자막만 있고 전체를 읽었다. AI Engineer Europe 2026의 발표이고 연사는 Arize 제품 책임자 Sally-Ann DeLucia다. 데이터 과학자로 시작해 지금은 제품을 만들면서 Alyx의 핵심 기여자로 일한다고 소개한다. 자막은 에이전트 이름을 Alex로 적었으나 설명란과 Arize 문서는 Alyx라고 쓴다. 설명란의 목차는 소개 0:00, Alyx 개요 1:02, 컨텍스트 엔지니어링과 프롬프트 엔지니어링 1:29, 데이터 증가의 악순환 4:06, 단순 자르기가 실패한 이유 5:16, 요약이 믿을 수 없었던 이유 6:14, 스마트 자르기와 메모리 저장소 6:46, 긴 세션 8:02, 하위 에이전트 9:23, 남은 과제 11:19, Claude Code 소스에서 알게 된 점 12:57, 핵심 정리 13:44, 질의응답 14:58이다. 같은 주제를 모델 제공자 관점에서 다룬 [OpenAI Build Hour 정리 노트](https://raphael-shin.github.io/jungseob-blog/posts/openai-build-hour-agent-memory-patterns/)와 이어서 읽을 수 있다.

## 문제: 컨텍스트 관리는 제품 문제다

연사는 지난해 중반부터 퍼진 컨텍스트 엔지니어링이라는 말을 Karpathy의 글로 소개한다. 초기에는 프롬프트에 매달렸지만 에이전트의 성패를 가르는 것은 컨텍스트였다. 좋은 전략은 에이전트가 필요한 것은 기억하고 필요 없는 것은 잊게 하는 것이다. 컨텍스트 관리는 창에 들어가는 만큼을 채우는 일이 아니라 모델이 무엇을 볼지 전략적으로 고르는 일이다.

Alyx는 Arize의 관측 플랫폼 위에서 돌기 때문에 AI 에이전트의 트레이스를 다뤄야 한다. 트레이스 하나에도 사용자 입력, 프롬프트, 메타데이터가 있고 Alyx와의 상호작용이 더해지며 여러 트레이스에서 패턴을 찾으려 하면 곱절로 늘어난다. 연사는 이것을 제품과 UX의 문제라고 부른다. 엔지니어가 여러 전략을 시도하지만 결국 에이전트에 맞는 데이터가 없으면 나쁜 답이 나오고 그러면 아무도 제품을 쓰지 않는다는 이유다.

## 악순환과 두 번의 실패

팀은 Alyx로 Alyx를 만들었다. 에이전트가 트레이스 스팬 데이터 위에서 돌면 스팬이 늘고 컨텍스트 한계에 걸려 실패한다. 실패를 일으킨 스팬은 세션에 그대로 남아 있어 다시 돌리면 같은 데이터에 새 데이터가 더해지고 또 실패한다. 분석하는 시스템이 분석 대상 데이터에 묶인 것이다. 탈출하는 데 배운 것은 세 가지로 정리된다. 컨텍스트를 제어하는 법, 컨텍스트와 메모리를 분리하는 법, 무거운 일을 다른 에이전트로 옮기는 법이다.

첫 시도는 단순 자르기였다. 긴 덩어리에서 처음 100자만 남기고 나머지는 버렸다. 간단한 질문에는 통했으나 에이전트는 모든 것을 잊었다. 후속 질문이 새 대화처럼 보였고 가장 흔한 입력이 무엇이냐고 묻고 나서 그중 B를 더 말해 달라고 하면 알아듣지 못했다. 연사의 결론은 과도한 자르기가 추론을 깼다는 것이다. 둘째 시도는 요약이었다. LLM이 요약을 잘하니 전체 컨텍스트를 더 짧게 요약해 보내면 될 것 같았지만 일관성이 없었다. 무엇이 중요한지 통제할 수 없었고 LLM에 판단을 맡긴 결과가 믿을 수 없었다. 연사는 요약이 안 통한 것이 가장 의외였다고 말한다.

## 지금의 해법: 중간을 자르고 원본은 저장소에

현재 Alyx가 쓰는 방식은 스마트 자르기와 메모리의 조합이다. 앞 100자와 뒤 100자를 남기고 중간을 빼서 저장해 두며 에이전트는 이 저장소에 언제든 접근한다. 같은 입력의 중복 도구 호출은 마지막 결과만 두고 시스템 프롬프트를 다시 보내지 않으며 중요하다고 판단한 도구 호출이나 이전 대화의 메시지는 에이전트가 직접 되찾을 수 있다. 연사는 이 방식이 매우 성공적이었고 몇 달간 손대지 않았다고 말한다. 한 줄 요약은 컨텍스트가 모델이 보는 것이고 메모리가 무엇이 살아남을지 정한다는 것이다.

긴 세션은 다른 문제다. 사용자는 대화를 거의 새로 시작하지 않고 한 채팅에서 여러 페이지를 오간다. 대화가 길어지면 실패가 늦게 나타나 사용자 제보나 데이터 점검으로 뒤늦게 알게 된다. 그래서 긴 세션 평가를 만들었다. 10턴을 미리 채워 넣고 11턴을 시험한다. 이로써 이런 버그를 재현할 수 있게 되었고 기다릴 필요가 없다. 처음 10턴 미만이던 대화가 지금은 20턴 이상으로 늘어난다고도 말한다.

그래도 한 에이전트가 감당하기에는 데이터가 너무 많은 경우가 있다. 연사의 결론은 모든 컨텍스트가 같은 에이전트에 속하지는 않는다는 것이다. 검색 작업은 여러 쿼리, 방대한 데이터, 단계별 중간 추론이 일어난다. 이를 하위 에이전트로 옮기면 메인 대화에는 채팅과 가벼운 컨텍스트만 남고 무거운 데이터는 하위 에이전트에 머문다. 결과만 메인 에이전트로 넘기고 필요하면 메모리 저장소에서 더 가져올 수 있다. 연사는 이것이 판도를 바꿨다고 하며 데이터 집약적 작업에 하위 에이전트를 점점 늘려 가고 있다.

## 아직 풀지 못한 것

연사가 인정한 한계는 네 가지다. 첫째, 거대한 컨텍스트는 여전히 문제다. 에이전트가 에이전트의 데이터를 다루므로 고객의 시스템 프롬프트, 사용자 메시지, 이력까지 모두 분석 대상이 되어 공급자 한도에 걸린다. 반복해서 돌아오는 해법은 하위 에이전트다. 둘째, 긴 메모리가 어렵다. 지금의 메모리는 같은 세션에서 컨텍스트를 되찾는 저장소일 뿐 진짜 장기 메모리가 아니며 사용자가 새 채팅을 시작하면 지난 논의를 모른다. 연사는 이에 대한 불만이 가장 많다며 장기 메모리를 추가하는 중이라고 한다. 셋째, 컨텍스트 선택이 아직 휴리스틱이다. 앞 100자와 뒤 100자 같은 단순한 기준이며 원칙 있는 컨텍스트 예산이나 컨텍스트 품질 지표가 없고 평가로 맞는지 가늠할 뿐이다. 넷째, Claude Code 소스가 공개되었을 때 비슷한 자르기와 압축을 쓰는 것에 놀랐고 비법을 기대했으나 얻지 못했다고 말한다.

마무리 메시지는 세 가지다. 컨텍스트 엔지니어링이 중요하고 메모리가 중요하며 평가가 중요하다. 그리고 에이전트는 프롬프트 때문이 아니라 컨텍스트 때문에 실패한다. 질의응답에서 한 청중은 Claude Code가 캐시를 무효화하지 않으려고 컨텍스트 관리에 쏟은 노력을 묻는다. 연사는 지금은 장기 메모리에 집중해 캐시는 깊이 다루지 않았으며 원본을 ID와 함께 데이터베이스에 저장하고 에이전트가 ID와 위치, 미리보기를 보는 도구로 접근한다고 답한다. 더 정교해질 필요가 있다는 점을 인정한다.

## 대조해서 확인한 점

AI Engineer 페이지의 해설은 이 강연을 같은 구조로 정리하며 정보를 시야에서 치우되 파괴하지 않는 방식(remove information from view without destroying it)이라는 소제목으로 정리한다. 40개 넘는 스킬이라는 소개도 같은 페이지에 있지만 강연을 옮긴 것이어서 독립된 확인은 아니다. 이 노트는 그 수치를 확인하지 못했다.

Arize의 블로그 글 「Managing Memory in AI Agents: Beyond the Context Window」가 같은 내용을 더 자세히 쓴다. 세부는 강연과 다르다. 강연은 처음 100자만 남겼다고 하지만 블로그는 입력 전체를 10만 자, 개별 행을 100자로 상한을 두는 방식이었다고 쓴다. 강연은 앞 100자와 뒤 100자를 남긴다고 하는데, 블로그는 처음 100자만 가져가는 것으로는 쓸모가 없다고 하며 "의미 있는 덩어리"를 앞뒤에서 남기고 잘린 덩어리에 ID를 붙여 저장했다고 쓴다. 따라서 강연의 100자는 단순화로 보이며 실제 운영 값으로 읽으면 안 된다. 블로그에는 강연에 없는 설계도 있다. 거대한 JSON 도구 결과를 컨텍스트에 넣지 않고 서버에 저장한 뒤 미리보기와 `json_id`만 모델에 주고 모델이 jq와 grep으로 필요한 조각을 가져가게 하는 LargeJSON 추상화다. Cursor와 Claude Code가 파일을 디스크에 두고 미리보기와 grep으로 접근하는 방식에서 얻은 발상이라고 쓴다. 블로그는 요약의 한계를 더 직접적으로 쓴다. 손실이 본질적이고 예측할 수 없으며 모델이 나중에 무엇이 중요할지 일관되게 식별하지 못한다. 모델이 장거리 추론에 나아지면 쓸 수 있을지도 모른다며 완전히 버리지는 않았다. 어느 턴을 압축해도 안전한지 가리는 휴리스틱을 아직 고민한다고도 쓴다.

Claude Code 발언은 제3자 분석과 맞는다. 2026년 3월 31일에 `@anthropic-ai/claude-code` v2.1.88 패키지가 소스맵을 포함해 배포되어 원본 TypeScript가 드러났다는 것이 한 분석 글의 설명이다. 이 글은 컴팩션이 4단계이고 마이크로컴팩션이 LLM 호출 없이 토큰 기준으로 오래된 도구 결과를 지우거나 자르는 순수 클라이언트 코드이며 9개 섹션 요약을 만드는 전체 컴팩션이 오히려 가장 드물게 작동한다고 적는다. 프롬프트 캐시를 일급 아키텍처 제약으로 다룬다는 서술도 있다. 이 분석은 앞선 자기 연구의 결론이 틀렸다고 정정한 글이기도 하며 이 노트는 유출 소스 자체를 읽지 않았다. 즉 "Claude Code도 비슷한 자르기와 압축을 쓴다"는 연사의 말은 이 제3자 분석과 방향이 같다.

## 읽을 때 유의할 점

첫째, 모든 효과가 Arize의 자기 보고다. 성공, 몇 달간 손대지 않음, 대화 길이 증가 같은 서술에 수치나 비교 실험이 없고 Alyx는 Arize 제품이라 강연은 제품 소개를 겸한다. 둘째, 해법은 관측 데이터라는 특수한 도메인(긴 JSON, 반복되는 행)에 맞춰져 있다. 대화나 코드 중심 에이전트에서는 앞뒤 자르기가 맞지 않을 수 있다. 셋째, 요약이 실패했다는 결론은 이 도메인과 당시 모델 기준이다. 연사도 모델이 나아지면 달라질 수 있다고 열어 둔다. 넷째, 중간을 저장소에 두는 방식은 에이전트가 그 존재를 알고 필요한 순간에 되찾아야 성립한다. 되찾기에 실패한 사례의 빈도는 제시되지 않았다. 다섯째, 저장소에 원본을 둔다는 것은 민감한 데이터가 별도 보관된다는 뜻이며 접근 통제와 보존 기간은 다뤄지지 않았다.

그래도 점검 질문은 선명하다. 우리 에이전트의 입력 중 어느 부분이 모델에게 정말 필요한가, 잘라낸 부분을 에이전트가 존재와 위치를 알고 되찾을 수 있는가, 11턴 이후에서만 나타나는 실패를 어떻게 시험할 것인가, 요약을 쓴다면 무엇이 빠졌는지 어떻게 알아챌 것인가. 요약을 시스템에 되먹일 때의 위험은 [컴팩션 요약 자기 주입 노트](https://raphael-shin.github.io/jungseob-blog/posts/compaction-summary-self-injection/)가, 하네스 전체의 방향은 [Katz의 하네스 노트](https://raphael-shin.github.io/jungseob-blog/posts/katz-is-the-agent-harness-dead/)가 다룬다.
