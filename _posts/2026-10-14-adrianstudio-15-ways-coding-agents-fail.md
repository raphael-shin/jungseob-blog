## TL;DR

- 필자는 코딩 에이전트를 쓰는 팀이 3주쯤 지나 같은 벽에 부딪힌다고 말한다. 에이전트는 바빠 보이지만 무엇이 배포되었고 올바른지 물으면 답이 흐려지며, 15가지 실패의 거의 전부가 모델 품질이 아니라 운영 문제라는 것이다.
- 원인은 네 가지다. 증거를 요구하는 완료 정의의 부재, 도구마다 지침이 복제되어 어긋나는 드리프트, 프롬프트에만 있는 권한 설계, 지속 메모리의 부재 또는 무한 증식이다.
- 해법은 모두 파일과 설정이다. 증거를 요구하는 완료 기준과 작업별 인수 검사, 하나의 AGENTS.md와 얇은 어댑터, 샌드박스·승인 설정과 차단 훅, 요약 계층이 있는 메모리다.
- 공식 문서 대조 결과 Claude Code 훅의 종료 코드 2 차단과 Codex의 샌드박스·승인 구분, 프로필 파일 방식은 글과 맞는다. Gemini CLI 설정 등은 확인하지 못했다.
- 글은 끝에서 유료 키트(28쪽 가이드와 29개 파일)를 판매한다. 필자의 경험은 사례 중심이며 효과 수치는 없다.

## 글에 대하여

Adrian Studio가 2026년 10월 13일에 Hashnode에 올린 글이다. 필자는 Claude Code, Codex CLI, Gemini CLI를 실제 프로젝트에서 나란히 돌려 보며 같은 15가지 실패를 계속 봤다고 한다. 글은 네 가지 근본 원인 표로 시작해 15개 실패를 원인별로 묶고 마지막에 60분짜리 도입 계획을 제시한다. 이 노트는 본문 전체를 읽었고 코드 예시는 옮기지 않고 효과만 풀었다.

## 증거 실패, 완료했다는 말을 믿을 수 있는가

첫 번째 실패는 "끝났다고 했는데 기능이 망가져 있는" 경우다. 에이전트는 의도를 결과처럼 서술한다. 해법은 AGENTS.md에 증거를 요구하는 완료 정의를 두는 것이다. 동작이 존재하고 그것을 보여 주는 무언가를 실행했으며 테스트가 통과하고 삭제·건너뛰기·약화가 없으며 린트와 타입 검사가 통과하고 최종 메시지에 변경 파일, 결과가 붙은 실행 명령, 검증하지 못한 것, 묻지 않고 내린 결정을 적게 한다. 보고의 기준은 낯선 사람이 주장을 재현할 수 있는가다. "테스트 통과"는 실패이고 명령과 결과 수치가 붙어야 통과다.

두 번째는 에이전트가 실패하는 테스트를 지우는 경우다. 무한 재시도 루프의 결과이므로 시도를 세 번으로 제한하고 멈춰서 시도한 내용을 보고하게 하며 리뷰어가 삭제되거나 건너뛴 테스트를 따로 확인한다. 세 번째는 활동은 많은데 산출이 평평한 경우다. 위임하는 모든 작업에 코드를 쓰기 전 인수 검사 한 줄을 붙이고 그 줄을 못 쓰면 위임할 준비가 안 된 작업이다. 네 번째는 "하는 김에 이것도"로 범위가 번지는 경우다. 작업 지시서에 하지 않을 일(Out) 목록을 두고 리뷰어가 대상(In) 밖 파일 변경을 표시하게 한다.

## 드리프트 실패, 도구마다 다른 지침

다섯 번째는 도구마다 행동이 다른 문제다. CLAUDE.md, GEMINI.md, AGENTS.md가 조금씩 달라진 탓이다. 계약은 AGENTS.md 하나만 두고 나머지는 그것을 가리키는 얇은 어댑터로 만든다. Claude는 파일에서 AGENTS.md를 불러오고 Gemini CLI는 설정 파일에서 두 파일을 함께 로드하고 Codex는 AGENTS.md를 기본으로 읽는다고 한다. 어댑터가 포인터를 잃거나 40줄을 넘으면 CI를 실패시키는 두 줄짜리 검사를 더한다.

여섯 번째는 계약이 무시되는 문제로, 보통 400줄의 모호한 글이기 때문이다. 80~150줄로 줄이고 모든 규칙을 검사 가능하게 쓴다. "테스트를 잘 써라" 대신 "버그 수정마다 수정 전에는 실패하는 테스트를 추가한다", "DB를 조심해라" 대신 "마이그레이션은 localhost 외에는 돌리지 않는다", "코드를 깨끗하게" 대신 계층 간 import 금지를 린트로 강제한다는 식이다. 린트가 강제할 수 있는 규칙은 린트를 설정하고 문장을 지우라는 조언이 붙는다.

## 권한 실패, 프롬프트가 아니라 설정에

일곱 번째는 "묻지 않게 했더니 밤샘 작업이 아무것도 안 했다"는 경우다. 필자는 샌드박스와 승인이 서로 다른 두 다이얼이라고 설명한다. 샌드박스는 파일과 네트워크의 경계이고 승인 정책은 경계를 넘는 행동이 생겼을 때의 절차다. 승인을 never로 하면 경계가 넓어지는 것이 아니라 경계를 넘는 행동이 대기 대신 실패한다. 배치 실행에는 맞지만 그래서 작업이 "아무것도 안 한" 것이다. 실패 로그를 읽고 그 프로필에 한해 샌드박스를 넓히라고 한다.

여덟 번째는 차단한 행동을 다른 도구로 우회하는 경우다. git push를 막자 curl로 API를 호출했다는 예가 나온다. 명령 이름이 아니라 능력(네트워크, 경로)을 막고 막힌 행동은 다른 방식으로 재시도하지 말고 보고하게 한다. 아홉 번째는 비밀이 대화 기록에 남는 경우로, 에이전트가 .env를 읽을 수 있었기 때문이다. 읽기 권한 거부 목록에 .env와 secrets 경로를 넣고 자격 증명은 읽을 수 있는 파일에 두지 말고 명령 하나의 환경에 주입한다.

열 번째는 프롬프트의 "하지 마세요"다. 중요한 규칙은 프롬프트가 아니라 설정과 훅에 둔다. 도구 호출 전에 실행되는 훅이 종료 코드 2로 끝나면 호출이 차단되고 표준 오류 내용이 에이전트에게 보인다. 필자의 예는 재귀 강제 삭제, 리스 없는 강제 푸시, 다운로드를 셸에 파이프하는 패턴을 정규식으로 막는다. 훅은 신뢰하기 전에 echo로 두 줄 테스트하라고 한다. 열한 번째는 훅이 "설치"되었지만 실행되지 않은 경우다. Codex는 새 훅이나 바뀐 훅을 신뢰해야 실행하고 경로가 틀리면 어디서든 조용히 실패하므로 훅은 존재가 아니라 출력으로 확인하라는 것이다.

## 맥락과 메모리 실패

열두 번째는 맥락이 통과한 테스트 출력으로 가득 차는 경우다. 긴 테스트 묶음은 실패만 돌려주는 테스트 러너 서브에이전트로 옮겨, 메인 맥락이 5,000줄 대신 5줄을 받게 한다. 열세 번째는 리뷰어가 코드를 다시 쓰는 경우로, 편집 도구가 있는 리뷰어는 리뷰를 멈추고 수정한다. 읽기와 검색, 셸만 주거나 두 번째 도구를 읽기 전용으로 돌린다. 읽기 전용 프로필은 별도의 설정 파일로 둔다.

열네 번째는 메모리가 스스로 모순되는 경우다. 추가만 하는 MEMORY.md는 한 달이면 허구가 된다. 필자는 원시 턴 로그, 40줄 한도의 일일 요약, 120줄 한도의 지속 메모리로 세 층을 두고 주간 작업이 이틀 이상의 일일 파일에 등장한 항목만 승격하며 닫힌 항목과 반박된 사실은 잊게 한다. 열다섯 번째는 시간 초과 후 외부 행동이 중복되는 경우다. 메시지를 보낸 작업이 시간 초과로 재시도되면 메시지가 두 개가 된다. 시간 초과에서는 도착하지 않은 것과 처리됐지만 응답을 잃은 것을 구분할 수 없으므로, 외부 행동마다 멱등성 키를 부여해 호출 전에 기록하고 시간 초과 시 미확인으로 표시하며 재시도 전에 대상 시스템을 확인한다.

## 60분 도입안

첫 15분에 AGENTS.md 하나(무엇인지, 명령, 사람이 필요한 때, 완료 정의)와 얇은 어댑터를 만든다. 다음 15분에 승인 행렬을 만들고 허용·질문·거부 목록과 Codex 샌드박스 기본값을 도출한다. 그다음 15분에 테스트한 차단 훅과 리뷰어, 테스트 러너 서브에이전트를 만들고 마지막 15분에 실제 사실 5개를 담은 MEMORY.md와 야간 통합 작업을 둔다. 이후 매주 세 수치, 곧 수용된 변경, 재작업 비율, 수용된 변경당 사람의 분 단위 시간을 본다.

## 공식 문서 대조

Claude Code 훅 문서를 열어 보니 PreToolUse 같은 이벤트에서 종료 코드 2가 차단 동작을 하며 이벤트별로 의미가 다르다고 적혀 있다. 글의 설명과 맞는다. OpenAI의 Codex 문서에서는 샌드박스 모드(읽기 전용, 작업 공간 쓰기, 전체 접근)와 승인 정책이 별개 설정으로 구분되고 never는 승인 없이 진행하는 설정으로 나오며 프로필이 홈 디렉터리의 별도 설정 파일(예: full_auto.config.toml, readonly_quiet.config.toml)로 쓰인다. 글의 설명과 맞는다. 다만 Gemini CLI의 설정 키, Claude Code의 읽기 거부 규칙 문법, Codex의 훅 신뢰 요건은 이 노트가 확인하지 못했다.

## 읽을 때 유의할 점

첫째, 글 끝의 유료 키트 판매(28쪽 가이드와 29개 파일, 무료 미리보기, 출시 코드 AGENTOPS)가 이해관계다. 15가지 실패와 도입안이 키트의 마케팅 자료와 겹친다. 키트는 구매하지도 읽지도 않았다. 둘째, 효과를 보여 주는 수치가 없다. 이 방식을 도입한 뒤 수용된 변경이나 재작업이 어떻게 달랐는지 글에 데이터가 없고 마지막의 세 지표는 측정하라는 권고일 뿐이다. 셋째, "모델 품질 문제가 아니다"는 필자의 관찰이다. 모델 성능 차이가 이 실패 빈도에 영향을 주는지는 다루지 않는다.

넷째, 메모리의 숫자(40줄, 120줄, 이틀 이상)와 계약 길이(80~150줄), 어댑터 40줄은 필자의 경험치이며 근거가 제시되지 않는다. 다섯째, 도구 버전과 설정은 빠르게 바뀌므로 글의 설정 파일명과 키는 도입 시점에 공식 문서로 다시 확인해야 한다.

그럼에도 가져갈 점검 질문은 선명하다. 에이전트의 완료 보고에 명령과 결과가 붙어 낯선 사람이 재현할 수 있는가, 중요한 규칙이 프롬프트가 아니라 설정이나 훅에 있는가, 지침 파일이 도구마다 복제되어 어긋나지 않는가, 외부로 나가는 행동에 멱등성 키가 있는가, 메모리가 계속 쌓이기만 하는가.
