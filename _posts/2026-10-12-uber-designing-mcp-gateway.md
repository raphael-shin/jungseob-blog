## TL;DR

- Uber는 팀마다 따로 만든 MCP 연동이 파편화되자 모든 MCP 상호작용을 맡는 중앙 게이트웨이를 만들었다. 글은 이 게이트웨이가 800개가 넘는 MCP 서버와 5천 개가 넘는 도구를 호스팅한다고 쓴다.
- 구조는 제어 평면인 MCP Registry와 데이터 평면인 Proxy Gateway로 나뉜다. 핵심 아이디어는 기존 API가 에이전트에게 도구를 주는 가장 빠른 길이므로 서비스를 고치지 않고 HTTP, gRPC, TChannel 호출을 MCP로 번역하는 것이다.
- 안전 원칙은 "발견이 노출을 뜻하지 않는다"다. 자동으로 찾은 서버와 도구는 모두 비활성 상태로 시작하고 소유 팀이 검토해 켠다. 설명을 바꿀 때마다 소유자 승인이 필요하다.
- 규모가 커지자 맥락 낭비가 문제가 되어 Omni MCP, Response Projection, Code Mode를 더했다. Code Mode는 코딩 에이전트의 사내 기본값이다.
- 모든 수치와 효과는 Uber 자사 서술이며 지연, 비용, 사고율 같은 측정값은 글에 없다. 이 노트는 본문 전체를 읽었고 도표는 이미지여서 읽지 못했다.

## 해결하려던 문제

글에 따르면 Uber의 AI 에이전트 도입은 코드와 데이터와 운영 시스템을 다루는 방식을 바꿨다. 초기에는 MCP(Model Context Protocol)를 임시로 붙인 연동만으로도 효과가 분명했다. 에이전트가 실제 업무 맥락을 읽고 내부 서비스를 질의하고 사용자를 대신해 행동할 수 있게 되자 훨씬 유능해졌다.

문제는 도입이 빨라지면서 생겼다. 팀마다 독립적으로 연동을 만들어 도구가 파편화되고 인프라가 중복되었다. MCP 도구는 찾기 어렵고 안정적으로 운영하기 어려웠으며 특정 서비스나 에이전트 구현에 단단히 묶여 있었다. 수백 개 팀이 에이전트 워크플로를 탐색하는 규모에서는 통합된 구조 없이 MCP를 늘리면 운영 복잡도와 보안 위험과 개발자 마찰만 커진다고 글은 진단한다. 그래서 프로토콜 차이(HTTP, gRPC, TChannel)를 추상화하고 일관된 보안과 관측 가능성을 강제하며 도구를 만들고 찾고 재사용하기 쉽게 하는 중앙 솔루션이 필요했다.

## 두 평면 구조

MCP Gateway는 에이전트와 기존 백엔드 서비스, 그리고 네이티브 MCP 서버 사이에서 조율과 라우팅을 맡는 마이크로서비스다. 제어 평면인 MCP Registry는 수백 개의 MCP 서버와 수천 개의 도구 카탈로그를 유지한다. 도구는 기존 API를 노출하는 노코드 정의에서 MCP 명세에 맞춰 직접 짠 네이티브 구현까지 걸쳐 있고 레지스트리는 발견, 소유권, 활성화의 단일 진실 원천이다. 데이터 평면인 Proxy Gateway는 런타임에 MCP 요청을 실행한다. MCP 호출을 HTTP, gRPC, TChannel 요청으로 번역해 백엔드로 보내고 응답을 다시 MCP 결과로 바꾼다. 하위 서비스는 바꿀 필요가 없다.

글이 결론에서 꼽는 핵심 통찰은 이것이다. 기존 API가 에이전트에게 도구를 주는 가장 빠른 길이므로, 서비스 팀에게 에이전트 시대에 맞춰 서비스를 다시 쓰라고 하지 않고 팀이 있는 곳에서 만난다. 글은 이를 하위 서비스를 바꾸지 않는 "제로 체인지"로 표현한다.

## 발견, 그러나 노출은 아니다

Uber에는 수천 개의 내부 서비스가 있고 이 API들은 AI 시스템에 값진 맥락을 준다. 하지만 팀마다 MCP 서버를 손으로 쓰게 하면 느리고 고통스럽다. 그래서 AutoCrawler를 만들었다. Cadence 기반의 분산 워크플로 시스템으로, 정해진 주기로 IDL 레지스트리를 훑어 새 서비스와 API와 스키마 변경을 찾는다. 발견한 각 항목에 대해 MCP 서버 표현을 만들거나 갱신하고 도구 정의와 스키마를 생성하거나 가져오고 도구를 레지스트리에 비활성 상태로 등록한다.

Protobuf나 Thrift IDL로 정의된 서비스는 메서드 이름과 요청·응답 스키마와 문서 주석을 파싱한다. LLM으로 에이전트 친화적인 도구 설명을 생성하고 스키마를 MCP 호환 JSON-RPC 2.0 스키마로 번역한 뒤 비활성 상태로 등록한다. MCP를 직접 구현한 네이티브 서버는 하트비트 지표로 발견하고 `listTools`를 호출해 도구와 스키마를 받아 가상 프록시 서버를 만든다. Jira나 Google 같은 외부 MCP 서버는 게이트웨이가 호출자의 사용자 토큰을 하위로 넘기며 인가, 속도 제한, 민감 정보 가림을 강제하고 제3자 MCP 서비스가 내부 토큰을 외부 인증 토큰으로 바꾼다.

가장 눈에 띄는 설계 원칙은 "발견이 노출을 뜻하지 않는다"다. 서비스 팀 없이 MCP 서버를 만들 수 있어도 소유권과 통제는 서비스 팀에 있어야 한다. 모든 서버와 도구는 비활성으로 시작하고 소유 팀이 생성된 도구 정의를 검토하고 다듬어 명시적으로 켜야 한다. 도구 설명이 바뀔 때마다 구성 변경 비교가 생기고 서버 소유자가 승인해야 하며 필요하면 이전 버전으로 되돌릴 수 있다.

## 런타임과 보안

데이터 평면은 제어 평면의 설정을 정해진 주기로 메모리에 갱신해, 도구 수정이나 활성화 변경이 재시작이나 재배포 없이 바로 반영된다. 서비스마다 단일 `/<service-name>/mcp` 엔드포인트가 에이전트의 진입점이다. IDL 기반 서비스는 서버 핸들러가 JSON 페이로드를 와이어 포맷으로 번역하고 Protobuf나 Thrift 바이트로 직렬화해 하위 서비스에 보낸 뒤, 응답을 다시 JSON으로 되돌린다. 실제 하위 요청은 서비스 메시 사이드카인 Muttley가 실행해 기존 서비스 간 라우팅 기능을 그대로 얻는다.

보안은 도구 단위의 세밀도로 인가와 가림 처리를 내장한다. 사내 접근 통제 시스템이 감지된 호출자(사람, 서비스, 에이전트)에게 헌장(charter) 정책을 적용하며, 정책은 서버 단위로 만들고 필요하면 도구 단위로 재정의한다. 도구 응답의 개인 식별 정보와 민감 데이터는 기본으로 가린다. 글이 꼽는 이점은 쉬운 발견과 설치, 기존 API의 노코드 활용, 내장된 관측 가능성과 보안, 중앙화된 소유권과 거버넌스다.

## 규모에서 생긴 문제와 세 가지 해법

수백 개 서버와 수천 개 도구로 커지자 소규모에서는 없던 문제가 드러났다. 글은 이를 맥락 낭비와 과도한 비용이라 부른다. MCP에는 서버를 가로지르는 검색 개념이 없어 에이전트가 먼저 어느 서버와 말할지 알아야 하고 서버마다 URL과 자격 증명과 도구 목록을 일일이 연결해야 한다. 수백 개 서버에서는 이 정보만으로 모델의 맥락 한도를 잠식한다.

첫째 해법인 Omni MCP는 모든 게이트웨이 서버에 점진적 발견으로 접근하게 하는 단일 프록시 서버다. 노출하는 도구는 `discover_server`(질의 의도로 서버 찾기), `discover_tools`(서버의 도구 조회), `get_tool_schema`(도구의 JSON 스키마 조회), `invoke_tool`(도구 호출) 네 개다. 둘째 해법인 Response Projection은 GraphQL과 비슷한 호출 방식이다. 도구 요청 스키마에 필드를 하나 주입해 LLM이 필요한 필드의 중첩 경로 배열만 적게 하고 게이트웨이가 런타임에 응답에서 그 필드만 남긴다. 셋째 해법인 Code Mode는 쉘 환경에서 도구 출력을 파일에 쓰는 것이 전체 응답을 맥락에 올리는 것보다 효율적이라는 관찰에서 나왔다. Uber의 에이전트 작업용 CLI인 aifx가 MCP 서버 설치 없이 게이트웨이를 통해 호출을 보내며 `aifx mcp list`, `aifx mcp search`, `aifx mcp call` 세 명령을 제공한다. 에이전트는 이를 한 명령으로 이어 출력을 파일에 쓰고 파일 시스템 에이전트가 필요한 부분만 골라 맥락에 올린다. 글은 Code Mode가 지금 코딩 에이전트의 MCP 도구 사용에서 회사 기본값이라고 쓴다.

## 읽을 때 유의할 점

첫째, 이 글은 자사 플랫폼을 소개하는 설계 글이다. 800개 서버와 5천 개 도구는 Uber의 서술이고 도입 효과를 지연, 비용, 사고 건수, 개발 시간으로 측정한 자료는 글에 없다. "몇 분 안에 어느 팀이든 연결할 수 있다"는 표현도 정성적 주장이다. 둘째, 본문에 그림 다섯 장(게이트웨이 구조, AutoCrawler 흐름, 레지스트리 UI, 도구 UI, 데이터 평면)이 있으나 이미지여서 읽지 못했고 위 설명은 본문이 말로 풀어 쓴 범위로 한정했다. 셋째, Omni MCP와 Code Mode가 맥락을 얼마나 줄였는지 수치가 없다. 점진적 발견이 에이전트의 도구 선택 정확도에 미치는 영향도 글이 다루지 않는다.

넷째, 글이 말하지 않는 위험도 있다. LLM이 생성한 도구 설명을 소유자가 검토하는 흐름은 검토가 형식적으로 흐르면 기본 비활성 원칙의 효과가 줄 수 있다. 중앙 게이트웨이는 모든 에이전트 호출이 지나는 단일 지점이어서 장애와 권한 설정 오류의 영향 범위도 크다. 글은 이 부분을 논하지 않으며 위 두 문장은 이 노트의 해석이다.

그럼에도 이 글에서 가져갈 설계 질문은 분명하다. 기존 API를 고치지 않고 도구로 노출하는 번역 계층이 있는가, 자동으로 찾은 것이 소유자의 승인 전에는 켜지지 않는가, 도구 설명이 바뀔 때 승인과 롤백이 있는가, 도구가 수백 개로 늘 때 에이전트가 전부 맥락에 올리지 않고 점진적으로 찾게 하는가, 큰 응답을 맥락에 직접 싣지 않고 파일로 우회하는가.
