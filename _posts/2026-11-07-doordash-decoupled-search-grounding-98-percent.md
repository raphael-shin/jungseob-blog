## TL;DR

- DoorDash는 "450 north" 같은 모호한 검색어가 식당인지 양조장인지 알아내려고 LLM에 검색 근거를 붙인다. 처음엔 모델 회사가 API에 넣어 둔 내장 검색을 썼지만, 어떤 검색을 얼마나 했는지 보이지도 고칠 수도 없었다.
- 그래서 추론하는 모델과 검색하는 일을 떼어 낸 공유 계층 DSG를 만들었다. 모든 에이전트가 MCP 방식의 한 창구로 검색하고, 검색 업체는 설정으로 갈아 끼우고, 결과는 캐시로 재사용하고, 질의마다 비용과 지연을 기록한다.
- 운영 평가에서 DSG는 내장 검색과 정확도가 같거나 조금 높았다. 일반 소매 검색어 7,988개에서 93.90% 대 93.40%였고, 검색 비용은 1천 건당 7.90달러에서 0.11달러로 98% 넘게 줄었다.
- 뜻밖의 발견으로, 내장 검색을 켜면 모델이 "답만 하라"는 지시를 어기고 "검색 결과에 따르면" 같은 설명을 붙였다. 한 벤치마크에서 Claude Sonnet 4는 78.1% 어겼다. DSG는 검색 결과를 별도 도구 응답으로 줘서 이 문제를 줄였다.
- 내장 검색이 늘 나쁜 건 아니다. 최신 정보가 중요한 질문에서는 내장 검색이 모든 모델에서 더 나았다. 결론은 "항상 떼어 내라"가 아니라, 검색을 갈아 끼울 수 있는 선택지로 만들라는 것이다.

## 무슨 글인가

DoorDash 엔지니어링 블로그에 2026년 10월 29일 실린 글이다. 쓴 사람은 생성형 AI 플랫폼 팀의 Amardeep Kumar, Emmanuel Aboah Boateng, Siddarth Kodwani, Kyle MacDonald다. 사이트가 curl을 막아(403) 브라우저로 본문 전체를 읽었다.

DoorDash에는 검색어의 의도를 파악하는 시스템(QIU, query intent understanding)이 있다. 사용자가 모호한 검색어를 넣으면, 상품 목록과 웹 검색 결과를 근거로 무엇을 찾는지 알아낸다. 예를 들어 "450 north"라는 검색어를 근거 없이 모델에 주면 식당으로 분류했다. 그런데 상품 목록과 웹 검색으로 찾아보니 수제 맥주 양조장이었고 시스템은 의도를 "주류"로 정했다. 이 구분에 따라 뒤의 검색이 식당이 아니라 맞는 상품 쪽으로 간다.

## 문제: 내장 검색은 편하지만 보이지 않는다

모델 회사의 내장 검색을 켜면 근거를 붙이기가 아주 쉽다. 요청 하나를 보내면 답 하나가 온다. 그 사이에 무슨 검색을 했는지는 보이지 않는다. 채팅 창이라면 괜찮지만 모델 호출이 파이프라인의 한 단계일 때는 문제가 된다. 글은 문제를 셋으로 나눈다.

첫째, 통제다. 어떤 모델이 추론하고 어떤 검색이 근거를 대는지 사이에 이음매가 없다. 그래서 모델을 바꾸거나 검색 업체의 가격이 바뀌면 모델 연동 코드를 건드려야 한다. 둘째, 재사용이다. 에이전트 두 개가 같은 질문을 하면 검색 비용도 두 번 낸다. 중간에서 가로챌 곳이 없다. 셋째, 관찰과 출력 약속이다. 질의마다 비용과 지연이 보이지 않고 검색을 켜면 엄격한 출력 형식이 깨진다. 글은 이 세 가지가 에이전트마다 따로가 아니라 하나의 공유 계층에 있어야 한다고 말한다.

## 검색을 켜면 말이 많아진다

세 번째 문제가 흥미롭다. DoorDash의 LLM 호출 상당수는 중간 단계다. 출력은 JSON으로 읽히거나 정해진 값 목록과 비교되거나 참/거짓으로 쓰인다. 그래서 프롬프트에 "설명 없이 최종 답만 내라"고 분명히 적는다.

검색 없이는 모델이 잘 따른다. 그런데 내장 검색을 켜면 자주 어긴다. 두 건물의 높이를 비교하며 "최종 답만 내라"고 했더니, 내장 검색은 "검색 결과에 따르면…"으로 시작하는 245자를 돌려줬다. DSG는 "Yes." 세 글자를 돌려줬다. 둘 다 맞는 답이었지만 프로그램이 읽을 수 있는 건 하나뿐이었다.

공개 벤치마크 HotpotQA에서는 Claude Sonnet 4의 내장 검색 답이 "답만 하라"는 지시를 78.1% 어겼다. 글은 이것을 형식만의 문제로 보지 않는다. 검색을 켜면 모델이 아는 것뿐 아니라 행동 방식이 바뀐다는 것이다. DSG에서는 같은 패턴이 보이지 않았다. 검색 결과가 답을 만드는 흐름 안이 아니라 구조화된 도구 응답으로 오기 때문이다.

## DSG의 구조

DSG(Decoupled Search Grounding)는 에이전트와 추론 모델, 그리고 여러 검색 업체 사이에 놓인다. 등록된 검색 업체는 Serper, BrightData, Firecrawl, Exa, Tavily 등이고 모델 회사의 내장 검색도 같은 창구 뒤의 업체 하나로 등록할 수 있다. 모든 에이전트와 모델은 MCP(모델이 외부 도구를 쓰는 표준 방식)와 호환되는 하나의 창구로 검색한다. 어떤 에이전트도 검색 연동을 직접 짜 넣지 않는다.

이렇게 나누면 좋은 점이 넷이다. 추론 모델을 바꿔도 검색 정책은 그대로다. 업체 선택, 실패 시 다음 업체 순서, 캐시 정책, 검색 깊이가 코드가 아니라 설정이 된다. 플랫폼 팀 하나가 모든 에이전트의 검색을 한 번에 다듬는다. 캐시가 에이전트마다 초기화되지 않고 여러 작업에 걸쳐 쌓인다.

검색 요청 하나는 이렇게 처리된다. 먼저 검색어를 정리해, 조금 다르게 쓴 같은 질문이 같은 캐시를 찾게 한다. 정확히 같은 캐시가 있으면 바로 돌려준다. 없으면 뜻이 비슷한 이전 결과를 찾는다. 둘 다 없을 때만 외부 업체에 물어보고 시간 초과나 오류가 나면 자동으로 다음 업체로 넘어간다. 업체마다 다른 결과 모양을 제목, 주소, 본문 조각으로 맞춘다. 결과를 두 캐시에 저장하는데, 최신성이 중요한 질문은 짧게, 잘 안 바뀌는 사실은 길게 보관한다. 마지막으로 구조화된 도구 응답으로 돌려준다. 모든 단계에서 어느 경로로 갔는지, 어느 업체를 썼는지, 지연과 비용이 얼마였는지 기록한다.

새 검색 업체는 코드 수정 없이 YAML 설정 파일 하나로 붙인다. 주소, 요청 양식, 응답 매핑, 비용 정보를 적으면 된다. 캐시는 업체별로 나눠 결과가 서로 덮어쓰지 않게 한다. 글은 이렇게 해서 이제 검색에 돈이 얼마나 드는지 알고 무엇에 어떻게 썼는지 보여 주는 대시보드가 생겼다고 말한다.

## 결과

공개 벤치마크에서 DSG를 내장 검색과 비교했다. 모델은 GPT-4o, GPT-4o-mini, Gemini 2.5 Flash, Gemini 2.5 Pro, Claude Sonnet 4 다섯 개, 벤치마크는 공개 질의응답 셋이다. DSG 구성은 정확도 83~86%로, 내장 검색의 87.7%와 비슷하면서 비용은 약 10~30배 낮았다. BrightData를 쓴 DSG는 내장 검색과 정확도 차이가 1.6점 이내였고 비용은 약 11배 낮았다. Serper를 쓴 DSG는 검색을 안 쓸 때보다 확실히 나으면서 가장 싼 구성으로, 1천 건당 70센트가 안 됐다.

예외도 있다. 최신 정보가 중요한 질문을 모은 FreshQA에서는 다섯 모델 모두 내장 검색이 DSG보다 나았다. 모델 회사의 검색은 최신성과 색인에서 범용 검색 API가 늘 따라가지 못하는 강점이 있다. 그래서 글의 결론은 "항상 떼어 내라"가 아니라, 검색을 경로 선택의 문제로 만들고 내장 검색도 같은 창구 뒤의 선택지 하나로 두라는 것이다.

운영 평가는 의도 파악 시스템으로 했다. 일반 비식품 소매 검색어 7,988개와 합성한 드문 검색어 2,335개다. 추론 모델은 Gemini Flash였고 비교 대상인 내장 검색은 Google 검색이 통합된 Gemini Flash로, 가장 강한 내장 검색 중 하나다. 비용은 검색 업체 요금만 셌고 모델 추론 비용은 뺐다.

| 평가 세트 | 내장 검색 정확도 / 1천 건당 비용 | DSG 정확도 / 1천 건당 비용 |
|---|---|---|
| 일반 소매 (7,988개) | 93.40% / 7.90달러 | 93.90% / 0.110달러 |
| 드문 검색어 (2,335개) | 87.62% / 10.37달러 | 87.79% / 0.146달러 |

글은 갈아 끼울 수 있는 범용 검색으로 가장 강한 내장 검색을 따라잡았다는 점이, 통제권을 밖으로 빼도 품질을 잃지 않는다는 뜻이라고 본다.

캐시 효과도 크다. 처음 돌릴 때는 캐시 적중률이 6.2%, 1천 건당 0.7385달러, 평균 4,570ms였다. 캐시가 데워진 뒤에는 적중률 99.4%, 1천 건당 0.0045달러, 평균 1,465ms였다. 지연이 68% 줄고 검색 비용은 사실상 0이 됐다. 캐시를 공유하니 더 많은 작업이 이 창구를 지날수록 더 빨리 데워진다.

검색 깊이도 이제 직접 정하는 값이 됐다. SimpleQA에서 세 모델 평균으로, 가져오는 결과를 2개에서 6개로 늘리자 정확도가 78.7%에서 84.9%로 6.2점 올랐다. 10개로 더 늘리자 0.6점만 더 올라 85.5%가 됐다. 그래서 근거 있는 기본값을 정하고 필요하면 깊이를 지연이나 비용과 맞바꿀 수 있다.

## 한계

글은 DSG가 내장 검색을 쓸모없게 만들지 않는다고 분명히 한다. 한계는 셋이다. 첫째, 이제 안정성, 지연, 데이터 품질을 외부 검색 업체에 기댄다. 업체 가격이 바뀌면 이번에 잰 거래 조건도 바뀐다. 그래서 오래가는 결과는 가격이 아니라 창구라고 글은 말한다. 둘째, 여러 단계로 추론해야 하는 질문은 한 번 찾는 질문보다 덜 좋아진다. HotpotQA에서는 어느 검색이든 개선이 작았다. 깊은 추론에는 한 번의 검색이 아니라 반복 검색이 필요할 것이다. 셋째, 검색 때문에 말이 많아지는 문제는 줄었지만 풀린 건 아니다. 이를 체계적으로 잡으려면 창구에서 출력 형식을 검사하는 장치가 필요하다. 다음 계획은 질의마다 깊이와 업체를 배우는 적응형 경로 선택, 출력 형식 검증, 여러 단계 질문을 위한 반복 검색이다.

## 확인해 본 것

표의 숫자로 98%를 계산해 봤다. 일반 소매는 7.90달러에서 0.110달러로 약 98.6%, 드문 검색어는 10.37달러에서 0.146달러로 약 98.6% 줄었다. 제목의 "98%"와 맞다. 캐시 표의 0.7385달러에서 0.0045달러도 99% 넘게 줄었다. 다만 이 수치는 모두 DoorDash가 자기 평가로 낸 것이고 외부에서 재현한 자료는 없다. 비용에 모델 추론 비용은 빠져 있다는 점도 글이 밝힌다.

## 읽을 때 생각할 점

"98% 절감"은 검색 업체 요금만의 이야기다. 전체 LLM 비용에서 검색이 차지하는 몫이 크지 않다면, 전체 절감은 훨씬 작을 수 있다. 또 내장 검색은 모델 호출 요금에 묶여 있고 DSG는 범용 검색 API 요금이라, 업체 가격이 바뀌면 숫자도 바뀐다. 글 스스로 오래가는 결과는 가격이 아니라 구조라고 말한다.

이 글의 더 큰 교훈은 구조에 있다. 추론과 검색은 서로 다른 속도로 바뀐다. 둘을 떼어 내면 각각을 따로 개선하고 작업마다 품질, 최신성, 지연, 비용의 균형을 고를 수 있다. 출력 형식이 깨지는 문제처럼, 편한 내장 기능이 파이프라인 안에서는 예상 못 한 부작용을 낼 수 있다는 점도 기억할 만하다.

내 일에 가져올 질문은 이렇다. 우리 파이프라인의 LLM 호출 중 모델 회사의 내장 기능에 묶여 비용과 동작이 보이지 않는 것은 무엇인가? 여러 에이전트가 같은 외부 호출을 각자 하고 있지는 않은가? 도구를 켰을 때 모델이 출력 형식을 어기지는 않는지 재 본 적이 있는가?
