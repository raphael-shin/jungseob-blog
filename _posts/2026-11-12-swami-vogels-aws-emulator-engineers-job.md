## TL;DR

- Swami는 약 20년 전 Amazon 초기 엔지니어 Al Vermeulen과 Paxos 기반 분산 잠금 서비스 Alf를 만들었다. Alf는 지금도 S3, DynamoDB 같은 복잡한 분산 시스템을 떠받친다. 분산 시스템은 시험하기 어려워서, 그들은 서버와 네트워크와 기반 시설을 JVM 하나 안에 시뮬레이션해 패킷을 떨어뜨리고 사건 순서를 일부러 바꾸며 동시성 버그 대부분을 실제 서버에 올리기 전에 잡았다.
- 그 방법은 작은 팀이 시스템 하나의 환경을 손으로 복제할 수 있을 때 통했다. 지금 AWS 서비스는 200개가 넘고, 에이전트는 어떤 팀이 운영에서 확인할 수 있는 것보다 훨씬 빨리 코드를 쓴다. 그래서 에이전트가 그 테스트 환경을 스스로 만들고 시험할 수 있는지 알고 싶었다.
- AWS Emulator는 그 답이다. 에이전트는 Smithy로 쓴 공개 API 모델에서 끝에서 끝까지의 충실도 테스트를 짜고, 실제 AWS에서 통과할 때까지 고친 뒤, 같은 테스트를 통과하도록 에뮬레이터를 만든다. 400개 넘는 API 모델로 200개 넘는 서비스를 다루고, 내 컴퓨터에서 무료로 오프라인으로 돈다.
- 코딩 에이전트는 쓰고, 돌리고, 결과를 읽는 고리로 일한다. 분산 시스템에서는 그 고리가 기반 시설 안에서 돌아서, 부르는 서비스가 진짜처럼 동작해야 에이전트가 자기 일을 확인하고 첫 시도에 맞는 코드를 낸다. AWS Emulator는 그 기반 시설을 고리 안, 내 컴퓨터로 가져온다.
- 그는 Alf의 복제 엔진을 Kiro로 다시 만들어 봤다. 처음에 넉 달 걸린 일이었는데, 에이전트가 결과를 확인할 방법이 없음을 알기까지 나흘 밤을 감독했고, 명세와 테스트 환경을 주자 두 시간 만에 끝났다. 그래서 그는 엔지니어의 일이 에이전트가 스스로 일할 공간을 주고, 그 일이 맞는지 정하는 명세와 테스트와 병합 관문을 짓는 것이라고 말한다.

## 무슨 글인가

Amazon CTO Werner Vogels의 블로그 All Things Distributed에 2026년 11월 11일 실린 글이다. 앞부분은 Vogels의 짧은 소개이고 본문은 Swami Sivasubramanian의 기고다. 본문 약 1,700단어를 끝까지 읽었다. 같은 날 About Amazon에 실린 Matthew Goldberg의 출시 글은 [따로 정리했다](https://raphael-shin.github.io/jungseob-blog/posts/goldberg-agents-built-aws-emulator/). 이 노트는 GitHub 저장소와 글이 링크한 다른 글을 열지 않았다.

## Vogels의 소개

Vogels는 2004년 Amazon에 들어와 한 달쯤 됐을 때 인턴 한 명을 고를 기회가 있었다고 회상한다. 그는 이미 암스테르담 자유대학교에서 박사 과정을 밟던 뛰어난 젊은이 이야기를 들었다. 그 자신도 그 학교에서 박사 학위를 받았다. 그는 곧바로 Swami를 골랐고 22년 동안 Amazon CTO로 내린 결정 중 가장 좋은 결정 하나였다고 말한다.

2004년 크리스마스에 상용 관계형 데이터베이스가 Amazon의 규모를 감당하지 못하는 재앙이 있었다. Vogels는 Swami에게 Amazon에서 관계형 데이터베이스가 실제로 어떻게 쓰이는지 깊이 파 보라고 했다. 데이터베이스 작업의 70%가 관계형이 아니라 키-값이었다. 그 통찰이 Dynamo로 이어졌고 Swami가 그 설계를 도왔다. Vogels는 인턴십이 끝나자 박사 학위를 마치기도 전에 그를 정규직으로 뽑았다. 그는 이후 Swami가 AWS 데이터 전략의 주요 설계자가 됐고 최근에는 Amazon의 AI 혁신을 이끈 지적 동력 중 하나였다고 소개한다.

## Alf: Paxos 위의 분산 잠금 서비스

Swami는 AWS Emulator 출시가 그의 경력 초기의 한 프로젝트와 이어진다고 말한다. 약 20년 전 Vogels는 그에게 Amazon 초기 엔지니어 Al Vermeulen과 함께 "Alf"라는 분산 잠금 서비스를 만들게 했다. Alf는 Paxos 위에 지었다. Paxos는 레슬리 램포트의 연구에 기댄 프로토콜로, 서버 무리가 값 하나에 합의하게 한다. Alf 안의 복제 엔진은 서버 사이의 데이터 사본을 일관되게 유지했다. 그는 Alf가 지금도 S3, DynamoDB 같은 복잡한 분산 시스템을 떠받치는 서비스라고 말한다. 그 위에 많은 변화가 더해졌는데, 그건 다른 글로 미룬다고 한다.

## 분산 시스템은 시험하기 어렵다

Paxos는 분산 시스템 합의 프로토콜의 표준이고 학계에서는 잘 이해돼 있었다. 하지만 Amazon과 AWS가 커 가던 규모에서 그것을 짓기는 쉽지 않았다. 서버와 데이터센터 사이의 복제만이 아니라, 수만 개의 클라이언트가 동시에 잠금을 요청하고 네트워크가 갈라진 동안에도 임대를 갱신하는 상황을 다뤄야 했다. 핵심 요구 사항은 하나였다. 언제나 맞아야 한다.

당시 분산 시스템을 시험하는 최선의 방법은 대규모 시스템 테스트와 카오스 테스트였다. 둘 다 통했지만 비쌌고 많은 상황을 원할 때 재현하지 못했다. 그건 Alf에게 중요했다. Alf는 모든 클라이언트에게 강하게 일관된 진실을 주는 진실의 저장소였고 서버 장애와 패킷 손실 중에도 계속 돌아야 했다. 업계 논문 여러 편이 Paxos 기반 잠금 서비스는 제대로 만들기 어렵다고 썼고 시험의 어려움이 그 이유 중 하나였다.

그들은 Alf의 환경을 가능한 한 충실하게 시뮬레이션해서 이 문제를 풀었다. 서버를 JVM 안에서 돌리고 네트워크와 서버가 기대는 나머지 기반 시설을 시뮬레이션해서, 시스템 전체가 그들이 통제하는 프로그램 하나 안에 살게 했다. 원할 때마다 패킷을 떨어뜨리고 다른 장애를 주입할 수 있었고 시뮬레이션을 찔러 버그와 확장성 문제를 찾는 도구도 만들었다. 동시성 버그는 사건이 특정 순서로 일어날 때만 나타나는데, 시뮬레이션에서는 그런 순서를 일부러 많이 만들고 Alf가 각각을 어떻게 다루는지 볼 수 있었다. TLA+ 같은 이론적 기법으로 형식적 추론도 했고 그것도 많은 문제를 찾았다. 이렇게 시험해서 Alf의 동시성 버그 대부분을 실제 서버에서 돌리기 전에 잡았다. 그 뒤 실제 환경에서 시험하자 다른 문제들이 나왔다. 실제 세계는 시뮬레이션이 드러내지 못하는 것을 드러내기 때문이다.

## 손으로 짓는 테스트 환경의 한계

시뮬레이션과 형식적 추론은 둘 다 적용한 분산 시스템의 품질을 높였다. 시뮬레이션이 통한 건 작은 팀이 시스템 하나의 환경을 손으로 복제할 수 있었고 당시 AWS에는 서비스가 몇 개뿐이었기 때문이다. 하지만 지금 AWS에는 서비스가 200개 넘게 있고 AWS를 부르는 애플리케이션은 쓰는 서비스마다 테스트 환경이 필요하다. 그 모두를 손으로 지으려면 몇 년의 엔지니어링이 든다. 게다가 에이전트는 이제 어떤 팀이 운영에서 확인할 수 있는 것보다 훨씬 빨리 코드를 쓴다. 그래서 그들은 에이전트가 그 환경을 스스로 짓고 시험할 수 있는지 알고 싶었다.

## 명세와 진짜 서비스만 있으면

아이디어는 AWS 개발자 도구 팀의 수석 주임 엔지니어 Matt Goldberg에게서 나왔다. 그의 가설은, 서비스가 어떻게 동작해야 하는지 적은 설명과 확인할 진짜 서비스가 주어지면 에이전트가 그 서비스의 동작하는 버전을 스스로 만들 수 있다는 것이었다. AWS에서 적힌 설명은 공개 API 모델 모음이다. Smithy, 곧 서비스의 작업과 입력, 출력, 오류를 기술하는 AWS의 형식으로 쓰였다. 확인할 진짜 서비스는 고객이 쓰는 바로 그 AWS 클라우드다.

에이전트는 충실도 테스트로 일한다. 공개 API 모델에서 짜낸 끝에서 끝까지의 고객 시나리오다. 예를 들어 SQS에서 받은 메시지가 가시성 제한 시간이 끝날 때까지 다른 읽는 쪽에게 숨겨지는지 확인하는 테스트가 있다. 에이전트는 각 테스트가 실제 AWS에서 통과할 때까지 고치니, 테스트는 AWS가 어떻게 동작하는지를 기록한다. 그다음 같은 테스트를 통과할 때까지 에뮬레이터를 만들고 아직 실패하는 테스트는 에뮬레이터의 빈틈을 가리킨다. Goldberg는 SQS 하나로 시작했고 이 방식을 설명한 프롬프트 하나를 Kiro에 주자 약 15분 만에 쓸 만한 SQS 에뮬레이터 첫 버전이 나왔다.

AWS Emulator의 코드는 모두 에이전트가 쓰고 시험했다. 400개가 넘는 API 모델로 200개가 넘는 AWS 서비스를 다룬다. 내 컴퓨터에서 무료로, 오프라인으로 돈다. 에이전트 팀이 실제 AWS에 대해 시험하고 찾은 빈틈을 고친다. 모든 변경은 병합 관문을 지난다. 코드베이스에 들어가기 전에 모든 변경이 통과해야 하는 촘촘한 자동 검사 모음이고 여러 보안 에이전트의 적대적 리뷰가 들어 있다.

## 코딩 고리 안의 기반 시설

코딩 에이전트는 고리로 일한다. 코드를 쓰고 돌리고 결과를 읽은 뒤 다음에 무엇을 바꿀지 정한다. 분산 시스템에서는 그 고리가 기반 시설 안에서 돌기 때문에, 부르는 서비스가 진짜처럼 동작해야 한다. 그러면 에이전트가 쓰면서 자기 일을 확인할 수 있고 첫 시도에 맞는 코드를 훨씬 자주 내서 소프트웨어 품질이 오른다. Swami는 AWS Emulator가 그 기반 시설을 내 컴퓨터의 고리 안으로 가져온다고 말한다.

## 엔지니어의 일

에이전트가 코드를 쓰고 자기 일을 확인할 때, 엔지니어의 일은 에이전트가 스스로 일할 공간을 주고 그 일이 언제 맞는지 정하는 명세와 테스트와 병합 관문을 짓는 것이라고 그는 말한다. 그는 이것을 어렵게 배웠다. Al과 함께 Alf용으로 지었던 복제 엔진을 Kiro로 다시 만들어 본 것이다. 처음에는 넉 달쯤 걸린 일이었다. 그는 나흘 밤 동안 에이전트를 감독한 뒤에야 에이전트가 결과를 확인할 방법이 없다는 걸 알았다. 명세와 테스트 환경을 주자 다시 만드는 데 약 두 시간이 걸렸다.

AWS Emulator를 만든 에이전트들은 처음부터 둘 다 있었다. 공개 API 모델과 실제 AWS다. 엔지니어 한 명이 그들을 돌리는 발판을 지었다. 내부 버전은 주말에 만들어졌고 한 달 안에 쓰이기 시작했다. 그것을 튼튼한 해법으로 바꾸는 데는 훨씬 더 많은 일이 들었다.

그는 AI 시대의 소프트웨어 품질이 엔지니어가 에이전트 주위에 설계하는 안전장치에 달렸다고 말한다. AWS Emulator에서 그 안전장치는 셋이다. 실제 AWS로 검증한 충실도 테스트, 일반 코드 리뷰어와 함께 여러 보안 에이전트가 저마다 다른 공격 방식으로 변경을 리뷰하는 병합 관문, 그리고 에이전트가 건드려서는 안 될 코드를 건드리지 못하게 막는 결정적 검사다. 그는 대부분의 소프트웨어를 에이전트가 짓고 확인하고 무엇을 지을지와 일이 언제 맞는지는 엔지니어가 정하게 될 거라고 본다. 엔지니어가 에이전트 팀을 이끌어 믿을 만한 고품질 소프트웨어를 짓는 법은 아직 배우는 초기이고 AWS Emulator가 생겨난 과정이 그 좋은 예라고 그는 말한다. 안전장치를 계속 더하고 에이전트가 짓는 방식을 다듬어 갈 것이라고 덧붙인다.

출시 시점의 사실도 정리한다. 에뮬레이터 코드는 퍼블릭 도메인 헌정인 CC0로 공개됐다. 전체 커밋 이력과 에이전트가 올린 모든 이슈가 GitHub 저장소에 있고 "things-that-do-not-work" 폴더에는 에이전트가 찾았지만 아직 실제 AWS와 맞지 않는 동작을 적은 이슈가 있다. 더 자세한 내용은 re:Invent에서 나누겠다고 한다.

## 읽을 때 생각할 점

이 글은 AWS의 리더가 자사 출시를 자기 경험과 엮어 쓴 기고다. "나흘 밤 대 두 시간"은 그의 개인 경험이고 다시 만든 복제 엔진이 원래 것과 같은 품질인지는 글에 나오지 않는다. 에뮬레이터의 충실도가 실제로 얼마인지도 숫자로 나오지 않는다. 그 스스로 실제 환경은 시뮬레이션이 드러내지 못하는 걸 드러낸다고 썼듯, 에뮬레이터를 통과한 코드도 실제 AWS에서 다시 확인해야 할 것이다.

그래도 이 글은 이 블로그가 다룬 여러 노트를 하나로 묶는다. "확인할 방법이 없으면 에이전트를 아무리 감독해도 안 되고, 명세와 테스트가 있으면 두 시간이면 된다"는 그의 경험은 [Lance Martin 노트](https://raphael-shin.github.io/jungseob-blog/posts/lance-martin-old-prompts-making-claude-worse/)의 "Claude가 올라갈 수 있는 평가를 만들어라", [허사비스 30년 노트](https://raphael-shin.github.io/jungseob-blog/posts/sixsigma-hassabis-simulation-thirty-years/)의 "검증할 수 있는 분야에서 자기 개선이 된다"와 같은 원리를 한 엔지니어의 하룻밤 이야기로 보여 준다. 20년 전 서버와 네트워크를 한 프로그램 안에 시뮬레이션해 시험한 이야기는, 허사비스가 게임과 지니로 가상 세계부터 만드는 방식과도 닮았다. 엔지니어의 일이 명세와 테스트와 관문을 짓는 것이라는 결론은 [Warp의 공장 엔지니어링 노트](https://raphael-shin.github.io/jungseob-blog/posts/lloyd-warp-self-improving-software-factory-infrastructure/)와 [Glazner 노트](https://raphael-shin.github.io/jungseob-blog/posts/glazner-on-being-an-engineer-in-2026/)가 말한 사람의 몫과 겹친다.

내 일에 가져올 질문은 이렇다. 내가 에이전트를 붙잡고 감독하는 일 중, 에이전트가 결과를 스스로 확인할 방법이 없는 일은 무엇인가? 그 일에 명세와 테스트 환경을 먼저 줄 수 있는가? 우리가 쓰는 외부 서비스를 에이전트의 고리 안에서 진짜처럼 시험할 방법이 있는가?
