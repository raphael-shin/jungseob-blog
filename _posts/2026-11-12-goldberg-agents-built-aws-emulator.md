## TL;DR

- AWS Emulator는 AWS 서비스를 내 컴퓨터에서 흉내 내 AWS 애플리케이션을 만들고 시험하게 해 주는 로컬 에뮬레이터다. 코드 전부를 자율 에이전트가 썼고, 팀은 코드를 하나도 쓰거나 리뷰하지 않았다. 소스 코드는 GitHub에 CC0로 공개됐다.
- 출발은 주말 실험이었다. 명세와 기준 구현이 있으면 에이전트가 스스로 만들 수 있다는 생각에서, Goldberg는 공개 AWS API 모델을 명세로, 실제 AWS를 기준 구현으로 삼았다. Kiro에 프롬프트 하나를 주자 15분 만에 쓸 만한 SQS 첫 버전이 나왔고, 주말 동안 나머지 AWS를 만들어 팀이 월요일부터 썼다.
- 에뮬레이터는 세 에이전트 팀이 만든다. 한 팀은 실제 AWS로 검증한 수만 개의 충실도 테스트를 관리하고, 한 팀은 그 테스트를 다시 돌려 에뮬레이터의 어긋남을 찾아 이슈로 올리고, 한 팀은 이슈 하나씩 받아 고친다. 범위가 정해진 일에서 에이전트가 더 잘하기 때문에 나눴다.
- 고친 변경은 병합 관문을 통과해야 한다. 컴파일 확인, 코딩 표준 리뷰, 보안 확인, 충실도 퇴행 검사를 다 거쳐야 메인에 합쳐지고, 하나라도 실패하면 되돌아간다. 수백 개 에이전트가 동시에 일하며 하루 수천 개 이슈를 고친다.
- 그는 에이전트가 말을 안 듣는 건 나쁜 뜻이 아니라 능력 부족이라며, 에이전트에게는 "색칠 공부 책"이 필요하다고 말한다. 잘 정해진 칸, 곧 안전장치가 있어야 에이전트가 혼자 일할 공간을 얻고, 사람은 선 밖으로 나가지 않는다는 믿음을 얻는다.

## 무슨 글인가

AWS 개발자 도구 팀의 수석 주임 엔지니어 Matthew Goldberg가 About Amazon에 2026년 11월 11일 쓴 글이다. 일반 요청으로는 본문이 다 보이지 않아, 받은 HTML에서 본문을 직접 뽑아 끝까지 읽었다. 글 중간에 끼어 있는 다른 기사 소개는 옮기지 않았다. 그림은 설명 문장만 봤다. 같은 날 Werner Vogels의 블로그에 실린 Swami Sivasubramanian의 글은 [따로 정리했다](https://raphael-shin.github.io/jungseob-blog/posts/swami-vogels-aws-emulator-engineers-job/). 그는 이 글을 다중 에이전트 워크플로 설계, 충실도 측정, 품질과 보안 기준을 다룰 연재의 첫 편이라고 밝힌다.

## 색칠 공부 책

그는 자신이 형편없는 화가라고 고백하며 시작한다. 부모가 그를 1년 일찍 유치원에 보냈다. 어느 날 선생님이 긴 탁자에 커다란 종이를 펼치고 공룡이 살던 지구를 그려 보라고 했다. 그는 자기 칸을 열심히 그렸지만 반에서 가장 어려 크레용을 제대로 쥘 만큼 손이 자라지 않았다. 몇 분 뒤 친구들이 그에게 소리를 질렀다. 다 잘못 그렸기 때문이다.

그는 올해 그 친구들을 자주 떠올렸다고 말한다. 친구들이 그에게 화를 냈듯, 그도 AI 에이전트에게 인정하기 싫을 만큼 자주 욕을 했다. 하지만 어느 쪽도 나쁜 뜻이 아니었다. 에이전트는 그를 거역하려는 게 아니었고 그도 그림을 망치려던 게 아니었다. 능력이 모자랐을 뿐이다. 올해 그는 연인과 색칠 공부 책 한 권을 몇 시간 동안 함께 칠했다. 잘 정해진 칸을 채우면 큰 그림이 완성된다는 걸 아는 데서 오는 편안함이 있었다. 그는 에이전트에게도 색칠 공부 책이 필요하다고 말한다.

그래서 AWS Emulator가 나왔다. 내 컴퓨터에서 돌려 AWS 애플리케이션을 만들고 시험하는 로컬 에뮬레이터이고 전부 자율 에이전트가 썼다. 팀은 코드를 하나도 쓰거나 리뷰하지 않았다. 그게 가능했던 건 그들이 세운 안전장치 덕이라고 그는 말한다. 안전장치가 에이전트에게는 혼자 일할 공간을, 사람에게는 에이전트가 선 밖을 칠하지 않는다는 믿음을 줬다.

## 주말 실험에서 시작했다

올해 초 Anthropic 연구진은 AI 에이전트가 C 컴파일러를 스스로 만들 수 있다는 걸 보였다. 그에게는 번뜩이는 순간이었다. 잘 정해진 명세와 기준 구현이 주어지면, 에이전트가 그 명세를 충실히 구현하는 해법을 스스로 만들 수 있다는 것이다. AWS에는 둘 다 있다. AWS API 모델이 명세이고 실제 AWS 클라우드가 기준 구현이다.

가설을 시험하려고 그는 생각할 수 있는 가장 단순한 프롬프트를 Kiro에 줬다. 될 거라는 기대도 없었다. AWS 명령줄 도구(CLI)를 바탕으로 테스트를 써라. 그 테스트가 실제 AWS에서 통과할 때까지 고쳐라. 같은 테스트가 통과하는 메모리 안의 구현을 만들어라. Kiro는 15분 뒤 쓸 만한 Amazon SQS 첫 버전을 들고 왔다. 그는 프롬프트를 다듬어 주말 동안 Kiro에게 나머지 AWS를 만들게 했고 실제로 해냈다. 빈틈은 당연히 있었지만 팀이 그 월요일부터 자기 소프트웨어를 시험하는 데 쓸 만큼은 설득력이 있었다.

그것을 튼튼한 제품으로 만드는 데는 주말보다 훨씬 더 걸렸다. 그는 요즘 이런 결과를 보고 AI가 무엇이든 만들 수 있다고 믿고 싶은 자연스러운 유혹이 있다고 말한다. 언젠가는 그럴지 모른다. 하지만 고객의 손에 쥐여 줄 자신이 있는 무언가를 만드는 데는 여전히 진지한 엔지니어링이 필요하다. AWS Emulator에서 그것은 에이전트가 선 안에서 칠하게 하는 안전장치를 짓는 일이었다.

## 세 에이전트 팀

AWS Emulator는 근본적으로 세 에이전트 팀이 만든다. 한 팀은 테스트 모음을 관리하고 한 팀은 에뮬레이터의 문제를 찾고 한 팀은 그 문제를 고친다. 그들은 에이전트가 범위가 정해진 일에서 더 잘한다는 걸 알게 돼 책임을 이렇게 나눴다.

첫 팀의 테스트 모음은 실제 AWS 클라우드에 대한 충실도를 잰다. 각 테스트는 실제 AWS 시나리오다. 예를 들어 SQS 테스트는 큐를 만들고 메시지를 보내고 받고 확인하고 큐를 지우는 과정을 담는다. 에이전트는 공개된 AWS API 모델에서 이런 테스트를 짜내고 제출 전에 실제 AWS로 하나하나 검증한다. AWS 전체에 걸쳐 수만 개의 충실도 테스트가 있고 에이전트가 AWS로 할 수 있는 새 일을 찾을 때마다 계속 늘어난다. 그는 이것이 시스템의 가장 근본적인 안전장치라고 말한다. 에이전트가 맞춰야 할 모호하지 않은 목표를 주고 AWS를 다시 부르지 않고도 몇 번이고 다시 돌릴 수 있기 때문이다.

둘째 팀은 충실도 테스트를 다시 돌려 에뮬레이터의 어긋남을 찾는다. 시스템이 처음 저장소를 만들었을 때는 438개 AWS API 모델의 요청을 받기만 하고 아무것도 하지 않는 빈 웹 서버였다. 에이전트들이 저장소에 몰려들어 무엇이 안 되는지 알아낸다. 처음 이슈는 그저 "SQS 첫 버전을 만들어라"였다. 서비스가 자리를 잡으면 에이전트는 충실도 테스트를 다시 돌리고 실패한 테스트마다 이슈를 올린다. 실패를 따져 보고 같은 원인일 수 있는 실패를 묶으라는 지시를 받는다.

셋째 팀의 에이전트는 이슈 하나씩을 받아 그것만 고친다. 코드를 받아 원인을 찾고 해결될 때까지 코드를 고친다. 그리고 그 변경이 기준을 넘는지 확인하는 관문을 통과해야 한다.

## 병합 관문

이 관문은 당연히 컴파일되지 않는 변경을 막는다. 거기에 더해 코딩 표준에 맞춰 리뷰하는 에이전트, 코드가 안전한지 확인하는 에이전트, 변경이 충실도를 퇴행시키지 않았는지 확인하는 에이전트가 있다. 하나라도 실패하면 변경은 다시 작업하라고 에이전트에게 돌아간다. 모두 통과하면 메인에 합쳐진다. 수백 개 에이전트가 동시에 코드베이스에서 일하며 하루 수천 개 이슈를 고친다고 그는 말한다. 그리고 이 병합 관문이 없으면 에이전트가 만드는 걸 믿지 못할 것이라고 덧붙인다. 그래서 관문을 최적화하는 데 많이 신경 쓴다. 에이전트가 얼마나 빠르고 믿을 만하게 만드는지가 거기에 달렸기 때문이다.

## GitHub로 내보내기

메인에 합쳐진 변경은 전부 AWS 개발자 도구로 지은 배포 파이프라인을 따라간다. 에이전트의 주 코드 저장소는 AWS CodeCommit이다. 커밋은 보통 여러 개 쌓여 다시 빌드하고 시험한 뒤 배포 브랜치에 합쳐진다. 그다음 에뮬레이터를 내려받을 수 있는 실행 파일로 묶는다. 코드를 GitHub에 공개하는 건 배포 과정의 맨 끝이다.

코드를 공개하는 이유는 에이전트가 수천 커밋에 걸쳐 무엇을 했는지 볼 수 있게 하려는 것이다. 올라온 모든 이슈가 저장소에 있다. 고친 것은 "issues/things-that-now-work" 폴더에, 남은 것은 "issues/things-that-do-not-work" 폴더에 있다. 그는 파 보면 흥미로운 게 많다고 말한다. 그들은 만드는 기계를 다듬으며 에이전트에게 이 에뮬레이터를 여러 번 만들게 했다. 그가 가장 좋아하는 건 예전 버전에서 에이전트들이 AWS Lambda 함수를 지원하려고 자기만의 Python 인터프리터를 만들기로 한 일이다. 그 뒤로 기존 라이브러리를 다시 쓰라는 안내를 줬다. 그는 색칠 공부 책이 필요 없는 사람에게는 당연해 보일 일이라고 웃는다. 그래도 결과를 믿는 건 안전장치 덕이라고 말한다. 이 역사에서 얻은 통찰이, 소프트웨어를 크리에이티브 커먼즈 CC0, 곧 퍼블릭 도메인으로 내놓기로 한 주된 이유였다.

## 읽을 때 생각할 점

이 글은 AWS가 자기 제품 출시를 알리는 글이고 숫자는 모두 자체 보고다. "수만 개의 충실도 테스트", "하루 수천 개 이슈", "수백 개 에이전트"는 정확한 수치가 아니다. 에뮬레이터가 실제 AWS와 얼마나 같은지, 곧 충실도 테스트의 통과율은 이 글에 나오지 않는다. 그는 충실도를 어떻게 재는지 다음 편에서 다루겠다고 한다. 저장소의 "things-that-do-not-work" 폴더가 아직 맞지 않는 동작을 공개한다는 점은 정직한 장치다. 이 노트는 GitHub 저장소를 열어 보지 않았다.

그래도 구조는 이 블로그가 다룬 여러 사례와 맞물린다. "명세와 기준 구현이 있으면 에이전트가 스스로 만든다"는 출발점은 [Fable 5.2 에이전트 1,000개 노트](https://raphael-shin.github.io/jungseob-blog/posts/anthropic-fable-5-2-thousand-agents-fermat-proof/)의 Lean 검사기, [허사비스 30년 노트](https://raphael-shin.github.io/jungseob-blog/posts/sixsigma-hassabis-simulation-thirty-years/)의 "검증할 수 있는 분야에서 자기 개선이 잘 된다"와 같은 원리다. 여기서는 실제 AWS가 정답지 노릇을 한다. 범위가 정해진 일로 나눈 세 팀과 병합 관문은 [Factory Missions 노트](https://raphael-shin.github.io/jungseob-blog/posts/alvoeiro-factory-missions-multi-agent-architecture/)의 작업자와 검증자를 닮았다. 다만 Missions가 코드를 바꾸는 일을 한 번에 하나씩 돌린 반면, 여기서는 수백 개 에이전트가 동시에 고치고 병합 관문이 충돌과 퇴행을 거른다.

내 일에 가져올 질문은 이렇다. 우리가 에이전트에게 맡기려는 일에는 명세와, 그 명세를 확인할 기준 구현이 있는가? 에이전트의 변경이 메인에 들어가기 전에 통과해야 하는 관문에는 무엇이 들어 있는가? 아직 안 되는 것을 숨기지 않고 기록하는 곳이 있는가?
