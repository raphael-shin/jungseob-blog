## TL;DR

- Kiro 팀은 Kiro CLI가 에이전트 하네스(컨텍스트 창에 무엇을 얼마나 넣을지, 대화를 압축하고 세션을 저장하고 도구 승인을 처리하는 코드)의 함수 26개를 Lean 4로 모델링하고 속성 96개를 검토하게 했다. 결과는 70개 증명, 2개 유한 범위 검사, 18개 반증 뒤 재현, 6개 부분 결과나 관찰이다.
- 방법의 핵심은 증명만 믿지 않는 것이다. Lean 모델을 컴파일해 TypeScript, Rust, Python 실제 코드와 약 9만 8천 건의 무작위 입력으로 대조하고, 반례는 실제 코드에서 재현해야 발견으로 센다.
- 증명된 속성의 예는 중복 파일 제거가 이전 턴의 요청 접두부를 바꾸지 않는다, 하위 에이전트의 권한이 부모보다 느슨해지지 않는다, 한 작업을 새 작업자가 가져간 뒤 이전 작업자의 쓰기가 막힌다는 것이다. 반례의 대표는 취소했는데 다시 실행되는 일회성 작업이다.
- 18개 발견 중 15개는 컨텍스트와 권한과 상태 기계 영역에 있고, 대부분 UTF-16과 UTF-8, 파일 경로와 글롭처럼 두 표현의 경계에서 나왔다. 보안 취약점으로 분류된 것은 없다.
- 증명은 모델에 대한 것이고 모델과 코드의 일치는 표본 입력으로만 확인한다. 수치는 Kiro 팀의 내부 실험 결과이며 분석 대상 저장소 중 둘은 비공개다.

## 글에 대하여

Kiro 블로그에 2026년 11월 2일 게시된 글로, 저자명은 페이지에 따로 적혀 있지 않다. Kiro의 컨텍스트 관리 팀이 쓴 글이며 영어 본문을 전부 읽었다. 표 1(검증 결과 표)은 수집한 페이지 본문에 포함되지 않아 읽지 못했고 본문 서술의 수치로 대신 확인했다. 같은 팀의 [Kiro 소프트웨어 공장 안정성 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-software-factory-stability-1000-prs/)와 [Kiro 프런티어 엔지니어링 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-frontier-engineering/)가 같은 제품의 다른 면을 다룬다.

## 무엇을 왜 증명했나

하네스 코드의 버그는 테스트로 잡기 어렵다. 입력을 모델이 고르고 동시 이벤트의 순서에 좌우되며 여러 턴과 재시작에 걸쳐 쌓인 상태에 의존하고 조용히 실패해 모델이 조금 틀린 컨텍스트로 일하기 때문이다. 일반 테스트는 사람이나 생성기가 떠올린 입력만 확인하지만 에이전트에서는 입력 대부분이 모델과 모델이 읽는 파일에서 오므로 훨씬 넓은 경우에 닿는다. 잘림, 읽기 전용 검사, 허용 목록 일치처럼 짧고 당연해 보이는 함수가 바로 증명이 가장 잘 먹히는 곳이라는 것이 저자들의 논지다.

대상은 세 코드베이스다. Kiro 에이전트 서버(IDE와 웹과 CLI v3가 공유하는 하네스), Kiro CLI, Kiro Crew다. 하네스가 기대는 속성은 여섯 갈래로 묶는다. 컨텍스트에 들어가는 모든 내용에 크기 상한이 있고 잘린 부분을 되찾을 수 있다는 것, 세션을 다시 불러도 모델이 라이브로 본 메시지와 같다는 것, 요청의 앞부분(도구 목록과 첫 메시지와 이력)이 턴마다 같아 제공자의 캐시를 재사용한다는 것, 승인은 승인한 만큼만 덮고 하위 에이전트는 부모보다 권한이 크지 않다는 것, 이벤트가 어떤 순서로 도착해도 최종 상태가 맞다는 것, 두 코드베이스가 서로 의존하는 곳의 계약이 맞는다는 것이다.

## 방법: 다섯 단계

작업은 Kiro CLI가 Amazon Bedrock에서 서비스되는 Claude Opus 5.5와 Lean 4 스킬로 수행했다. 에이전트가 대상을 찾고 Lean 모델과 증명과 차등 테스트와 재현 스크립트를 썼고 사람은 저장소와 범위를 정하고 정리 문장(theorem)과 발견을 검토했다. 도구는 Lean 4.28.0 배포판만 쓰고 Mathlib 같은 외부 의존성은 없다.

첫 단계는 대상 찾기다. Kiro CLI가 문서 주석과 설계 불변식과 호출 위치를 읽어 크기 상한, 승인 규칙, 불러온 세션이 라이브와 같아야 한다는 조건, 거꾸로 가지 않는 상태 기계 같은 함수를 순위로 만든다. 둘째로 같은 구조를 유지한 Lean 모델을 쓰고 원본 파일과 줄 번호를 머리말에 단다. 셋째로 모델을 실행 파일로 컴파일해 실제 구현과 나란히 무작위 입력으로 돌린다. TypeScript는 Node나 Bun, Rust는 실제 크레이트에 링크한 작은 바이너리, Python은 실제 모듈을 불러오는 식이며 입력 생성기는 다중 바이트와 한중일 문자, 상한 바로 아래와 위의 길이, 섞인 이벤트 순서를 겨냥한다. 최종 실행은 세 코드베이스에 걸쳐 97,938건이고 불일치가 없었다. 모델과 코드가 다른 두 곳에서 일부러 동작을 바꾸자 차등 테스트가 수백 건의 불일치를 보고해 테스트 자체도 점검했다.

넷째로 정리 문장을 쓰고 증명한다. 막힌 증명은 문장이 거짓이거나 모델이 틀렸거나 증명이 불완전하다는 세 원인 중 하나이고 막힌 목표가 깨지는 입력을 가리키면 그 입력이 위반한다는 bug_ 정리를 Lean으로 증명해 반례 자체를 검사한다. 외부 소프트웨어에 의존해 충실한 모델링이 어려운 속성 둘은 증명 대신 유한 범위 검사를 쓰고 증명으로 세지 않았다. 다섯째로 실제 수정되지 않은 코드에서 스크립트로 같은 결과가 나와야 발견으로 센 뒤 호출자가 그 입력에 닿을 수 있는지와 사용자가 보게 될 모습을 따졌다. 대부분의 발견은 Lean으로 수정안을 쓰고 동작을 유지하면서 문제를 닫음을 증명했다. 다만 이는 수정된 모델이 맞다는 증명이며 실제 코드 수정은 별도의 차등 테스트가 필요하다.

AI가 증명을 썼기 때문에 Lean이 의도를 놓친 증명 목표를 받아들이는 길도 점검했다. 미완성 단계와 추가 공리, 동시에 만족할 수 없는 가정으로 정리가 공허하게 참이 되는 경우를 확인하기 위해, 인용하거나 설명한 모든 정리에 대해 가정을 모두 만족하는 구체 입력을 Lean에서 확인했다.

## 증명된 것

Lean은 96개 속성 중 70개를 증명했고 각각 정리의 가정을 만족하는 모든 모델 입력에서 성립한다. 컨텍스트와 이력 영역에서는 중복 파일 첨부를 한 부분만 남기는 단계가 이전 메시지를 바꾸지 않는다고 증명했다. 이력 xs 뒤에 메시지 ys를 붙인 결과가 xs의 결과로 시작하므로 프롬프트 캐시 접두부가 대화가 길어져도 깨지지 않는다. 삭제와 되돌리기가 있는 세션 이력을 해석해도 두 번 적용한 결과가 한 번과 같고 순서를 바꾸지 않으며 분기한 세션은 부모의 유효 이력으로 시작한다. 불러온 뒤 모든 도구 카드가 라이브 때 본 상태로 끝나며 CLI가 도구 결과를 바이트 상한으로 자를 때 알림 문구를 붙이더라도 UTF-8 바이트 수가 상한을 넘지 않는다. 비동기 이벤트가 어떤 순서로 끝나도 세션 상태는 원래 순서와 같다는 정리는 모든 순열을 다룬다.

권한 영역에서는 하위 에이전트의 결정이 부모의 결정과 합쳐질 때 결과가 항상 둘 중 더 제한적인 쪽이고 정책을 조이면 거부가 승인으로 바뀌지 않으며 정규화된 절대 경로가 .. 로 루트 위로 올라가지 않는다고 증명했다. Crew가 CLI의 허용 도구 형식을 하네스 정책 패턴으로 번역할 때, 역슬래시가 없는 항목은 CLI보다 더 많이 허용하지 않는다.

상태 기계에서는 모델 거부 시의 대체가 한 턴에 세 번을 넘지 않고 이미 시도한 모델로 돌아가지 않으며 Crew 작업 큐에서 두 디스패처가 같은 작업을 동시에 가져가려 해도 한쪽만 성공한다는 정리가 있다. 큐는 작업마다 15개 상태를 거치고 claim이 성공할 때마다 행의 세대가 올라가므로, 새 작업자가 가져간 뒤에는 이전 작업자의 쓰기가 행을 바꾸지 못한다. 이 정리들은 저장소 호출 하나가 쪼개지지 않는 한 단계라는 가정에 기댄다. 이 가정은 Lean이 검사하지 않고 저장소의 잠금과 SQLite 트랜잭션이 보장하는 것이다.

## 반례로 찾은 버그

18개 코드 의도가 모델에서 반증되었고 모두 분석한 코드에서 재현되었다(세션 시작 경합은 모듈 수준 재현). 2026년 10월 1일에 CLI와 Crew의 GitHub 이슈와 에이전트 서버의 풀 리퀘스트를 검색했을 때 이 중 어느 것과도 맞는 열린 이슈는 없었다. 대부분은 사용자가 다시 묻거나 모델이 의도보다 약간 많거나 적은 텍스트를 보는 안전한 실패다.

가장 구체적인 예는 취소된 일회성 작업이 다시 실행되는 Crew의 버그다. 사용자가 작업 시작 직전에 실행 취소를 누르면 실행은 멈추지만 작업이 켜진 채로 남아 스케줄러가 몇 초 뒤 다시 실행한다. 테스트로는 취소가 작업 시작 직전의 짧은 순간에 닿아야 해서 못 잡는다. Lean은 10개의 이벤트로 이루어진 반례를 냈고 실제 스케줄러에서 재현되었으며 취소 처리에 조건 하나를 더하면 어떤 이벤트 순서에서도 취소된 작업이 다시 실행되지 않음을 증명했다.

그 밖의 묶음이 있다. CLI에서 새 세션이 시작되는 동안 다른 세션이 등록되면 세션 시작 훅의 도구 호출 같은 갱신이 사라지는 경합, 하네스의 web_fetch가 바이트로 예산을 받아 놓고 UTF-16 코드 단위로 자르기 때문에 한중일 문자 페이지가 상한의 최대 1.5배로 돌아오는 문제(하네스 발견 아홉 개 중 일곱 개가 이런 자르기 함수에 있음), grep_search가 일치 줄은 줄이지만 문맥 줄은 줄이지 않는 문제가 있다. 셸 출력이 약 5억 1천만 문자(Node 26.3.0과 V8 14.6 기준)를 넘으면 상한 검사 전에 문자열 한계에 걸려 프로세스가 종료되는 문제도 있는데, 백그라운드 터미널 수집기는 이미 최근 출력만 유지하며 한계에 닿을 수 없음이 증명되어 있어 수정은 모든 명령에 이를 쓰는 것이다. 스펙 모드의 암묵 규칙이 라이브 경로와 재불러오기 경로에서 다른 메시지에 붙어 콜드 리로드 뒤 한 턴의 접두부가 달라지는 것, "항상 허용" 경로를 이스케이프 없이 글롭으로 바꿔 Next.js의 [slug] 경로가 의도하지 않은 경로까지 허용하는 것도 포함된다.

도달 가능한 호출 경로를 못 찾은 두 건은 발견이 아니라 관찰로 센다. 보안 취약점으로 분류된 버그는 세 코드베이스 어디에도 없다.

## 배운 점과 한계

저자들은 증명이 하네스에 잘 맞는다고 본다. 컨텍스트 관리와 권한과 상태 기계가 짧고 정확한 정리를 만들고 함수가 작아 Lean으로 바로 옮겨지며 발견 대부분은 두 표현의 경계에서 나왔다. 두 쪽을 한 언어로 쓰면 어디서 어긋나는지 보인다. 증명이 막힌 목표가 깨지는 입력을 알려 주는 경우가 많았고 차등 테스트가 모델 오류를 잡는 데 증명만큼 중요했다.

한계도 직접 쓴다. 증명은 모델에 대한 것이므로 모델이 코드와 같아야 하는데 에이전트가 소스를 보고 쓴 모델이 놓친 것은 표본 입력 밖에서 발견되지 않는다. 정리가 코드의 의도를 빠뜨리면 증명이 성공해도 버그가 빠져나간다. Lean의 무한 자연수는 오버플로와 부동소수점을 담지 못한다. 신뢰 기반은 Lean 커널보다 크고 native_decide를 쓰는 17개 정리는 Lean 컴파일러와 C 툴체인도 믿는다(증명된 속성의 근거는 아니고 유한 검사와 반례와 대조 사례다). 결과는 분석한 커밋에 묶여 있다. 앞으로는 기능을 설계할 때 정리로 쓰고 코드가 바뀌면 차등 테스트를 다시 돌릴 계획이지만 모든 정리와 발견은 여전히 사람이 검토해야 해서 확대는 검토 노력에 달려 있다고 밝힌다.

## 대조해서 확인한 점

이 글의 수치는 본문 안에서 일관되다. 70과 2와 18과 6을 더하면 96이고 대상 함수는 26개, 실패 발견은 18개이며 그중 하네스가 아홉 개다. 글은 수치가 Kiro 팀이 검토한 내부 실험 결과이며 에이전트 서버와 CLI는 비공개 저장소이고 Crew만 공개 저장소의 커밋 909e0fc에서 분석했다고 밝힌다. 그래서 외부에서 이 노트가 확인할 수 있는 것은 Crew 쪽에 한정된다. 풀 리퀘스트 25130은 글에서 취소된 작업 버그의 링크로 언급되며 이 노트는 직접 열어 보지 못했다. 표 1 본문, Lean 코드 블록, 저장소의 증명 파일도 읽지 못했다.

주의할 점은 이 글이 제품 회사의 자기 평가라는 것이다. 다만 한계 절이 구체적이고(모델 충실성, 정리의 완전성, 신뢰 기반, 커밋 고정) 자체 점검 항목(공허한 정리 검사, 차등 테스트의 민감도 검사)을 밝혀서, 일반적인 홍보 글보다 주장의 범위를 좁게 잡는다. 독립 검증은 없다. 이 노트는 Lean 4.28.0의 존재나 Opus 5.5 서비스 여부도 따로 확인하지 않았다.

## 읽을 때 유의할 점

첫째, 증명이 성공했다는 말은 모델이 정리를 만족한다는 뜻이고 실제 시스템이 안전하다는 뜻이 아니다. 모델과 코드의 일치는 약 10만 건의 표본으로 확인하는 증거일 뿐 증명이 아니다. 둘째, 정리 문장은 에이전트가 문서 주석과 설계 불변식에서 썼고 사람이 검토했다. 정리가 의도를 빠뜨리면 증명은 쓸모없다. 셋째, 이 방식이 잘 먹힌 곳은 작은 함수와 경계 조건이다. 큰 시스템 전체나 외부 소프트웨어 의존이 큰 속성에는 유한 검사에 머물렀다. 넷째, 발견된 버그는 대부분 영향이 작은 안전한 실패라서 방법의 비용 대비 효과를 판단하려면 더 많은 사례가 필요하다. 다섯째, 도입에는 정리 검토 인력이 병목이고 그 비용은 글이 수치로 밝히지 않는다.

가져갈 질문은 선명하다. 내가 만드는 에이전트 하네스에서 상한과 접두부 안정성과 권한 상속 같은 속성을 코드 의도로 적어 두었는가, 두 표현(바이트와 문자, 경로와 글롭)의 경계를 한 곳에서 점검하는 테스트가 있는가, 모델과 실제 코드를 무작위 입력으로 대조하는 습관이 있는가, 증명을 쓴다면 정리의 가정이 서로 모순되지 않음을 확인하는가.
