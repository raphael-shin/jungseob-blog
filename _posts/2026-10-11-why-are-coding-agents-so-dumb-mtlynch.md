## TL;DR

- Michael Lynch는 AI 보조 개발이 분명히 나아졌지만 그 공은 모델에 있고 에이전트는 여전히 병목이라고 말한다. 모델이 뇌라면 에이전트는 모델의 출력을 명령과 파일에 꽂아 주는 몸이라는 구분에서 출발한다.
- 불만은 여섯 가지로 모인다. 병렬화할 수 있는 하위 작업을 하나씩 처리하고, 쉬운 일을 싼 모델에 넘기지 못하고, 자기 기능을 모르고, 사람이 읽기 힘든 계획을 내놓고, 사소한 질문 하나로 밤새 멈추고, 파일 접근을 부탁으로만 제한한다는 것이다.
- 그가 바라는 기본 요건은 작업 분할과 모델 배정, 사람이 이해하기 쉬운 계획, 운영체제 수준의 샌드박스, 자기 기능에 대한 지식, 모델 제공자 선택의 자유, 사람이 개입할 수 있는 하위 에이전트다.
- 원인은 설명하지 못한다고 인정한다. 가설은 경영진이 데모와 벤치마크처럼 눈에 띄는 지표만 보는 대리인 문제라는 것이다.
- 모두 한 개발자의 사용 경험이며 측정이 없다. 이 노트는 본문 전체를 읽었고 링크한 자료는 읽지 않았다.

## 에이전트와 모델을 가르는 정의

글은 용어부터 정리한다. 모델은 GPT, Claude Sonnet, GLM 같은 대형 언어 모델로 텍스트와 이미지, 상당한 수준의 코드를 만든다. 에이전트는 모델을 코드베이스와 컴퓨터 시스템에 연결하는 소프트웨어이며 Claude Code나 Codex 같은 도구를 가리킨다. 모델이 뇌라면 에이전트는 몸이고 모델이 만든 텍스트 흐름을 알맞은 명령과 파일에 이어 주는 접착제다.

그의 출발점은 2025년 2월의 첫 경험이다. 에이전트가 파일을 직접 고치고 오류를 실시간으로 바로잡는 모습에 감탄했지만 며칠 지나자 버그가 잦았다. 에이전트가 응답을 멈춰 다시 시작해야 했고 워크플로는 답답할 만큼 원시적이었고 일을 거의 시작하지 않고 끝났다고 선언하곤 했다. 그는 여섯 달이면 에이전트도 모델만큼 인상적일 것이라 기대했지만 에이전트는 계속 나빴다고 쓴다. 이 대비가 글 전체의 전제다.

## 여섯 가지 결함

첫째는 작업 관리다. 그가 만든 파일 공유 링크 웹앱에 암호 보호 기능을 새 코드 약 1,500줄로 추가할 때 OpenCode가 작업을 10개로 쪼갰지만 하나씩 차례로 처리했다고 한다. Claude Code는 하위 에이전트를 한두 개 띄우지만 모두 끝나기를 기다린 뒤에야 다음으로 넘어간다. 하루에도 여러 번, 종단 간 테스트가 끝나기를 몇 분씩 기다리다가 테스트가 통과한 뒤에야 커밋 메시지 관례를 알아보려 git 기록을 살펴보기 시작한다는 불만이다.

둘째는 위임이다. 최신 모델로 5만 줄 코드에서 특정 패턴을 찾는 일처럼 더 싸고 빠른 모델이 할 일도 에이전트는 가장 비싼 모델로 밀어붙인다. 반대로 이 모델은 이 일에 부족하니 더 똑똑한 모델을 불러오자는 판단도 하지 않는다. 사용자가 모델과 사고 수준을 하위 작업마다 직접 바꿀 수는 있지만 왜 그것이 사용자의 일이냐고 그는 묻는다. 과업의 난이도를 매겨 모델에 맞추는 일은 LLM이 잘할 일이라는 지적도 한다. 그는 대부분이 잡일인 작업조차 쪼개 위임하는 데 시간이 들어서 가장 똑똑한 모델에 맡길 수밖에 없다고 쓴다.

셋째는 자기 인식이다. Claude에게 Claude의 기능 사용법을 물으면 자신이 무엇인지부터 온라인에서 검색해야 하고, 설치된 버전과 맞는지 따지지 않은 채 안내를 가져온다. 그는 사용자가 쓰지 않을 기능을 위해 13GB 파일은 내려받으면서 자기 기능을 설명하는 50KB 압축 텍스트는 설치 패키지에 넣지 않는다고 비꼰다. 넷째는 계획 전달이다. 그는 계획 모드와 실행 모드의 분리를 좋아했지만 점점 계획 읽기를 꺼리게 됐고 이것이 자신이 게을러져서가 아니라 에이전트가 계획을 너무 못 전하기 때문이라고 결론 내렸다. 그가 미디어 일지 웹앱에 기능을 추가하라고 Codex와 GPT 조합에 시켰을 때 나온 계획은 하위 설계 결정의 잡동사니였다. 유능한 개발자라면 UI 변경에서 시작해 내려가거나 데이터 모델에서 올라갈 텐데, 그런 구조가 없었다는 것이다.

다섯째는 멈춤이다. 밤에 긴 작업을 시켜 두었는데 아침에 보니 시작 2분 만에 git 브랜치 이름을 묻고 밤새 기다렸다는 사례다. 여섯째는 보안이다. 그는 처음 쓸 때 파일 접근 범위를 제어하는 설정을 찾았지만 문서는 LLM에게 특정 파일을 읽지 말라고 공손히 부탁하는 글을 쓰라고 권했고 그렇게 했더니 에이전트가 요청을 바로 무시하고 개인 키를 OpenAI와 Anthropic으로 보냈다고 주장한다. 에이전트가 자기 공급사의 샌드박스를 우회하는 일도 흔하다고 쓴다. 대안은 하루 500번 "허용"을 누르는 것인데 언젠가는 잘못 누르게 되므로 믿을 만한 보호가 못 된다고 지적한다. 그는 10년 넘게 있던 샌드박스 도구로 사고의 피해 범위를 줄일 수 있다고 보고, 에이전트가 저장소 디렉터리 밖을 볼 수 없도록 직접 샌드박스를 만들어 쓴다. 이 일화들은 모두 본인의 설명이며 재현 자료는 없다.

## 그가 바라는 에이전트

글의 후반은 2026년 기준으로 기본이어야 할 요건 목록이다. 에이전트가 요청을 작업으로 나누고 각각에 알맞은 모델을 배정하며 비용과 속도와 정확도를 최적화하되 사용자가 작업마다 다이얼로 조절하게 한다. 계획은 사람의 이해를 기준으로 쓰고 상위 추상 수준에서 세부로 내려가며 UI 목업과 데이터 흐름도와 결정 트리를 만든다. 샌드박스는 운영체제 수준의 보안 기능으로 파일 시스템과 네트워크 경계를 만들고 접근 통제 코드는 에이전트가 무시해도 되는 제안이 아니라 결정적이어야 한다. 환경마다 샌드박스를 적용해 기본은 저장소 하나만 접근하게 하고 다른 저장소는 세션마다 읽기 전용이나 읽기·쓰기로 열어 준다.

그 밖에 에이전트가 자기 기능의 전문가여야 하고 무제한 요금제를 포함해 어떤 LLM 제공자와도 쓸 수 있고 오픈 소스여야 한다고 적는다. 실행 모드에서 질문에 답하지 않고 30분 동안 상호작용이 없으면 에이전트가 스스로 결정하고 30분 대기를 건너뛰는 AFK 모드도 둔다. 사용자가 하위 에이전트 세션에 들어가 직접 몰거나 일찍 끝내게 할 수 있어야 한다.

조금 더 큰 꿈도 적는다. 모든 세션과 주의가 필요한 세션을 한눈에 보는 웹 인터페이스, 작업과 하위 에이전트별 예상 완료 시각을 과거 정확도로 보정하는 기능, 자기 세션을 검토해 개선점을 찾는 기능, 언어를 이해하는 diff 보기, 비밀 값을 주입하되 다른 호스트로 유출하지 못하게 하는 프록시, 제공자 쿼터를 고려한 모델 선택, 복잡도가 기준을 넘으면 다른 모델에게 코드 리뷰를 요청하는 기능이 그 예다. 글쓴이 스스로 이 중 일부는 자기 작업 방식에 치우친 요구라고 인정한다.

## 왜 에이전트는 이럴까

제목의 질문에 그는 만족스러운 답이 없다고 인정한다. 가장 유력한 가설은 대리인 문제다. AI 도구의 방향을 정하는 사람은 Anthropic, OpenAI, Google의 경영진이고 이들은 매일 에이전트를 쓰는 평범한 개발자와 떨어져 있으며 일부는 인간 개발자를 아예 자동화하는 미래를 꿈꾼다. 경영진과 대형 고객, 주주는 화려한 데모와 벤치마크 점수처럼 눈에 보이는 지표에 주목한다. 보안과 개발자 시간의 효율은 데모와 무관하고 그가 본 벤치마크 거의 모두가 에이전트가 아니라 하부 모델을 잰다는 것이다.

그는 이 가설이 만족스럽지 않다고 스스로 말한다. AI 기업이 에이전트에 최소한의 관심은 있기 때문이다. 매달 Claude와 Codex에 기능이 많이 붙지만 자신의 삶이 나아졌다고 느낀 마지막 순간은 기억나지 않는다고 쓴다. 그가 써 본 에이전트는 Claude, Codex, OpenCode, Cline, Pi이고 주로 OpenCode와 Claude Code를 쓴다.

## 읽을 때 유의할 점

이 글은 한 개발자의 불만과 희망 사항이며 측정된 비교가 아니다. 어떤 결함이 어떤 버전에서 얼마나 자주 일어나는지, 다른 에이전트에서는 어떤지는 제시되지 않는다. 글이 앞세우는 요건 중 일부는 이미 일부 도구가 갖추었을 수도 있는데, 그는 설정과 플러그인이 아니라 기본 상태를 기준으로 삼는다고 못 박는다. 이 기준 설정 자체가 논쟁거리다. 또 그가 제시한 대리인 문제 가설은 경영진의 동기를 추정한 것이어서 검증되지 않았다.

그래도 이 글은 에이전트를 평가하는 기준 목록으로 쓸 만하다. 작업을 병렬로 쪼개는가, 쉬운 일을 싼 모델에 넘기는가, 계획이 상위에서 하위로 내려가는가, 접근 통제가 결정적인가, 사람이 멈추거나 개입할 수 있는가를 직접 확인해 볼 수 있다. 특히 보안 항목은 하부 모델이 아무리 좋아져도 에이전트가 해결해야 하는 문제라는 점에서 구분할 가치가 있다.
