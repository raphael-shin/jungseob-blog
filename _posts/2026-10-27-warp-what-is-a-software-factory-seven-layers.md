## TL;DR

- Warp는 소프트웨어 공장을 개발 수명주기 주변에 둘러친 클라우드 자동화 루프로 정의한다. 분류, 명세, 구현, 리뷰, 검증, 승인, 모니터링 단계를 에이전트가 반복 작업으로 돌리고 사람은 결정 지점에만 남는다.
- 팀이 공장을 필요로 하는 이유로는 코딩 에이전트가 코드 작성을 싸게 만들었지만 코드 주변 일은 싸지지 않았다는 점을 든다. 리뷰가 병목이 되고, 자동화의 가치를 말할 수 없고, 에이전트마다 보안 표면이 생긴다는 세 한계다.
- 만들어야 할 것은 일곱 겹이다. 팩토리 코드화, 데이터와 컨텍스트, 컴퓨트, 추론, 개선, 오케스트레이션, 접근이며, 모두 첫날 필요한 것은 아니고 코드화와 측정이 나머지를 복리로 만든다고 본다.
- 이 글은 Warp Factories를 파는 회사의 글이다. 자사 코드베이스에서 변경의 약 75%를 자동화했다는 보고와 벤치마크로 비용을 63% 줄였다는 보고는 모두 Warp의 자체 수치이고 업계 기준이 아니라고 글 스스로 밝힌다.
- 노트는 본문 전체를 읽었고 Warp 자체 자료와 Cursor 보고는 검색 발췌로 일부만 확인했다.

## 글에 대하여

Warp의 블로그 글로 2026년 9월 17일에 올라와 10월 22일에 수정되었다. 제목은 정의와 구축할 일곱 겹을 약속한다. 필자는 Warp(회사)로 표기되고 글 끝에서 Warp Factories의 초기 접근과 데모를 권한다. 본문과 출처 목록과 관련 글을 읽었다. 출처 열두 건은 대부분 Warp의 자사 글과 경쟁사 문서다. 이 블로그의 [Kiro 소프트웨어 공장 노트](https://raphael-shin.github.io/jungseob-blog/posts/kiro-software-factory-stability-1000-prs/)와 [Grok Bot 소프트웨어 공장 하우투 노트](https://raphael-shin.github.io/jungseob-blog/posts/contentlab-grokbot-software-factory-thursday-arena-launch/)가 같은 이름의 다른 구현을 다룬다.

## 정의와 루프

글이 그리는 루프는 일곱 단계다. 일은 Slack 메시지, Linear나 Jira 티켓, GitHub 이벤트, Sentry 경보, 또는 로컬 코딩 에이전트가 MCP 서버로 밀어 넣는 작업처럼 이미 있는 곳에서 들어온다. 분류 에이전트가 문제를 재현하고 자동화할 수 있는지, 명세가 필요한지, 사람이 필요한지 판단한다. 명세 에이전트는 범위가 모호하면 사람과 반복한다. 구현 에이전트가 코드를 쓰고 리뷰 에이전트가 변경분을 읽고 검증 에이전트가 실제 빌드에서 컴퓨터 사용으로 동작을 증명한다. 사람이 승인하고 CI가 돌면 출시된다. 모니터링 에이전트가 운영을 보고 다음 이슈를 올려 고리를 닫는다. 점 자동화 모음과 구분되는 성질은 두 가지다. 모든 단계가 같은 컨텍스트를 쓰고 모든 실행이 기록되어 시스템 전체를 측정할 수 있다는 것이다. 글은 이것이 없으면 코드 리뷰를 개선해도 분류에 도움이 되지 않고 자동화가 값을 하는지 아무도 말할 수 없다고 쓴다.

## 왜 필요한가, 무엇을 만드나

세 한계는 이렇게 쓰여 있다. 에이전트가 사람이 읽을 수 있는 양보다 많은 풀 리퀘스트를 열어 리뷰가 병목이 된다. 자동화마다 로그가 따로여서 변경당 비용이나 수용률 같은 단일 수치가 없다. 독립 에이전트마다 자격 증명과 감사 공백과 모델 종속이라는 보안 표면이 생긴다. 공장은 리뷰와 검증 단계를 넣어 결정만 사람에게 보내고 모든 실행을 한곳에 기록하고 에이전트를 하나의 통제 평면 뒤에 둔다.

일곱 겹은 표로 정리된다. 팩토리 코드화는 공장 정의 전체를 버전 관리하는 것으로, 최소는 저장소의 factory.yaml 하나와 에이전트 파일이고 규모가 커지면 카나리와 롤백과 구성의 A/B 테스트다. 데이터와 컨텍스트는 조직 지식을 먹이고 에이전트가 한 일을 기록하며 최소는 저장소에 둔 스킬 파일이고 규모가 커지면 사내 MCP, 메모리, 전체 추적, 감사 로그다. 컴퓨트는 노트북이 아닌 곳에서 일을 돌리는 것으로 컨테이너 원격 개발 환경 하나에서 시작해 빠르게 뜨고 멈출 수 있는 러너와 컴퓨터 사용과 Linux, macOS, Windows로 간다. 추론은 모델과 하네스로 최전선 모델 하나에서 시작해 오픈 웨이트 모델과 여러 하네스와 모델 라우팅으로 간다. 개선은 공장이 나아지는지 증명하는 층으로 변경당 비용과 주기 시간에서 시작해 채점기, 실행 재생, 벤치마크, 자기 개선 에이전트로 간다. 오케스트레이션은 실행을 시작하고 추적하고 복구하며 트리거 하나에서 에이전트 하나로 시작해 서브에이전트를 나누는 감독 에이전트와 실시간 조종과 클라우드에서 로컬로의 인계로 간다. 접근은 일의 입출구로 Slack이나 GitHub 트리거 하나에서 시작해 Slack, Jira, Linear, 포지, Factory MCP, 웹과 모바일의 통합 API로 간다.

글은 두 층이 나머지를 복리로 만든다고 본다. 팩토리를 코드로 정의하면 모든 변경이 시험 가능하고 되돌릴 수 있고(글의 비유로 팩토리용 Terraform), 개선 층의 주인이 추적을 갖는 쪽이어야 한다. 재생할 수 없는 공장은 감으로만 조정된다는 것이다.

## 기다 걷다 달리다, 플랫폼 비교, 흔한 실수

대부분의 팀은 이미 기는 단계다. PR 리뷰어 하나 Sentry가 부르는 수정기 하나 같은 것이 그렇다. 걷는다는 것은 마케팅 사이트나 사내 앱처럼 위험이 낮은 표면 하나에서 고리를 끝까지 한 번 돌리는 것이고 달린다는 것은 복잡한 저장소로 확장하며 원격 환경과 모델 라우팅과 감사와 리뷰 처리량이 병목이 되는 단계다. 글은 Warp 자신의 걷는 단계 공장이 마케팅 사이트 warp.dev 변경의 약 75%, 전체 풀 리퀘스트의 20~30%를 자동화한다고 쓰며 첫 번째 자사 수치이고 업계 기준이 아니라고 밝힌다.

비교표는 Warp Factories, Factory.ai, Cognition Devin, GitHub Copilot cloud agent, Cursor Cloud Agents, Claude Code 여섯을 대조한다. 글은 이들이 대체재가 아니라 하나는 고리를 조율하고 다섯은 한 단계에서 훌륭하다고 설명하고 표가 답하는 질문은 프런티어가 두 번 바뀐 뒤에도 어느 쪽이 워크플로 정의를 쥐고 있는가라고 말한다. 비교 축은 모델과 하네스 선택, 워크플로가 정의되는 곳, 배포와 데이터다. 이 축이 Warp의 설계 주장과 겹친다는 점은 이 노트의 판단이다. Cursor Cloud Agents에 대해서는 Cursor가 자사 팀 PR의 40% 넘게가 이 에이전트에서 나온다고 보고한다고 인용한다.

흔한 실수는 세 가지다. 에이전트 품질로만 후보를 거르는 것(벤치마크는 가장 눈에 띄지만 가장 오래가지 않는 신호이고 모델 선두는 1년에 여러 번 바뀐다), 한 워크플로를 자동화하기 전에 조립 라인 전체를 사는 것, 비용이 든다는 이유로 측정을 건너뛰는 것이다. Warp는 LLM 심판 채점이 자사 내부 공장 토큰 지출의 약 3%라고 보고한다. 제안은 명확한 입력과 측정 가능한 결과와 사람 대안이 있는 워크플로 하나(분류, 검증, 의존성 유지, 사고 후속)를 한 달 돌리면서 비용, 주기 시간, 수용률, 개입률을 추적하고 숫자가 유지될 때만 넓히라는 것이다.

## 대조해서 확인한 점

Warp가 인용한 수치 중 Cursor의 40%는 Cursor의 운영 회고 보도에서 확인된다. 다만 최근 보도는 Cursor가 모노레포에서 클라우드 에이전트가 병합 PR의 절반 넘게를 쓴다고 갱신해 보고했다는 요약도 있어 시점에 따라 수치가 다르다. 이 노트는 Cursor 원문을 읽지 않았다. Warp의 63% 비용 절감은 Warp가 자체 코드베이스에서 특정 작업 유형에 대해 낸 값이며 Factory Benchmarks 발표 게시물에도 같은 취지의 문장이 있다. "70만 명 넘는 개발자, Docker, Ramp, Peloton, 포천 500대 기업의 절반 넘게"는 Warp의 자기 소개로 Warp의 다른 글에도 같은 문구가 나오며 독립 확인은 하지 못했다. 75%와 3%는 이 노트가 확인할 방법이 없다. Factory.ai, Devin, Copilot, Claude Code 행의 서술은 글이 인용한 각 사 문서를 이 노트가 읽지 않아 검증하지 못했다.

## 읽을 때 유의할 점

첫째, 이 글은 정의를 명분으로 한 제품 글이다. 일곱 겹의 틀이 Warp Factories의 기능과 거의 일대일로 겹치므로 일반 정의가 아니라 Warp의 분류로 읽어야 한다. 둘째, 모든 수치가 필자 자사 코드베이스의 보고이며 마케팅 사이트의 75%는 변경이 단순한 표면에서의 수치다. 셋째, 비교표의 축이 Warp의 설계 주장과 겹치고 에이전트의 작업 품질은 비교 축에 들어 있지 않다. 넷째, 소프트웨어 공장이라는 말은 업계에서 쓰임이 제각각이다. Kiro 팀은 PR 1,000개 규모의 운영 규율로, Grok Bot 사례는 출시 후 고리로 쓴다. 다섯째, 글이 권하는 한 워크플로로 시작하라는 조언은 제품과 무관하게 유효한 부분이다.

그래도 가져갈 질문은 선명하다. 지금 돌리는 에이전트들이 같은 컨텍스트를 공유하는가, 변경당 비용과 수용률 같은 단일 수치를 말할 수 있는가, 공장 정의를 코드로 두고 되돌릴 수 있는가, 한 달 돌릴 낮은 위험의 워크플로는 무엇인가.
