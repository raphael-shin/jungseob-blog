## TL;DR

- 백엔드 개발자인 필자는 AI가 만든 프론트엔드가 한눈에 AI 티가 나는 원인을 페이지마다 제각각인 기본값에서 찾았다. 개편 전 코드를 세어 보니 서로 다른 색이 162개, 그림자가 206곳, 버튼 모양이 41종이었다.
- 해법은 순서를 뒤집는 것이었다. 디자인 시스템을 먼저 만들고, 필요한 컴포넌트는 화면이 아니라 디자인 시스템에 먼저 추가하며, 화면은 그것을 조합만 한다.
- 기준을 적어 두는 것으로는 부족했다. 기준에 없는 색이나 그림자는 아예 화면에 나오지 않도록 막았고, 규칙 문서에 금지 목록을 적었고, Playwright로 40개 화면을 자동 검사했다.
- 보고된 결과는 페이지 32개를 약 3시간 50분 만에 전환했고 토큰은 약 3억 8천만 개를 썼다는 것이다. 다른 색은 162개에서 33개로 줄었다.
- 이 수치는 한 제품에서 필자가 직접 센 자기 보고이며, 디자이너 검토 전이라고 글이 밝힌다. 본문 속 코드 줄 수 서술과 표의 숫자가 서로 맞지 않는다.

## 글에 대하여

VacayBuddy 팀의 글로 필자는 백엔드 개발자다. 2026년 10월 14일자이고 작성자는 구조화 데이터에서 이승우로 확인된다. VacayBuddy는 Slack 연차·근태 관리 앱이며 웹 화면을 Express와 EJS로 서버가 그린다. 프론트엔드 코드는 대부분 AI가 썼다. 지난 글에서는 htmx로 코드를 걷어내며 화면 상태의 기준을 서버로 정했고 이번 글은 화면 모양의 기준을 디자인 시스템으로 정한 이야기다. 환경은 Node, Express, TypeScript, EJS, htmx이고 이번에 추가한 것은 Tailwind CSS v4 하나다. 이 노트는 본문 전체를 읽었다. 개편 전후 비교 사진과 연결된 다른 글은 읽지 않았다.

## AI 티의 정체는 페이지마다 다른 값

화면을 열면 파란 정사각형 안의 흰 아이콘이 있는 통계 카드, 그라데이션 배지, 대문자 ADMIN 라벨, 페이지마다 미묘하게 다른 파란색이 보였다. 필자는 감으로 말하기 전에 직접 쓴 화면 코드만 세었다. 색은 162종에서 33종(25개가 디자인 시스템 지정색)으로, 그라데이션은 65곳에서 1곳으로, 그림자는 206곳에서 34곳으로 줄었다. 글자 크기는 68종에서 4종, 모서리 둥글기는 43종에서 11종, 버튼 모양은 41종에서 8종, 페이지 안 직접 스타일은 498곳에서 24곳으로 줄었다. 개편 후 수치에서는 쓰지 않는 옛 페이지와 디자인 시스템 설명 페이지를 뺐다고 밝힌다.

원인 진단은 단순하다. AI는 페이지 단위로 만들고 다른 페이지와 맞출 기준이 없으니 매번 가장 그럴듯한 기본값을 고른다. 이미 공용 CSS가 있는데도 AI가 그 자리에서 새로 만들어 쓴 경우도 있었다. 같은 "승인 대기"가 달력에서는 주황, 팀 연차 화면에서는 빨강이 된 것이 대표 예다. 필자의 결론은 기준이 있는 것과 기준을 반드시 따르게 하는 것이 다르다는 점이다. 따르지 않아도 화면이 멀쩡히 돌아가면 AI는 편한 값을 쓴다.

## 디자인 시스템을 먼저, 화면은 조합으로

첫 단계는 기준 페이지다. 색, 글자 크기, 버튼, 입력창, 표, 모달, 배지를 한 페이지에 그려 두고 맨 위에 "새 화면은 여기 있는 값과 컴포넌트만 쓴다. 없으면 먼저 여기에 추가한다"는 취지의 안내를 적었다. AI에게는 카탈로그이고 필자에게는 리뷰 화면이다.

둘째 단계는 컴포넌트 추가 순서다. 연차 신청 상세 창에 "10월 12일에서 14일"을 달력 한 장처럼 보이는 날짜 카드가 필요했을 때, 화면에서 만들지 않고 디자인 시스템에 먼저 날짜 카드를 추가했다. 이때 색, 모서리, 글자 크기는 이미 있는 값만 썼고 신청 상세 창은 이 카드에 기존 배지와 타임라인을 조합해 만들었다. 직원 목록, 날짜 카드, 태그 입력이 이렇게 늘어난 컴포넌트다. 화면이 하나 늘 때마다 디자인 시스템이 자랐고 다음 화면은 빨리 만들어졌다.

셋째 단계가 가장 중요하다. 기준에 없는 색, 모서리, 그림자는 써도 화면에 나오지 않게 막았다. AI가 습관대로 Tailwind 기본 파랑을 쓰면 그 색이 존재하지 않아 버튼에 색이 칠해지지 않고 화면을 열자마자 이상한 점이 보여 바로 잡힌다. "쓰지 마세요"를 "쓸 수 없다"로 바꾼 셈이다. 마지막으로 AI가 읽는 규칙 문서에 원칙과 금지 목록을 적었다. 그라데이션, 카드 그림자, 대문자 라벨은 쓰지 않고 장식은 형광펜 하나와 한 화면에 핵심 숫자 하나로 제한하며 버튼 문구는 동작("승인하기"), 완료 알림은 같은 동사의 과거형("승인했어요")으로 쓴다.

## 전환과 검증

전환은 안내 화면 같은 단순한 것부터 감사 로그, 전자결재, 팀 휴가 달력, 근태, 연차 관리, 설정 순으로 페이지(또는 묶음)를 하나씩 옮겼다. 시간표는 08:50부터 09:57까지 디자인 시스템 제작, 09:59부터 11:37까지 페이지 32개 이전, 11:40 규칙 문서 정리, 12:16부터 12:30까지 직접 써 보고 낸 피드백 반영이다. 합계 약 3시간 50분이고 토큰은 약 3억 8천만 개, 모델은 Claude Opus 5.5였다. htmx 덕에 서버가 HTML을 그리는 구조라 옮길 곳이 한 곳이었고 페이지마다 따로 있던 모달, 알림, 확인창 코드를 공용 코드 하나로 합쳤다.

검증은 Playwright로 40개 화면을 데스크톱과 모바일 두 크기로 띄워 스크린샷을 찍고 자동으로 잡았다. 화면 오류와 실패한 요청, 가로 스크롤, 디자인 시스템에 없는 색, 배경 대비가 너무 낮은 글자, 한 단어가 두 줄로 쪼개진 곳이다. 마지막 항목은 한국어 화면에서 개편 전 모바일 달력이 실제로 그랬다고 한다. 자동 검사가 못 잡은 것은 필자가 직접 써 보며 찾았다. 넓은 모니터에서 달력 오른쪽이 비는 것, 탭 아래 세로 스크롤바, 달력의 휴가가 누를 수 있게 안 보이는 것, 칩 모서리가 어색한 것이다. 잴 수 있는 것은 자동 검사에 맡기고 스크린샷은 사람이 봐야 한다는 결론이다.

## 디자인 시스템만 고치면 화면이 따라온다

전환 후에 나온 이점도 설명한다. 칩 모서리를 더 둥글게 하는 수정은 칩 컴포넌트 하나만 고쳤더니 칩을 쓰는 모든 화면이 바뀌었다. 넓은 화면에서 한쪽이 비는 문제는 공통 화면 틀에 가운데 정렬을 넣어 전체 페이지를 고쳤고 달력의 마우스 커서 문제도 달력 컴포넌트 한 곳만 고쳤다. 색감도 아직 디자이너 검토 전이지만 디자인 시스템의 색만 바꾸면 전 화면에 반영되니 걱정이 덜하다. 거꾸로 디자인 시스템이 AI스러우면 모든 화면이 똑같이 AI스러워지므로 사람이 시간을 쓸 곳은 거기라는 평가다.

## 읽을 때 유의할 점

첫째, 모든 수치는 한 제품, 한 필자의 자기 보고다. 코드를 직접 세어 비교했다는 방법은 투명하지만 측정 도구와 대상 파일 범위는 글에 자세히 나오지 않는다. 둘째, 코드 줄 수 서술이 일관되지 않는다. 본문 3장은 2만 4천 줄을 지우고 7천 줄을 썼다고 쓰고 6장 표는 1만 3천 줄 추가와 2만 4천 줄 삭제라고 쓴다. 어느 쪽이든 순감소라는 결론은 같지만 추가 줄 수는 서로 다르다. 셋째, "일관성이 유지되면 AI 티가 나지 않는다"는 주장은 주관적 인상에 기대며 사용자나 디자이너의 평가가 없다.

넷째, 3시간 50분과 3.8억 토큰은 이 앱의 규모(32개 페이지)와 이미 정리된 htmx 서버 렌더링 구조에서의 결과다. 클라이언트 렌더링 앱이나 더 큰 코드베이스에서 같은 비용이 나온다는 보장은 없다. 다섯째, 기준 밖 값을 막는 구체적 설정은 글에 코드가 없어서 재현 방법은 확인하지 못했다. 여섯째, 개편 전후 화면 사진은 읽지 못했다.

그럼에도 가져갈 점검 질문은 선명하다. AI가 만드는 UI에 "기준을 따르라"고 쓰는 데 그치지 않고 기준 밖 값이 동작하지 않게 막았는가, 새 요소가 필요할 때 화면에서 만들지 않고 공용 컴포넌트에 먼저 추가하는 규칙이 있는가, 측정할 수 있는 불일치(색, 크기, 대비)를 자동 검사로 돌리는가, 사람이 보는 시간을 화면 하나하나가 아니라 기준 하나에 쓰는가.
