## TL;DR

- 2026년 10월 Anthropic은 사내 모노레포에서 Git을 자체 버전 관리 시스템 Scion으로 바꿨다고 밝혔고, 11월 OpenAI는 병렬 에이전트 개발을 위한 새 Git 백엔드 Pando를 공개했다. 둘 다 에이전트가 늘며 저장소 부하가 커졌지만, Anthropic은 버전 관리 시스템 자체를, OpenAI는 서버 쪽만 바꿨다. 그래서 OpenAI 개발자는 여전히 git clone과 git push를 쓴다.
- 글은 "Git을 쓴다"는 일을 세 층으로 나눈다. 커밋을 만들고 주고받는 클라이언트와 프로토콜, 코드를 보관하고 브랜치 갱신을 처리하는 서버와 저장소, 그리고 리뷰하고 CI로 검증하고 main에 합치는 협업 흐름이다.
- Anthropic 사례에서 일일 병합은 넉 달 만에 약 2,500건에서 3만 건 이상으로 약 12배가 됐고, CI 체크아웃은 하루 약 2,500만 회였다. 초당으로 바꾸면 병합 약 0.35건, 체크아웃 약 290회로, 변경을 반영하는 횟수보다 코드를 가져가는 횟수가 훨씬 많을 수 있다.
- OpenAI Pando, GitHub, Cursor Continuity, Entire, GitLab은 대체로 Git 명령은 그대로 두고 서버를 다시 설계했지만, 푸시가 빨라져도 main에 합치는 일은 남는다. Aspen은 브랜치별 푸시를 초당 567회 처리했지만, main에 하나씩 순서대로 반영하면 초당 약 4회였다. 각각 통과한 변경을 합친 결과가 돌아가는지도 따로 확인해야 한다.
- 리뷰하는 기록도 바뀌고 있다. Zed의 Delta는 동료를 나와 에이전트의 작업 스레드에 초대해 코드와 대화를 함께 리뷰하게 한다. 이제 저장소를 옮길 때 PR과 이슈만이 아니라 에이전트와 나눈 대화와 편집 기록이 어디에 남는지도 따져야 한다.

## 무슨 글인가

GeekNews가 2026년 11월 12일 올린 아티클이다. 그동안 GeekNews에 올라온 여러 소식을 이어 붙여, 각 팀이 어디서 막혔고 어느 층까지 바꿨는지 정리한 글이다. 본문 약 7,200자와 사례 표를 끝까지 읽었다. 글이 인용한 각 회사의 원 발표와 GeekNews 개별 글은 이 노트가 열지 않았다. 이 블로그에는 Anthropic의 Scion을 다룬 [Scion 노트](https://raphael-shin.github.io/jungseob-blog/posts/scion-online-source-control/)가 있다.

## 세 층으로 나눠 보기

글은 우리가 평소 "Git을 쓴다"고 부르는 일을 세 층으로 나눈다. 첫째, 클라이언트와 프로토콜이다. 커밋을 만들고 clone이나 push로 주고받는 방식이다. 둘째, 서버와 저장소다. 코드를 보관하고 여러 작업에 전달하며 브랜치 갱신을 처리하는 방식이다. 셋째, 협업 흐름이다. 변경을 리뷰하고 CI로 검증하고 main에 합치는 방식이다.

7월 Entire의 지역 미러 발표부터 11월 OpenAI의 Pando와 오픈소스 서버 Aspen 공개까지, 몇 달 사이 여러 시도가 나왔다. GitHub와 Cursor는 Git 서버를 다시 설계했고 GitLab은 에이전트가 필요한 코드만 가져오는 인터페이스도 만들고 있다. Anthropic이 클라이언트와 프로토콜까지 바꾸는 사이, Zed는 Git 커밋은 그대로 두고 리뷰가 이뤄지는 자리를 바꿨다.

## 에이전트가 늘면 어디가 바빠지나

에이전트에게 버그 세 개를 각각 맡긴다고 해 보자. 한 컴퓨터에서라면 git worktree로 작업 디렉터리를 나눌 수 있다. 각자 다른 브랜치와 파일을 다루면서도 Git 객체 저장소는 공유하니, 작업마다 원격에서 저장소를 다시 받지 않아도 된다.

클라우드에서 작업마다 새 샌드박스를 띄우면 서버와 저장소도 바빠진다. 기존 사본을 다시 쓰지 못하면 환경을 띄울 때마다 코드를 가져와야 한다. 작업이 끝나 푸시하면 이번에는 CI가 움직이고 테스트를 여러 작업으로 나눴다면 같은 커밋을 여러 환경이 다시 가져갈 수 있다.

Anthropic 사례에서는 사내 모노레포의 일일 병합이 2026년 5월 약 2,500건에서 9월 3만 건 이상으로, 넉 달 사이 약 12배가 됐다. CI 체크아웃은 하루 약 2,500만 회였다. 하루 평균으로 바꾸면 병합은 초당 약 0.35건, CI 체크아웃은 초당 약 290회다. 글은 병합 한 건이 체크아웃을 몇 번 일으켰다는 뜻은 아니지만 변경을 반영하는 횟수보다 그 코드를 가져가는 횟수가 얼마나 많을 수 있는지 보여 준다고 짚는다.

GitHub가 4월에 낸 가용성 업데이트를 보면 부하는 저장소에만 머물지 않는다. PR 하나를 열어도 Actions, 브랜치 보호, 검색, 알림 같은 기능이 함께 움직인다. 에이전트가 만드는 변경이 늘면 그 변경을 받아 처리하는 서비스들도 함께 바빠진다.

## Git 명령은 그대로, 서버를 다시 짓다

OpenAI의 Pando가 바꾼 곳은 두 번째 층, 서버와 저장소다. Git 브랜치는 어느 커밋을 가리키는지 기록하는 작은 참조다. 새 코드와 이력을 저장하는 일과 브랜치가 가리키는 커밋을 갱신하는 일은 나눠서 처리할 수 있다. Pando는 서로 다른 브랜치의 푸시를 따로 처리해서, 관계없는 브랜치의 푸시가 한곳에서 차례를 기다리지 않는다. 같은 브랜치의 갱신 순서는 보장하지만 여러 브랜치를 함께 읽는 도구는 각 브랜치를 서로 다른 시점의 상태로 볼 수 있다. 읽기에서는 Git 객체를 압축해 묶은 팩파일을 다시 쓰고 지역 캐시에서 내준다. 클라이언트가 이미 가진 객체를 일부 다시 받을 수 있지만 서버는 같은 이력을 요청받을 때마다 새로 압축하는 일을 줄인다.

단일 저장소에서 초당 7,200회 푸시를 처리한다는 GitHub의 새 저장 구조도 큰 팩 데이터와 브랜치 참조를 따로 다룬다. Cursor의 Continuity는 푸시를 S3의 변경 로그에 남기고 서버 디스크의 저장소 사본은 필요하면 다시 만들 수 있는 캐시로 쓴다. 글은 구현과 일관성 보장은 다르지만 코드를 보관하는 곳과 요청을 처리하는 서버를 떼어 내면서 기존 Git 사용법을 지킨다는 공통점이 있다고 정리한다.

저장소를 옮기지 않고 읽기 요청만 나누는 방법도 있다. Entire의 분산 Git 네트워크는 GitHub를 원본으로 두고 에이전트가 가까운 지역의 미러에서 clone과 pull을 하게 했다. 앞선 GeekNews 글에서 미러는 장애가 났을 때 코드를 다시 가져오는 사본이었다면, Entire의 미러는 평소 여러 에이전트가 같은 코드를 가져갈 때 원본에 몰리는 요청을 줄이는 사본이다. GitLab의 차세대 소스 관리 시스템은 기존 Git 프로토콜을 지키면서 서버 구조를 바꾸고 에이전트가 저장소 전체를 복제하지 않고 필요한 파일과 이력만 요청하는 인터페이스도 더하고 있다. 함수 하나가 언제 바뀌었는지 알아보는 일이라면 빌드 환경부터 띄울 필요가 없다. 컴파일과 테스트에는 여전히 작업 공간이 필요하니, 코드를 살펴볼 때와 실행할 때 저장소에 접근하는 방식이 달라질 수 있다고 글은 말한다.

## Anthropic은 왜 Git 자체를 바꿨나

Anthropic은 Scion으로 서버를 넘어 클라이언트와 프로토콜까지 바꿨다. 얕은 복제와 내부 미러로 한동안 버텼지만 병합과 체크아웃이 늘면서 미러를 운영하고 사본을 최신으로 유지하는 일도 복잡해졌다. Scion은 대부분의 작업 환경이 온라인이라는 전제에서 시작한다. 클라이언트는 필요한 데이터를 서버에서 받아 오고 커밋과 리베이스와 병합도 서버에서 처리한다. 로컬에 전체 이력을 갖고 오프라인에서 일할 수 있는 Git의 장점 대신, 작업 환경마다 내려받아야 할 데이터를 줄이는 쪽을 택했다.

Scion은 기존 Git 클라이언트가 그대로 붙는 백엔드가 아니다. 자체 클라이언트와 프로토콜을 쓰고 Anthropic은 코드 리뷰, 검색, 권한 관리도 함께 지었다. 글은 Git에서 Scion으로 데이터를 옮긴 과정은 소개됐지만 거꾸로 일반 Git 저장소로 내보내거나 미러링하는 방법은 발표 글에서 확인되지 않는다고 짚는다. Anthropic도 대부분의 저장소에는 Git의 설계가 여전히 맞다고 설명한다. Scion은 초대형 저장소에서 수많은 작업 환경이 동시에 코드를 받아 가고 병합도 빠르게 느는 상황에서 나온 선택이다.

## 푸시가 빨라져도 main에 합치는 일은 남는다

에이전트 열 개가 각자 브랜치에 푸시하는 것과, 그 열 개의 변경을 main에 반영하는 것은 다르다. 앞쪽은 서버가 변경을 받아들이는 속도이고 뒤쪽부터는 변경을 어떤 순서로 합치고 검증할지라는 협업의 문제다.

Pando의 설계를 독립적으로 구현한 오픈소스 Git 서버 Aspen이 이 차이를 보여 준다. Aspen 팀은 git.git 저장소에서 브랜치 전용 URL을 쓴 자체 실험으로 5분 동안 초당 567회 푸시를 처리했다. main에 변경을 하나씩 순서대로 반영했을 때는 초당 약 4회였다. 다음 변경이 바로 앞 반영 결과에 기대기 때문이다. 두 숫자 모두 CI 실행은 빼고 단순 푸시만 잰 것이다.

그리고 변경을 합칠 수 있다는 것과 합친 결과가 제대로 돌아간다는 것도 다르다. 한 에이전트는 API 응답 형식을 바꾸고 다른 에이전트는 기존 응답 형식을 전제로 화면을 고쳤다고 해 보자. 서로 다른 파일을 건드렸다면 Git은 충돌 없이 합친다. 각 브랜치에서 테스트를 통과했어도, 두 변경을 함께 넣었을 때 화면이 제대로 동작하는지는 따로 확인해야 한다.

GitHub의 병합 큐는 최신 main에 큐에서 앞선 PR들의 변경과 이번 PR을 합친 상태를 만들어, 실제로 반영하기 전에 필수 검사를 돌린다. 검사를 통과한 여러 PR을 묶어 합칠 수도 있다. 다만 한 번에 합칠 PR 수를 늘린다고 각각 예약된 CI 검사까지 하나로 합쳐지는 건 아니다. 글은 Aspen에서 눈여겨볼 점이 여러 PR을 묶을 수 있다는 사실보다 서버가 main을 갱신하는 횟수라고 말한다. PR을 하나씩 반영하면 main 갱신이 차례로 끝나길 기다려야 한다. Aspen은 각 PR을 별도 커밋으로 남기면서도, 여러 PR의 변경이 다 들어간 결과를 만들어 main을 한 번만 갱신한다. PR이 몰릴 때 같은 브랜치를 거듭 갱신하는 비용을 줄이는 것이다. GitLab이 소스 관리 다음의 병목으로 CI, 보안 검토, 배포를 짚은 이유도 여기에 있다. 서버가 푸시를 더 많이 받아 낼 수 있게 되면, 그다음은 검증을 마친 변경을 얼마나 꾸준히 main에 반영하느냐가 중요해진다.

## 리뷰할 때 보는 기록도 바뀐다

앞선 GeekNews 글은 저장소를 옮겨도 PR에 쌓인 토론과 설계 판단까지 그대로 따라오지는 않는다고 했다. 에이전트와 일할 때는 어떤 제약을 줬는지, 다른 방법을 시도했다가 왜 버렸는지 같은 기록이 PR을 열기 전부터 쌓인다.

Zed의 Delta는 동료를 나와 에이전트의 작업 스레드에 초대한다. 리뷰어는 코드와 대화를 함께 보고 별도 작업 트리에서 수정도 시험할 수 있다. Delta 팀은 자기 제품 저장소에서 PR을 끄고 이 방식으로 일했지만 푸시와 빌드의 기준으로는 Git 커밋을 계속 썼다. 여기서 코드가 옮겨 가는 경로와 작업 기록이 옮겨 가는 경로가 갈린다. Delta는 대화와 편집 과정을 Git 커밋과 따로 DeltaDB에 기록한다. 기기 사이에 동기화한 기록은 로컬과 Delta 서버에 남으니, Git 저장소만 옮겨서는 따라오지 않는다. Entire CLI의 체크포인트는 Git 객체로 저장하지만 코드 브랜치와는 별도의 Git 참조를 써서, main만 푸시하면 세션 기록이 따라오지 않는다. 글은 예전에는 저장소를 옮길 때 PR과 이슈가 어디 남는지 따로 봐야 했다면, 이제는 에이전트와 주고받은 대화와 편집 기록도 같은 질문의 대상이 됐다고 말한다.

## 어디까지 바뀌고 있나

글은 사례를 표 하나로 정리한다.

| 사례 | 바꾼 층 | 달라진 것 | Git 명령 |
|---|---|---|---|
| OpenAI Pando | 서버와 저장소 | 브랜치별 푸시, 팩파일 재사용 | 유지 |
| GitHub | 서버와 저장소 | 팩 데이터와 브랜치 참조 분리 | 유지 |
| Cursor Continuity | 서버와 저장소 | S3에 변경 기록, 디스크는 캐시 | 유지 |
| Entire | 서버와 저장소(읽기) | 지역 미러에서 clone과 pull | 유지 |
| GitLab | 서버와 저장소 | 백엔드 재설계, 파일과 이력 조회 API | 유지 |
| Aspen | 서버와 저장소, 병합 | Pando 설계의 독립 구현, 병합 큐 | 유지 |
| Anthropic Scion | 클라이언트와 프로토콜, 서버와 저장소 | 자체 클라이언트, 서버에서 커밋과 병합 | 교체 |
| Zed Delta | 협업 흐름 | 작업 스레드에서 코드와 대화를 함께 리뷰 | 유지 |

에이전트가 일을 시작할 때 무엇을 얼마나 받아 올지, 사람이 결과를 넘겨받을 때 diff에 더해 작업 과정도 볼 수 있을지를 두고 실험이 이어지고 있다. 글은 몇 년 뒤에도 개발자는 같은 git push를 입력할지 모르지만 그 앞에서 에이전트가 코드를 가져오는 방식과 그 뒤에서 팀이 변경을 검토하고 합치는 방식은 지금과 꽤 달라져 있을 수 있다고 맺는다.

## 확인해 본 것과 읽을 때 생각할 점

글 안의 환산을 맞춰 봤다. 하루 3만 건 병합을 86,400초로 나누면 초당 약 0.35건, 하루 2,500만 회 체크아웃은 초당 약 289회로 글과 같다. 다만 각 숫자는 회사들의 자체 발표에서 나온 것이고 이 노트는 원 발표를 열지 않았다. Aspen의 초당 567회와 약 4회는 Aspen 팀의 자체 실험이고 CI 실행을 뺀 단순 푸시라는 단서가 붙어 있다. Scion을 다시 일반 Git으로 내보내는 방법이 확인되지 않는다는 지적은, 특정 회사의 자체 시스템에 묶일 때의 위험을 생각하게 한다.

이 글은 이 블로그가 다룬 여러 노트의 바닥을 받친다. [Factory Missions 노트](https://raphael-shin.github.io/jungseob-blog/posts/alvoeiro-factory-missions-multi-agent-architecture/)는 코드를 바꾸는 에이전트를 동시에 돌리면 서로 밟는다며 한 번에 하나씩 돌렸고 [AWS Emulator 노트](https://raphael-shin.github.io/jungseob-blog/posts/goldberg-agents-built-aws-emulator/)는 수백 개 에이전트가 동시에 고치고 병합 관문이 충돌과 퇴행을 걸렀다. 이 글의 "각각 통과한 변경을 합친 결과가 돌아가는지는 따로 확인해야 한다"는 대목이 그 두 선택이 같은 문제의 다른 답이라는 걸 보여 준다. [Fable 5.2 에이전트 1,000개 노트](https://raphael-shin.github.io/jungseob-blog/posts/anthropic-fable-5-2-thousand-agents-fermat-proof/)가 각 증명을 별도 파일과 브랜치로 나누고 병합을 따로 맡긴 것도, 이 글의 두 번째 층과 세 번째 층을 나눈 설계다.

내 일에 가져올 질문은 이렇다. 우리 팀에서 에이전트가 코드를 가져가는 횟수와 main에 반영되는 횟수는 각각 얼마이고 어디가 먼저 막히는가? 각각 통과한 변경을 합친 결과를 확인하는 단계가 있는가? 에이전트와 나눈 대화와 결정 기록은 저장소를 옮길 때 함께 따라오는가?
