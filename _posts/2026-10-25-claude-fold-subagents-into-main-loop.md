## TL;DR

- 서브에이전트끼리 같은 자료를 반복해서 전달하고 있다면, 하나의 에이전트가 전체 과정을 맡도록 바꿔볼 만하다. Anthropic은 여러 기업의 실제 운영 사례에서 이 방식이 답변 품질을 높이고 비용과 응답 시간을 줄이는 경우를 확인했다고 설명한다.
- 에이전트를 줄여도 업무별 전문 지식은 남길 수 있다. 일하는 절차는 **스킬**, 데이터 조회와 실제 작업은 **도구**로 분리하고, 담당 에이전트가 필요할 때 불러 쓰게 한다.
- 독립적으로 병렬 처리할 일이나 별도 검증이 필요한 일에는 서브에이전트가 여전히 유용하다. 먼저 실제 업무를 평가할 기준을 만들고, 하나씩 합쳐 보면서 결과가 좋아지는지 확인해야 한다.

## 왜 에이전트를 나눴는데 일이 더 복잡해질까

Anthropic의 Applied AI 팀이 소개한 한 기업은 고객을 응대하는 시스템에 전문 서브에이전트를 열두 개가량 두고 있었다. 업무를 잘게 나눈 결과, 고객에게 일관된 말투와 응대 방식을 유지하기가 어려워졌고 답변도 느려졌다.

서브에이전트는 별도의 대화 기록, 지침, 도구를 갖고 특정 일을 맡는 보조 에이전트다. 이를테면 메인 에이전트가 고객과 대화하다가 주문 관련 질문은 주문 담당에게, 배송 관련 질문은 배송 담당에게 넘기는 식이다. 이런 분담은 각 담당자가 독립적으로 일을 처리할 수 있을 때 유용하다.

문제는 담당자들이 같은 자료를 계속 주고받아야 할 때다. 다른 에이전트에게 일을 넘기려면 지금까지의 상황을 설명해야 하고, 일을 마친 에이전트는 결과를 요약해서 돌려준다. 이 과정에서 세부 조건이 빠질 수 있고, 넘겨받은 쪽이 이미 확인한 내용을 다시 조회할 수도 있다. 고객 입장에서는 같은 질문에 답을 받는 데 거치는 단계만 늘어난다.

원문은 기업이 부서마다 에이전트를 하나씩 만들고, 그 위에 전체를 조율하는 에이전트를 얹는 경우가 많다고 지적한다. 각 팀이 자기 부분만 평가하면 개별 점수는 좋아도 고객의 요청을 처음부터 끝까지 해결했는지는 놓치기 쉽다. 팀별 지침을 계속 덧붙이다 보면 규칙끼리 충돌하거나 답변의 말투가 달라지는 문제도 생긴다.

## 하나의 에이전트가 전체 흐름을 맡는다는 뜻

원문 제목의 ‘fold subagents into your main agent loop’는 서브에이전트가 하던 일을 메인 에이전트로 옮긴다는 뜻이다. 기존 노트의 ‘메인 루프로 접어 넣는다’는 표현은 이 과정을 직역한 말이었다.

여기서 **루프**는 에이전트가 작업을 끝낼 때까지 반복하는 과정을 뜻한다. 다음에 할 일을 정하고, 필요한 도구를 실행하고, 결과를 읽은 뒤 다시 다음 행동을 정한다. 하나의 에이전트가 이 과정을 이어 가면 계획을 세운 주체가 실행 결과까지 직접 보고 계획을 고칠 수 있다.

이 방식에서도 여러 도구를 동시에 실행할 수 있다. 도구 실행을 담당하는 프로그램이 결과를 모아 같은 에이전트에게 돌려주면 된다. 에이전트 하나를 쓴다고 모든 조회와 작업을 반드시 순서대로 처리해야 하는 것은 아니다.

비용 한도, 최대 실행 횟수, 쓰기 작업의 승인 같은 제한은 실행 프로그램에 남긴다. 원문에서 말하는 **하네스**가 이 실행 프로그램이다. 모델이 다음 행동을 고르더라도, 허용된 작업의 범위는 프로그램이 통제해야 한다.

## 전문 지식은 스킬로, 실제 작업은 도구로

에이전트를 하나로 합치면 모든 업무 지침을 긴 프롬프트에 넣어야 한다고 생각하기 쉽다. 원문이 제안하는 방식은 필요한 지침과 도구를 그때그때 불러오는 것이다.

처음에는 에이전트에게 스킬과 도구의 짧은 설명만 보여준다. 해당 업무를 처리할 때 자세한 절차나 도구 사용법을 읽게 한다. 원문의 **점진적 공개(progressive disclosure)**는 이렇게 ‘필요할 때 자세한 내용을 불러오기’를 뜻한다.

업무 지식을 어디에 둘지는 다음처럼 구분한다.

| 필요한 것 | 두는 곳 | 예시 |
| --- | --- | --- |
| 일을 처리하는 순서와 판단 기준 | 스킬 | 고객 문의를 확인하는 순서, 답변 전에 점검할 항목 |
| 최신 데이터 조회나 실제 작업 실행 | 도구 | 주문 상태 조회, 시스템에 변경 사항 기록 |
| 가끔 찾아보는 사실과 참고 문서 | 지식 베이스나 스킬의 참고 파일 | 제품 사양, 정책, 지표의 정의 |

이렇게 하면 각 팀은 자기 업무의 스킬과 도구를 관리할 수 있다. 작은 중앙 팀은 공통 시스템 지침과 전체 업무의 품질을 책임진다. 팀마다 에이전트를 따로 운영하지 않아도 전문성을 유지할 수 있다는 설명이다.

원문은 일부 업무가 명확한 시스템 지침 하나, 간단한 데이터 조회 도구 4~5개, 출력 규칙으로도 충분했다고 전한다. 도구가 많아지면 필요한 도구를 검색해서 불러오는 방식을 권한다. 시스템 프롬프트에 도구 정의를 30~50개 넘게 넣으면 선택 정확도가 떨어지는 경향이 있다는 설명도 나온다. 이 숫자는 Anthropic이 제시한 경험적 기준이며, 모든 시스템에 적용되는 한계값은 아니다.

사용자 권한과 작업의 선행 조건은 도구가 직접 확인해야 한다. 예를 들어 앞선 조회 결과가 있어야 실행할 수 있는 도구라면, 그 결과가 있는지 검사하고 없으면 필요한 절차를 안내한다. 사용자가 볼 수 없는 데이터는 도구 단계에서 접근을 거절한다.

## 서브에이전트를 남겨두는 편이 나은 경우

Anthropic도 자체 멀티에이전트 연구 시스템에서 서브에이전트를 사용한다. 이번 글은 다음과 같은 상황에서는 별도 에이전트가 유용하다고 설명한다.

- **한 에이전트가 읽어야 할 내용이 너무 많아져 성능이 떨어질 때.** 대화 기록과 작업 자료가 쌓이면서 실제로 답변 품질이 나빠지는지 측정해야 한다.
- **서로 독립적인 일을 병렬로 처리할 때.** 다른 조사자의 진행 상황을 몰라도 수행할 수 있는 조사나, 입력과 출력이 명확한 구성요소의 작업이 여기에 해당한다. 작업이 끝나면 보조 에이전트의 임시 대화 기록을 버릴 수 있다.
- **하나의 에이전트가 도구를 제대로 고르지 못하거나 지침끼리 충돌할 때.** 역할을 분리하는 편이 나은지 평가로 확인할 수 있다.

결과를 따로 검증하는 에이전트도 유용한 예다. 원문은 역할을 나눌 때 다른 작업의 사정을 얼마나 알아야 하는지 살펴보라고 권한다. 다른 담당자의 상세한 기록을 계속 알아야 한다면, 둘을 분리한 탓에 정보 전달 비용이 커지고 있을 수 있다.

## 이미 여러 에이전트를 쓰고 있다면 어떻게 바꿀까

먼저 지금 시스템이 얼마나 일을 잘 끝내는지 평가할 기준을 만든다. 원문은 정답이나 기대 결과가 분명한 대표 사례 10개 정도로도 시작할 수 있다고 제안한다. 중앙 팀은 전체 업무를 평가하고, 각 업무 담당 팀은 자기 스킬의 세부 평가를 보탠다.

그다음에는 한 번에 하나씩 구조를 바꾼다. 전환 방법은 크게 세 가지다.

| 방법 | 바꾸는 내용 | 적용하기 좋은 상황 |
| --- | --- | --- |
| 자주 함께 쓰는 전문 에이전트 합치기 | 같은 자료를 보거나 앞선 결과를 이어받는 담당자를 하나로 묶는다. | 실제 요청에서 A 다음 B가 자주 실행될 때 |
| 서브에이전트를 도구처럼 호출하기 | 고객과의 대화는 메인 에이전트가 맡고, 필요한 작업만 보조 에이전트에 요청한다. | 별도 에이전트는 필요하지만 대화 전체를 넘길 필요는 없을 때 |
| 서브에이전트를 스킬과 도구로 바꾸기 | 업무 지침은 스킬로, API 호출은 도구로 옮겨 메인 에이전트가 직접 처리한다. | 업무를 분리할 이점보다 정보 전달 부담이 클 때 |

두 번째 방법은 기존 서브에이전트를 크게 고치지 않고 시도할 수 있다. 다만 내부에서는 여전히 별도 모델이 실행되고 요약 결과를 돌려주므로, 호출 시간과 정보 손실 문제는 남는다. 고객과 직접 대화해야 하는 담당자에게만 대화 자체를 넘기라는 것이 원문의 권고다.

세 번째 방법을 적용할 때는 기존 구조와 바꾼 구조에 같은 평가를 실행한다. 전체 점수뿐 아니라 이전에는 성공했는데 변경 후 실패한 요청이 있는지도 살펴야 한다.

## 빨라졌지만 필요한 확인을 건너뛴 사례

원문에 나온 고객 지원 에이전트 실험에서는 서브에이전트를 합친 뒤 응답 시간이 줄었지만, 잘 처리하던 절차 하나가 깨졌다. 메인 에이전트가 주문 조회 도구를 갖게 되자 배송 담당에게 배송일을 확인하지 않고 스스로 답한 것이다.

이 오류는 같은 테스트를 두 번 실행했을 때 한 번만 나타났다. 한 번 통과했다고 변경이 안전하다고 판단하기 어려운 이유다. 실제 운영에서 함께 실행되는 에이전트 조합과 반드시 지켜야 할 규칙을 평가에 넣고, 각 사례를 반복해서 실행해야 한다.

작업이 빨라졌는지와 사용자의 요청을 정확히 해결했는지는 따로 확인해야 한다. 바꾼 구조의 성능이 나빠졌다면 해당 서브에이전트를 유지하고, 문제가 생긴 절차부터 다시 살펴본다.

## 원문의 수치는 어디까지 받아들여야 할까

Anthropic은 여러 기업의 운영 사례에서 스킬을 갖춘 단일 에이전트가 복잡한 멀티에이전트 구조보다 품질이 좋은 경우가 많았다고 설명한다. 한 고객 사례에서는 실행 속도가 약 2배 빨라졌다고 전한다. 필요한 지침만 불러오는 방식 등을 적용하면서 Claude Code의 시스템 프롬프트를 80% 넘게 줄였다는 설명도 있다.

다만 이 수치들은 서로 다른 사례에서 나온 결과다. 프롬프트를 80% 줄였다고 비용이나 실행 시간도 같은 비율로 줄었다는 뜻은 아니다. 기업별 비교 대상, 모델, 평가 항목, 세부 점수가 충분히 공개되어 있지 않아 모든 업무에서 단일 에이전트가 우월하다고 일반화하기도 어렵다.

자기 시스템에 적용할 때는 자주 함께 실행되는 서브에이전트 한 쌍부터 살펴볼 수 있다. 같은 자료를 반복해서 주고받는다면 합친 버전을 만들고, 같은 업무 사례로 정확도와 비용, 실행 시간을 비교한다. 그 결과가 다음 변경의 기준이 된다.
