## TL;DR

- Emre Okcular(OpenAI 솔루션 아키텍트)는 에이전트 메모리를 컨텍스트 엔지니어링의 한 갈래로 본다. 목표는 원하는 결과 가능성을 최대로 올리는 가장 작은 고신호 컨텍스트이고, 창이 유한하므로 프롬프트에 넣는 모든 것이 고정된 토큰 예산을 놓고 경쟁한다.
- 실패는 네 유형으로 나눈다. 도구 출력으로 토큰이 갑자기 튀는 폭주(burst), 모순된 지시가 섞이는 충돌(conflict), 잘못된 정보가 요약과 상태 객체를 타고 번지는 오염(poisoning), 겹치는 도구 정의가 쌓이는 잡음(noise)이다.
- 대응은 세 묶음이다. 컨텍스트 창에 맞게 줄이는 트리밍·컴팩션·요약(단기), 하위 에이전트로 나누는 격리와 라우팅, 메모리를 추출해 필요한 때 꺼내는 장기 메모리다. 트리밍은 빠르지만 정보를 잃고, 요약은 정보를 지키되 지연과 비용이 든다.
- 데모는 가상의 IT 지원 에이전트에서 도구 출력 하나가 컨텍스트를 300~400토큰에서 3,000토큰 넘게 부풀린 것과, 요약을 시스템 프롬프트에 넣었더니 새 세션에서 맥락을 이어받은 것을 보인다. 측정된 평가 결과는 없고, 평가는 메모리 켬·끔 비교와 메모리 전용 평가를 직접 만들라는 조언으로만 나온다.
- 현행 OpenAI 문서와 대조하면 서버 측 컴팩션은 사람이 읽을 수 없는 암호화 항목을 쓰는데, 데모의 요약은 읽을 수 있는 메모리 객체다. 이 노트는 영어 자막 전체(57:44)와 쿡북, 문서를 읽고 정리했다.

## 영상에 대하여

OpenAI 채널이 2025년 12월 4일에 올린 57분 44초 영상이다. 영어 자동생성 자막만 있고 전체를 읽었으며 마지막 자막은 57분대 중반이다. 사회자는 스타트업 마케팅 팀의 Michaela이고 발표자는 솔루션 아키텍트 Emre Okcular(자막에는 Emry)다. 앞선 Build Hour에서 Responses API로 에이전트를 처음부터 만들고 에이전트 RFT를 다뤘으며 이번이 메모리 편이라는 소개가 나온다. 설명란의 목차는 컨텍스트 엔지니어링(0:00), 컨텍스트 수명 주기 데모(10:44), 기법(20:13), 재구성·맞춤 데모(26:49), 결론(39:16), 질의응답(42:45)이다. 쿡북의 [세션 메모리 예제](https://cookbook.openai.com/examples/agents_sdk/session_memory)와 Agents SDK, 코드 저장소가 함께 소개된다. 발표자는 데모 앱도 저장소에 올리겠다고 말한다.

## 문제: 컨텍스트는 유한하다

발표는 Andrej Karpathy의 컨텍스트 엔지니어링 정의에서 시작한다. 판단이 필요해 기술(art)이고 구체적 패턴과 측정 가능한 효과가 있어 과학(science)이다. 프롬프트 엔지니어링, 구조화된 출력, RAG, 상태와 이력 관리, 메모리가 모두 이 큰 틀 안에 들어간다. 메모리는 파일, 데이터베이스, 메모리 도구 같은 지속 또는 반지속 저장소에 핵심 정보를 올리고 꺼내는 일이다. 에이전트가 강력해져도 병목은 컨텍스트가 유한하다는 점이다. 지시, 대화 이력, 도구 출력이 모두 고정된 토큰 예산을 놓고 다투기 때문에 오래 도는 도구 중심 에이전트는 품질이 떨어진다.

네 가지 실패 유형은 예시와 함께 나온다. 폭주는 한 턴에서 도구 출력이 크게 늘어 토큰이 갑자기 튀는 현상이다. 충돌은 시스템 지시가 "보증이 유효하지 않으면 환불하지 않는다"고 하는데 도구 결과가 VIP는 환불 대상이라 하고 에이전트가 급한 여행을 이유로 환불해 주겠다고 답하는 식이다. 오염은 환각이나 부정확한 정보가 어느 단계에서 섞여 여러 턴에 걸쳐 번지는 것으로, 손실이 큰 요약 편집, 시간이 지나며 서로 모순되는 자유형 노트, 새 요약을 옛 요약이 덮는 경우가 함정으로 꼽힌다. 잡음은 도구 정의가 너무 많거나 서로 비슷할 때 생긴다. 에이전트 유형도 세 가지 컨텍스트 프로필로 나눈다. 검색 증강 비서는 검색된 지식과 인용이 컨텍스트를 채우고 도구 중심 워크플로는 도구 반환값이 채우며 대화형 컨시어지는 늘어나는 대화 이력이 채운다. 시스템 지시와 도구 정의는 대체로 고정이고 도구 결과, 검색된 지식, 메모리, 대화 이력이 동적이어서 이 동적인 쪽을 조절한다.

## 단기와 장기, 세 갈래 전략

세 갈래는 이렇다. 재구성과 맞춤(reshape and fit)은 트리밍, 컴팩션, 요약이고 격리와 라우팅(isolate and route)은 컨텍스트와 도구를 하위 에이전트로 넘기는 것이며 추출과 검색(extract and retrieve)은 메모리 추출, 상태 관리, 메모리 검색이다. 앞의 둘을 단기 메모리(세션 내 기법), 마지막을 장기 메모리(교차 세션)로 부른다. 단기 메모리는 활성 대화 중에 컨텍스트 창을 최대한 쓰는 일이고 장기 메모리는 세션을 넘는 연속성을 만드는 일이다. 프롬프트와 도구 위생도 원칙으로 둔다. 시스템 프롬프트를 짧고 구조적으로 유지하고 소수의 대표 예시를 쓰고 도구가 겹치지 않게 하며 모호한 정의를 피한다. "사람이 고를 수 없는 도구는 모델도 못 고른다"는 말이 이 대목에 나온다. 도구는 많다고 좋지 않고 의미 있는 필드만 사람이 읽을 수 있는 식별자와 함께 돌려주라고 한다.

## 세 가지 줄이기 기법

트리밍은 가장 단순하다. 최근 N턴만 남기고 오래된 턴을 버린다. 컴팩션은 오래된 턴에서 도구 호출과 결과만 제거하고 나머지 메시지는 두며 도구 자리표시자는 남긴다. 요약은 이전 메시지를 구조화된 요약으로 압축해 이력에 다시 넣는다. 휴리스틱으로는 프로덕션 컨텍스트 스냅샷을 모으고(좋아요·싫어요 포함), 평균 토큰 크기와 세션당 작업 종류를 따져 보라고 한다. 사용자 메시지부터 다음 사용자 메시지 전까지가 한 턴이므로 턴 중간에서 자르면 맥락을 잃는다. 한계에 닿기를 기다리지 말고 40%나 80% 같은 임계값을 정해 작동시키고 절약한 토큰을 추적한다. 이 기법들은 비용 절감에도 쓰인다는 설명이다.

트리밍과 요약의 선택 기준은 이렇다. 트리밍은 빠르고 추가 지연이 없지만 이미 있는 정보를 잃고 도구 중심 작업이나 짧은 워크플로에 맞는다. 요약은 정보를 버리지 않지만 모델을 한 번 더 불러 지연과 비용이 든다. 장기 에이전트의 작업들이 서로 독립이면 트리밍이 낫고 여러 턴과 작업에 걸쳐 쓸모 있는 정보가 쌓이고 서로 의존하면 요약이 낫다.

## 데모: 도구 출력 하나가 컨텍스트를 부풀린다

데모 앱은 Next.js로 만든 IT 문제 해결 에이전트이고 OpenAI Agents SDK를 쓴다. 두 에이전트를 나란히 돌려 같은 모델과 추론 수준에서 메모리 설정만 다르게 비교하며 주문 조회와 환불 정책 조회 두 도구가 붙어 있다. 컨텍스트 사용 막대가 시스템 지시(84토큰), 사용자 입력, 도구 토큰, 에이전트 출력을 턴마다 보여 준다. 2턴에는 300~400토큰이던 컨텍스트가 MacBook Pro 2014 환불 정책 도구 호출 직후 3,000토큰을 넘는다. 도구가 정책 전문을 모두 컨텍스트에 쏟아부었기 때문이고 발표자는 이를 폭주의 예로 든다.

트리밍은 최대 3턴을 임계값으로 두고 3턴을 유지하게 설정한 데모에서 6턴 끝에 도구 출력이 사라지고 새 컨텍스트가 된다. 컴팩션은 트리거 4턴, 유지 2턴으로 설정해 같은 효과를 낸다. 요약은 트리거 5턴, 유지 3턴으로 설정한다. 사용자가 기기 모델(2014년형 MacBook Pro 14인치), 구매지(암스테르담)와 거주지(미국), 배터리 교체, OS 업데이트, 이미 해 본 하드 리셋을 말하고 나서 요약이 일어나면, 컨텍스트에 주황색 "메모리" 항목이 생겨 사용자 메시지로 들어간다. 요약 프롬프트는 모순에 주의하고 시간 순서를 지키고 환각을 통제하라고 지시하며 제품·환경, 보고된 문제, 효과가 있었던 것과 없었던 것, 시도한 단계, 식별자, 주요 시점, 도구 성능 통찰, 현재 상태, 다음 권장 단계를 구조화된 필드로 쓰게 한다.

크로스 세션 주입은 이렇게 보인다. 에이전트를 초기화하고 기능을 켜면 앞서 만든 요약이 새 세션의 시스템 프롬프트에 들어가고 인사만 보냈는데 오른쪽 에이전트가 "MacOS Sequoia 업데이트 뒤 인터넷 문제가 계속되나요?"라고 묻는다. "같은 MacBook인데 Tahoe로 어떻게 올리나"라고 물으면 기기와 버전을 이미 알고 답한다. 주입할 때의 지시도 중요하다. 메모리는 지시가 아니라 오래되었거나 불완전할 수 있는 참고 정보로 취급하고 우선순위 규칙을 두어 모델이 메모리에 지나치게 기대지 않게 하며 비밀 저장 금지와 인젝션 방어를 가드레일로 넣는다.

## 격리, 추출, 검색, 모범 사례

격리와 라우팅은 컨텍스트와 도구를 하위 에이전트로 넘기는 것이다. 새 컨텍스트가 만들어져 충돌과 오염을 줄인다. 메모리의 모양은 단순하게 시작해 필요할 때 키우라고 한다. 일관된 구조 형식을 쓰고 사람이 자연스럽게 기억할 것을 우선하며 가장 복잡한 형태는 한 문단짜리 메모리다. 추출은 라이브 턴에서 메모리 도구로 JSON 한두 문장 노트를 저장하거나 타입 안전한 함수와 마크다운을 쓴다. 상태 관리는 목표 등을 담은 상태 객체를 정의해 일정 주기로 시스템 프롬프트에 다시 넣거나 새 세션에 넣는다. 검색은 RAG와 같아서 장기 저장소(벡터 DB)에 두고 라이브 턴에서 검색·필터·랭크해 주입한다.

모범 사례는 셋이다. 전형적 컨텍스트를 이해하고 무엇이 의미 있는지 정의한다. 언제 어떻게 기억하고 잊을지 정한다. 안정적이고 재사용 가능한 사실은 메모리로 승격하고 오래되었거나 확신이 낮은 정보는 적극적으로 잊으며 메모리를 정리·병합·통합한다. 평가는 메모리 켬과 끔을 비교하는 기존 평가, 긴 과제와 긴 컨텍스트를 겨냥한 메모리 전용 평가(요약 품질, 주입 시점, 주입 프롬프트), 트리밍과 컴팩션의 임계값 같은 휴리스틱 탐색으로 나뉜다. 좋은 요약의 골든 예시는 50개쯤 모으라고 한다. 컨텍스트 임계값에 닿지 않는 에이전트라면 메모리 개선이 필요 없을 수도 있다고 덧붙인다.

## 질의응답에서 나온 설계

범위(scope)는 두 층이다. 사용자에 관한 전역 메모리(친근한 어조를 좋아함, 미국 거주)와 특정 세션의 메모리(이번 여행은 창가 좌석)를 분리하고 같은 선호가 여러 번 반복되면 세션 메모리를 전역 메모리로 승격한다. 낡은 메모리 정리는 시간 태그와 가중 감쇠 두 가지다. 두 달 전 "개를 좋아한다"와 오늘의 "고양이를 좋아한다"가 충돌하면 시간 태그로 최신을 알아보고 덮어쓰며 사용 사례에 따라 오래된 것의 가중치를 낮추거나 모두 똑같이 중요하다고 보고 통합한다. 확장은 방식에 달려 있다. 검색 기반이면 벡터 DB의 샤딩, 임베딩, 필터링, 랭킹 같은 검색 시스템을 키우고 요약을 디스크에 두는 방식이면 많은 텍스트의 저장과 관리 문제가 된다. 일부 사용자에게 먼저 켜 보는 시험 도입을 권하며 여행 컨시어지(좌석·호텔·식사 취향)는 메모리 종류가 한정적이고 라이프 코치는 꿈과 목표를 포함해 기억량이 빠르게 늘어난다고 대비한다. 추천 라이브러리를 묻는 질문에는 Agents SDK를 시작점으로 들면서 이 영역의 라이브러리가 빠르게 변한다고 답한다.

## 대조해서 확인한 점

쿡북 페이지는 제목이 "Context Engineering - Short-Term Memory Management with Sessions"이고 트리밍과 요약을 세션으로 구현하는 예제다. 영상이 소개한 기법과 일치한다. 도구 수에 대해 영상은 "작게, 겹치지 않게"라고만 말하며 숫자를 주지 않는다. 현행 함수 호출 문서는 한 턴 시작 시점에 쓸 수 있는 함수를 20개 미만으로 두라는 권고를 "소프트 제안"이라고 적고 자주 안 쓰는 도구는 tool search로 미루라고 한다(gpt-5.4 이상 모델).

컴팩션은 영상 이후 API 기능으로 나왔다. 현행 가이드에 따르면 Responses 요청에서 `context_management`에 `compact_threshold`를 주면 토큰 수가 임계값을 넘을 때 서버가 컴팩션을 수행하고 반환되는 컴팩션 항목은 암호화되어 사람이 읽도록 만들어지지 않았다. 별도의 `/responses/compact` 엔드포인트로 상태 없이 호출할 수도 있다. 영상의 요약은 사람이 읽고 편집할 수 있는 구조화 메모리 객체여서, 검수·병합·크로스 세션 재사용이 필요하면 직접 요약을, 단순히 창을 관리하면 서버 측 컴팩션을 쓰는 식으로 갈릴 수 있다. 이 구분은 이 노트의 해석이며 문서가 직접 비교하지는 않는다. 앞서 정리한 [컴팩션 요약 자기 주입 노트](https://raphael-shin.github.io/jungseob-blog/posts/compaction-summary-self-injection/)는 요약을 시스템 프롬프트에 넣을 때의 위험을 다룬다.

## 읽을 때 유의할 점

첫째, 데모는 가상의 IT 지원 시나리오이고 정량 결과가 없다. 토큰이 줄었다는 막대 그림은 있지만 정확도나 비용 비교는 나오지 않는다. 둘째, 임계값(40%, 80%, 3턴 등)은 예시이며 어떤 근거로 정했는지 설명이 없다. 셋째, 요약을 그대로 시스템 프롬프트에 넣는 방식은 요약에 섞인 오류와 지시가 계속 영향을 주는 경로가 될 수 있다. 영상도 이를 오염이라 부르지만 검증 절차(요약 검수, 출처 표시)는 구체적으로 제시하지 않는다. 넷째, 발표자는 OpenAI 직원이고 Agents SDK를 시작점으로 권한다. 다섯째, 전역·세션 범위와 승격 규칙은 개념 수준이고 개인정보와 삭제 요청 처리는 다루지 않는다.

그래도 점검 질문은 선명하다. 우리 에이전트의 컨텍스트는 검색, 도구, 대화 중 무엇이 채우는가, 자르기와 요약 중 어느 쪽이 맞는 작업 구조인가, 메모리를 켠 것과 끈 것의 차이를 어떤 평가로 볼 것인가, 오래된 메모리가 새 메모리와 충돌하면 무엇이 이기는가. 같은 주제를 다룬 [rari의 메모리 스택 노트](https://raphael-shin.github.io/jungseob-blog/posts/whrrari-ai-memory-stack/)와 [메모리 대신 문서를 주자는 노트](https://raphael-shin.github.io/jungseob-blog/posts/agents-need-documentation-not-memory/)를 함께 보면 설계 선택지가 넓어진다. 데이터베이스 쪽에서 본 같은 주제는 [MongoDB 발표 정리](https://raphael-shin.github.io/jungseob-blog/posts/alake-mongodb-architecting-agent-memory/)에 있다.
